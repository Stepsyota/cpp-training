Этот текст — ровно тот минимум, после которого можно открывать

Код в примерах — учебный, не решения задач. Задачи чуть другие,
чтобы ты сам собрал кусочки, а не скопировал абзац.

## 1. Зачем потоки

Обычная программа — один повар на одной плите. Инструкции идут друг за
другом: пока суп не закипит, салат не начнётся.

**Поток (thread)** — ещё один повар на той же кухне. У него свой счётчик
инструкций, свой стек, свои локальные переменные. Но холодильник один:
куча, глобальные переменные, объекты, на которые оба держат ссылки.

Поэтому потоки умеют две полезные вещи:

- **параллелить работу** — два ядра считают две половины массива;
- **не блокировать друг друга** — один ждёт сеть, второй рисует интерфейс.

И одну опасную: оба могут одновременно трогать одни и те же данные.
В C++ это не «иногда неправильный ответ». Это **гонка данных
(data race)**, а она — неопределённое поведение. Компилятор имеет право
сложить программу как угодно, в том числе «правильно на твоём ноутбуке
и сломать на сервере».

Процесс (твоя программа) — квартира. Потоки — жильцы этой квартиры.
Межпроцессное взаимодействие — это уже переписка между квартирами,
здесь его не будет: все задачи живут в одном процессе и делят память.

## 2. Что происходит на машине

У процессора несколько **ядер** — отдельных исполнителей. Поток сам по
себе не бежит: его инструкции выполняет какое-то ядро, как повар стоит
у плиты. Ядер мало (4, 8, 16), потоков может быть больше. Планировщик ОС
решает, *кто сейчас у плиты*.

**«Отдать ядро другому»** значит: ядро перестаёт выполнять инструкции
потока A и начинает выполнять инструкции потока B. A не закончился —
его просто поставили на паузу (сохранили регистры и адрес следующей
команды) и усадили за плиту B. Через миллисекунды могут поменять снова.
Это и есть **вытеснение**.

Если программных потоков больше, чем свободных исполнителей, они делят
железо по очереди. Даже когда исполнителей хватает, ОС всё равно может
снять поток с ядра (подошёл квант времени, пришло прерывание, поток сам
ушёл в ожидание).

### Ядра CPU и потоки `std::thread` — разные вещи

На коробке Ryzen 5 5500 написано **6 ядер / 12 потоков**. Это не лимит
на `std::thread`. Это железо:


| Слово                        | Что это                                                                                                                                                                                                      |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Ядро**                     | Физический исполнитель. 6 ядер ≈ до 6 кусков работы *одновременно*.                                                                                                                                          |
| **Поток процессора (SMT)**   | У каждого ядра Ryzen по два аппаратных контекста. Ядро умеет вперемешку крутить *два* потока, чтобы простой одного (промах кэша, ожидание памяти) заполнять работой второго. ОС видит **12 логических CPU**. |
| **Поток ОС /** `std::thread` | Сущность, которую создаёшь ты. Их может быть 2, 20 или 2000. Планировщик раскидывает их по 12 логическим CPU.                                                                                                |


C++ программа **не** прибита к одному ядру. `main` стартует на каком-то
одном логическом CPU, а каждый новый `std::thread` ОС может посадить
на любой свободный. Отдельного «пула, из которого ядра берут потоки»
в языке нет: есть очередь *готовых к выполнению* потоков (её ведёт ОС),
и каждый логический CPU берёт оттуда работу.

Зачем тогда программные потоки, если ядер всего шесть:

- **Параллелизм** — два потока на двух ядрах считают одновременно,
стенка в стенку. Это ускорение CPU-работы.
- **Совмещение простоев** — один поток ждёт диск или `sleep`, ядро
в это время крутит другой. Это не «магия ускорения от переключения»,
а чтобы простой одного не останавливал всю программу.

Создать потоков больше, чем 12, можно. Пользы на чистом счёте обычно
мало: они начнут отбирать друг у друга кванты. Имеет смысл, когда много
ожидания (сеть, диск) или когда режешь работу на удобные куски, а пул
ограничиваешь числом ядер (`std::thread::hardware_concurrency()` на
твоём 5500 вернёт 12).

Из этого следуют три факта, которые стоит держать в голове всегда:

1. **Порядок между потоками не обещан.** Поток A может целиком
  отработать раньше B, позже, или их инструкции перемешаются.
2. **Порядок записей, который ты написал в одном потоке, другой поток
  без синхронизации может увидеть иначе.** Ты пишешь
   `data = 42; ready = true;`, а соседний поток иногда видит
   `ready == true`, но ещё старый `data`. Компилятор и процессор имеют
   право переставить *независимые* записи (между ними нет связи с точки
   зрения *этого* потока) и показать их другому ядру в другом порядке.
   Синхронизация (мьютекс, `join`, `future::get`, атомик) как раз и
   ставит барьер: «вот тут другой поток обязан увидеть то, что я сделал».
3. **Даже** `++x` **— не одна инструкция.** Это прочитал → прибавил → записал.
  Между этими шагами ядро могут отдать другому потоку — и тот прочитает
   ещё старое значение.

Пока ты не синхронизировал доступ, рассуждать «ну они же почти не
пересекаются» нельзя.

## 3. `std::thread`: запустить и дождаться

Заголовок: `<thread>`.

```cpp
#include <iostream>
#include <thread>

void countdown() {
    std::cout << "3... 2... 1...\n";
}

int main() {
    std::thread worker(countdown);  // поток уже бежит
    worker.join();                  // main встаёт и ждёт конца worker
    std::cout << "поехали\n";
}
```

Конструктор `std::thread` сразу стартует функцию в новом потоке.
Аргументы, если нужны, передаются следом: `std::thread(fn, a, b)`.
По значению они **копируются** в новый поток. Чтобы передать ссылку
на объект из `main`, нужен `std::ref(obj)` — иначе уйдёшь в копию
и будешь удивляться, почему оригинал не меняется.

### `join` и `detach`

У потока два честных конца:


| Метод      | Смысл                                                                                                                   |
| ---------- | ----------------------------------------------------------------------------------------------------------------------- |
| `join()`   | «Я подожду, пока ты закончишь». После `join` поток мёртв, объект `std::thread` пустой.                                  |
| `detach()` | «Живи сам по себе». Ты больше не узнаешь, когда он закончил, и не должен трогать его данные после того, как они умерли. |


Для учебных задач почти всегда нужен `join`. `detach` легко превращается
в **use-after-free**: жизнь объекта уже кончилась (стек функции ушёл,
память больше не твоя), а отсоединённый поток всё ещё читает её по
старой ссылке. Это как отдать ключ от квартиры, которую уже снесли:
дверь ещё может открыться, но внутри уже чужая стройка. Повезёт —
мусор в переменной; не повезёт — падение. Для стандарта C++ оба варианта
одинаково незаконны.

**Правило жизни** `std::thread`**:** уничтожается не поток ОС, а **объект-
ручка** `std::thread` (обычно локальная переменная вроде `t`). Пока ты
не сделал `join` или `detach`, эта ручка *владеет* живым потоком —
она joinable. Если ручка умирает в таком состоянии (вышли из функции,
сработал деструктор `t`), стандарт считает это ошибкой программиста:
деструктор вызывает `std::terminate`, процесс падает. Забыл `join` —
это не «ну ладно, поток доработает», это аборт.

```cpp
void bad() {
    std::thread t([] { /* ... */ });  // t — ручка на стеке bad()
    // забыли t.join()
}   // здесь умирает t, поток ещё joinable → std::terminate
```



### Как понять, что это другой поток

```cpp
const auto here = std::this_thread::get_id();
```

У каждого потока свой `std::thread::id`. Это номер *того, кто сейчас
выполняет эту строчку*, а не «номер функции».

Два разных способа вызвать `check`:

```cpp
check();                              // та же кухня, тот же повар — id совпадёт
std::thread t(check); t.join();       // другой повар — id другой
```

Если ты просто написал `check()`, функция ушла «в фон» только в твоей
голове: процессор так и остался в текущем потоке. Тест первой задачи
как раз сравнивает id внутри `check` с id вызывающего кода и требует,
чтобы они **не** совпали.

`std::this_thread::sleep_for(20ms)` усыпляет **текущий** поток: ОС
снимает его с ядра и может посадить туда любой другой *готовый* поток.
Ядро 20 мс вхолостую не крутится. Это не синхронизация, а пауза: ты не
узнаешь, что сделал сосед, и не разбудишь конкретный поток.

Принудительно переключить «ядро, возьми поток X» из переносимого C++
нельзя. Можно только *отдать* процессор: `sleep_for`, ожидание на
мьютексе/`cv`/`join`, либо намёк `std::this_thread::yield()` — «если
есть кому бежать, бегите, я подожду». Кого именно поставят, решает ОС.

### Лямбда в потоке

```cpp
int n = 0;
std::thread t([&n] { n = 42; });
t.join();
// здесь n уже 42: join — барьер, запись видна
```

Квадратные скобки лямбды — *что из внешнего мира ей видно*. Это не
«передать мьютекс в поток», а список захвата.

| Захват | Что видит лямбда |
|--------|------------------|
| `[]` | ничего. Члены класса и локальные переменные недоступны. |
| `[&n]` / `[=n]` | одну переменную: по ссылке или копией. |
| `[&]` | все **локальные** переменные текущей функции — по ссылке. |
| `[=]` | те же локальные — копиями. |
| `[this]` | объект, чей метод сейчас выполняется: `this->jobs`, `this->m`. |

В методе класса `[&]` ещё и неявно тащит `this` (иначе члены не достать).
Поэтому в кузнице `[&]` и `[this]` часто *ведут себя одинаково*: кузнец
живёт, пока жив пул. Разница в *намерении*:

- `[this]` — «мне нужен объект-мастерская». Явно и честно.
- `[&]` — «мне нужны локальные переменные конструктора по ссылке».
  Если по ошибке захватишь `worker_count` или временную `job` с стека
  конструктора, а поток переживёт этот стек — снова use-after-free.

В пуле кузнецу нужны `jobs` / `m` / `cv` / `stopped` — это поля, не
локальные. Пиши `[this]`. Локальный счётчик `n` в `main` — `[&n]` и
обязательный `join` до конца `n`.

Итог главы, он же смысл задачи **01**: создать поток и `join`-ить его,
чтобы работа точно закончилась до возврата из функции.

## 4. Гонка: почему `++` ломается

Два потока делают `++counter` без защиты.

```
счётчик = 0

поток A: прочитал 0
поток B: прочитал 0
поток A: записал 1
поток B: записал 1     ← одна из двух продаж исчезла
```

Итог 1 вместо 2. На восьми кассах и ста тысячах продаж часть билетов
стабильно теряется — это задача **02**.

В стандарте C++ одновременная запись и чтение (или две записи)
неатомарной переменные без синхронизации — **data race**. Не «неточный
счётчик». Любое поведение законно, включая падение и «вчера работало».

Два легальных способа убрать гонку на обычном `int`:

- пускать потоки к переменной **по одному** — мьютекс;
- заменить переменную на **атомарную** — `std::atomic` (глава 7).

Пока делишь обычный `int` / `bool` / структуру — бери мьютекс.

## 5. `std::mutex`: очередь к общему ресурсу

Заголовок: `<mutex>`.

Мьютекс — это замок на дверь. `lock()`: если дверь свободна, вошёл и
запер; если занята — стоишь в коридоре. `unlock()`: открыл, следующий
заходит.

Вручную `lock`/`unlock` почти никогда не пишут: исключение или ранний
`return` забудут открыть дверь, и все остальные потоки встанут навсегда
(это уже **deadlock** другого сорта — «забыли отпереть»).

Берут RAII-обёртку:

```cpp
std::mutex mtx;
int counter = 0;

void inc() {
    std::lock_guard<std::mutex> lock(mtx);  // заперли
    ++counter;
}                                           // lock уничтожился — отперли
```

`std::lock_guard` в конструкторе берёт замок, в деструкторе отдаёт.
Область видимости = критическая секция. Чем она короче, тем лучше:
под замком не ходи в сеть и не зови чужой код, который сам может
захотеть тот же мьютекс.

`lock_guard` умеет только это: запер — держи — отпер на выходе.
Разжать дверь *в середине* жизни объекта он не может. Поэтому его
нельзя отдать в `cv.wait`: ждать событие можно, только отпустив замок
(иначе будящий никогда не выставит флаг). Для ожидания нужен
`unique_lock`: тот же RAII, плюс `unlock()` / `lock()` вручную.
`wait` как раз вызывает этот `unlock` за тебя, засыпает, потом снова
`lock`.

`std::unique_lock<std::mutex> lock;` без аргумента — **пустой** замок,
он ни к какому мьютексу не привязан. Нужно `lock(m)`: передать **поле**,
которое стережёт данные. Имя лока не должно совпадать с именем поля,
иначе затенение: думаешь, что берёшь кухню, а создаёшь новый пустой
объект.

### Несколько правил, которые экономят дни отладки

- Один мьютекс стережёт конкретные данные. В комментарии или в имени
должно быть ясно, *что* он охраняет (`cash_register` стережёт
`tickets_sold`).
- Читать охраняемую переменную тоже нужно под замком. «Я только гляну»
— тоже гонка.
- Два мьютекса в разном порядке в разных потоках — классический
deadlock: A взял M1 и ждёт M2, B взял M2 и ждёт M1. В этих пяти
задачах по одному замку, но привычку «всегда в одном порядке»
лучше поставить сразу.
- Нельзя уничтожить мьютекс, пока кто-то в нём сидит.

Для простого `++` хватает `lock_guard`. Для лифта и пула — `unique_lock`,
потому что там есть `cv.wait`.

Итог главы — задача **02**: вокруг увеличения счётчика поставить
`lock_guard` на уже переданный мьютекс. Новый мьютекс создавать не
нужно: если у каждой кассы свой замок, он ничего не защищает.

## 6. Результат из другого потока: `async` и `future`

`std::thread` не возвращает значение функции. Шумный способ — завести
переменную-слот, отдать её в поток **по ссылке**, записать туда ответ,
потом `join()`. «Протащить слот» = эта переменная. «Не забыть барьер» =
не забыть `join()` (или другой барьер) **до** того, как читать слот.
Без `join` ты можешь прочитать слот, пока рабочий поток ещё не записал.

Стандартный канал «там посчитают — здесь заберут»:

```cpp
#include <future>
#include <string>

std::string answer = std::async(std::launch::async, [] {
    return std::string{"42"};
}).get();
```

Разберём по частям.

`std::async` запускает задачу и возвращает `std::future<T>` — билет
на результат. `future.get()`:

- ждёт, пока задача закончится (как `join`);
- отдаёт возвращаемое значение;
- если задача бросила исключение — пробрасывает его сюда.

После `get()` future пустой, второй раз звать нельзя.

### Почему `std::launch::async`

У `async` два режима:


| Политика                | Поведение                                                                            |
| ----------------------- | ------------------------------------------------------------------------------------ |
| `std::launch::async`    | Точно в новом потоке, сразу.                                                         |
| `std::launch::deferred` | Лениво: задача выполнится в том потоке, который первым сделает `get()` или `wait()`. |
| обе (по умолчанию)      | Решает реализация. Часто это «как получится».                                        |


Без `async` политика по умолчанию может выполнить лямбду прямо внутри
`get()` — в вызывающем потоке. Для задачи **03** это провал: тесты
проверяют, что id потоков разные. Пиши `std::launch::async` явно.

### `promise` / `future` с нуля

Для задачи **03** руками их собирать не нужно — хватает `async` + `.get()`.
Ниже — что это за классы, чтобы `async` не был чёрным ящиком.

#### Задача, которую они решают

`std::thread` умеет только «беги вот эту функцию». Вернуть `int` из
`countdown()` в `main` он не умеет: конструктор потока `void`, результата
нет.

Грубый обход:

```cpp
int slot = 0;
std::thread t([&slot] { slot = compute(); });
t.join();
use(slot);
```

Две проблемы: слот надо создать самому, и прочитать его можно слишком
рано, если забыть `join`. `promise`/`future` — стандартный ящик вместо
этого слота: туда кладут ровно один ответ, забрать его раньше, чем
положили, нельзя.

#### Три сущности, не две

В голове держи не «promise и future», а тройку:

```
promise  ----кладёт---->  [скрытое состояние]  <----забирает----  future
         set_value              int / ошибка / «ещё пусто»              get
```

`std::promise<T>` и `std::future<T>` — это **ручки**. Само значение живёт
в скрытом общем состоянии (shared state) между ними. Заголовок у обоих
один: `<future>`. `T` — тип посылки: `promise<int>` кладёт `int`,
`future<int>` его забирает.

Как появляется тройка:

```cpp
std::promise<int> box;                        // создали ручку-вход
                                              // и пустое общее состояние
std::future<int>  ticket = box.get_future();  // прикрутили ручку-выход
                                              // к тому же состоянию
```

`get_future()` зовут **один раз**. Второй вызов — исключение
`std::future_error`: билет уже выдан.

После этого `box` и `ticket` можно разнести по разным потокам. Связь
между ними — то самое скрытое состояние, не сами объекты.

#### Что умеет `std::promise<T>`

Это пишущая сторона. Главные методы:


| Метод              | Смысл                                                                  |
| ------------------ | ---------------------------------------------------------------------- |
| `get_future()`     | отдать читающую ручку. Один раз.                                       |
| `set_value(x)`     | положить `x` в состояние. Один раз. Кто ждал на `get()` — просыпается. |
| `set_exception(p)` | положить не число, а ошибку. `get()` у читателя эту ошибку выбросит.   |


Нельзя: второй `set_value`, `set_value` после `set_exception`, забыть
положить что-либо и уничтожить `promise`. В последнем случае состояние
помечается как «сломанное», и `ticket.get()` бросает
`std::future_errc::broken_promise`.

`promise` не запускает поток. Это только ящик. Поток, если нужен,
создаёшь сам.

#### Что умеет `std::future<T>`

Это читающая сторона.


| Метод             | Смысл                                                                                                                             |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `get()`           | если посылки нет — **уснуть и ждать**. Когда появилась — вернуть значение (или пробросить исключение). После `get` future пустой. |
| `wait()`          | дождаться готовности, значение не забирать. `get()` всё равно потом нужен.                                                        |
| `wait_for(время)` | подождать ограниченно. Вернёт «готово» / «ещё нет». Так тесты лифта проверяют, что поток ещё спит.                                |
| `valid()`         | «ручка ещё прикручена к состоянию?» После `get()` обычно `false`.                                                                 |


`get()` — и ожидание, и доставка. Отдельный `join` ради *результата*
не нужен: пока `set_value` не случился, `get()` не вернётся.

#### Прогон по времени

```cpp
std::promise<int> box;
std::future<int>  ticket = box.get_future();

std::thread worker([&box] {
    int answer = 40 + 2;
    box.set_value(answer);     // состояние: 42, ждущие просыпаются
});

int v = ticket.get();          // если 42 ещё нет — main спит здесь
worker.join();                 // хороним ручку std::thread, не результат
```

Возможные порядки:

1. `set_value` раньше `get` — `get` сразу забирает 42, не спит.
2. `get` раньше `set_value` — `main` спит внутри `get`, рабочий кладёт
  42, `main` просыпается с 42.

Оба законны. Ты не управляешь, кто успеет первым — ящик это переживёт.

Зачем тогда `join`, если `get` уже ждал? Потому что `std::thread worker`
— отдельный объект. Он владеет потоком ОС. Его всё ещё нужно `join`
или `detach`, иначе деструктор вызовет `std::terminate`. К числу 42
это уже не относится: число ты забрал через `future`.

#### Чем это не `std::thread` и не `async`

- `std::thread` — «запусти функцию». Результата нет.
- `std::promise` / `std::future` — «ящик на один ответ». Потока нет,
пока ты сам его не создал.
- `std::async` — «запусти функцию **и** дай мне `future` на её `return`».
Внутри он сам делает promise-подобное состояние. Тебе остаётся `.get()`.

Поэтому в задаче 03 достаточно:

```cpp
return std::async(std::launch::async, question).get();
```

«Достать promise» — не метод и не термин языка. Это просто «завести
ящик самому», потому что `async` тут не подходит.

`async` умеет одно: запустить функцию и забрать её `return`. Если
ответа в `return` нет — значение родится *позже* и *в другом месте*
кода — `async` не к чему прикрутить. Тогда ты создаёшь `promise`,
отдаёшь его туда, где ответ появится, а сам ждёшь на `future`.

#### Когда `async` не подходит

**1. Чужой колбэк.** Библиотека сети сама вызовет твою функцию, когда
пакет приедет. У этой функции тип вроде `void on_packet(int n)` — она
ничего не возвращает *тебе*, она вызывается *у тебя*. `async` тут
некуда поставить: ты не запускаешь расчёт, ты реагируешь.

```cpp
std::promise<int> box;
std::future<int>  ticket = box.get_future();

// библиотека когда-нибудь вызовет это из своего потока
socket.on_packet([&box](int n) {
    box.set_value(n);          // ответ родился здесь, не в return
});

int n = ticket.get();          // наш поток спит, пока пакет не пришёл
```

**2. Кнопка / событие UI.** Пользователь нажмёт «ОК» через секунду или
через минуту. Обработчик клика — снова `void`, не `return 42`.

```cpp
std::promise<bool> box;
auto ticket = box.get_future();

ok_button.on_click([&box] {
    box.set_value(true);       // человек нажал — посылка в ящике
});

bool confirmed = ticket.get(); // код, которому нужно «уже нажали»
```

**3. Ответ в середине длинной функции.** Поток ещё будет работать после
того, как первое нужное число уже известно. `async` отдаст результат
только когда *вся* функция закончится. `set_value` можно позвать в
середине — ждущий поток проснётся раньше.

```cpp
std::promise<int> header_ready;
auto ticket = header_ready.get_future();

std::thread loader([&] {
    int header = read_header();
    header_ready.set_value(header);  // main уже может идти дальше
    read_the_rest_of_the_file();     // это ещё долго
});

int h = ticket.get();   // не ждём весь файл, только заголовок
loader.join();
```

Общее у трёх случаев: место, где значение **появилось**, и место, где
оно **нужно**, — разные функции, часто разные потоки. Ящик их связывает.
`async` связывает только «функция закончилась → вот её return».

Можно ли те же три истории написать через `async`? Третью — да.
Первые две — нет, если библиотека отдаёт только колбэк.

Наивный `async` на весь `loader` в примере 3 заставит `get()` ждать и
заголовок, и хвост файла. Тогда `main` увидит `h` позже. Чтобы не
потерять параллельность, работу режут на две задачи: первая вернула
заголовок, вторая читает хвост, `main` уже орудует `h`. Это уже другая
нарезка, не «сигнал из середины одной функции».

Колбэк и кнопка — не функции, которые *ты запустил ради return*. Их
вызывает чужой код, когда захочет, и тип у них обычно `void`.
`std::async(on_packet)` ничего не ждёт: колбэк либо ещё не вызывали,
либо он ничего не возвращает наружу. Можно обернуть ожидание в функцию
и скормить *её* в `async` — но внутри этой функции всё равно будут
`promise`/`cv`/блокирующий `recv`. `async` тут только транспорт,
ящик никуда не делся.

#### Частые ошибки

- вызвать `get_future()` дважды;
- вызвать `get()` дважды (значение уже забрали);
- уничтожить `promise` без `set_value` — читатель получит
`broken_promise`;
- передать в поток и `promise`, и `future` «на всякий случай» — future
должен остаться у того, кто ждёт;
- думать, что `promise` сам стартует поток.

Итог главы — задача **03**: выполнить функцию в другом потоке и вернуть
её результат. Один `.get()` закрывает и ожидание, и доставку значения.
`promise` руками собирать не обязательно.

## 7. Ждать событие: `condition_variable`

Мьютекс отвечает на вопрос «кто сейчас трогает данные».
Он **не** отвечает на вопрос «уже приехали?».

Плохой способ ждать лифт:

```cpp
while (!arrived) {
    // крутимся и жрём ядро
}
```

Это *busy-wait*. Иногда так делают на микросекундах, в обычном коде —
нет. Поток должен **уснуть** и проснуться, когда событие случилось.

Для этого нужна тройка:

1. **мьютекс** — чтобы флаг не читали и не писали одновременно;
2. **флаг / очередь / счётчик** — само условие («лифт на этаже»);
3. `std::condition_variable` — звонок, который будит спящих.

Заголовок: `<condition_variable>`.

```cpp
std::mutex m;
std::condition_variable cv;
bool arrived = false;

// пассажир
{
    std::unique_lock<std::mutex> lock(m);
    cv.wait(lock, [&] { return arrived; });
    // здесь arrived == true, замок снова у нас
}

// кнопка вызова
{
    std::lock_guard<std::mutex> lock(m);
    arrived = true;
}
cv.notify_all();
```



### Как устроен `wait`

`cv.wait(lock, предикат)` делает примерно следующее:

1. проверяет предикат. Если уже `true` — сразу возвращается.
  Замок остаётся у тебя;
2. если `false` — **атомарно** отпускает мьютекс и засыпает
  (иначе кнопка никогда не смогла бы выставить флаг);
3. когда его будят, снова берёт мьютекс и снова проверяет предикат;
4. если всё ещё `false` — спит дальше (ложное пробуждение);
5. если `true` — выходит из `wait`, мьютекс снова заперт.

Поэтому ждут через `unique_lock`, а не `lock_guard`: `wait` должен
уметь временно отдать замок.

### Зачем `wait` вообще передают мьютекс

`condition_variable` сама данные не стережёт. Она только звонок.
Предикат (`!jobs.empty()`, `arrived`) живёт в переменных под замком.
`wait` обязан:

- проверить предикат **под замком** (иначе lost wakeup: флаг уже true,
  ты ещё не спишь);
- если спать — отдать **тот же** замок атомарно с засыпанием
  (иначе будящий навсегда упрётся в занятую дверь);
- проснувшись — снова взять **тот же** замок, снова проверить.

Поэтому в `wait` передают не «какой-нибудь mutex», а тот `unique_lock`,
который уже держит кухню. Другой мьютекс = другой замок = ты спишь на
одной двери, сосед меняет флаг за другой.

### Почему `notify` можно звать под замком

Спящий в `wait` **уже отпустил** мьютекс. `notify_all` его будит, он
идёт обратно к двери. Если ты ещё стоишь в проёме (лок жив), он просто
подождёт в коридоре, потом зайдёт и перепроверит предикат. Это не
deadlock: ты лок скоро отпустишь (конец `lock_guard`), он его возьмёт.

Чуть медленнее, чем `notify` сразу после `}`: лишний раз кто-то постоит
у двери. На корректность не влияет. В кузнице `notify` после `--busy`
под тем же замком — нормально. Шаблон «сначала отпустить, потом
звонок» тоже законен; главное — **менять** `jobs` / `busy` / `stopped`
только под замком. Звонок замка не меняет, он будит.

Путать с `join` под тем же `m`: `join` может ждать *минуты*, пока
кузнец сам не захочет этот замок. `notify` не ждёт кузнеца — он только
шлёт сигнал.

### Lost wakeup — главная ловушка этой темы

Сценарий:

1. кнопка делает `notify_all()`, ещё никто не спит;
2. уведомление улетает в пустоту — CV **не запоминает** звонки;
3. пассажир вызывает голый `cv.wait(lock)` без предиката и засыпает
  навсегда.

Если бы он сначала посмотрел на `arrived`, он бы понял, что лифт
уже здесь, и не ложился бы.

Предикат в `wait` как раз закрывает дыру: «спи только пока условие
ложно». Флаг обязан жить, звонок — только способ не крутить цикл
активно.

Голый `cv.wait(lock)` без предиката ещё и ловит *spurious wakeup*:
стандарт разрешает разбудить поток просто так. Без повторной проверки
условия ты выйдешь, хотя лифта нет.

### Кто что делает


| Роль    | Действия                                                                                        |
| ------- | ----------------------------------------------------------------------------------------------- |
| Ждущий  | Берёт `unique_lock`, `wait` с предикатом на флаге.                                              |
| Будящий | Под тем же мьютексом меняет флаг, **отпускает** замок, зовёт `notify_one()` или `notify_all()`. |


`notify` можно звать и под замком, и сразу после — см. выше. Менять
флаг / очередь — только под замком.

- `notify_one()` — разбудить одного. Имеет смысл, если работу заберёт
кто-то один (один слот в очереди).
- `notify_all()` — разбудить всех. Нужно, когда условие стало истинным
для нескольких ждущих («лифт приехал, заходят все»).

Флаг и CV без общего мьютекса — снова гонка. Менять `arrived` только
под тем замком, на котором ждут.

Итог главы — задача **04**: две функции, ждать и будить, с предикатом,
чтобы поздний пассажир не потерял уже приехавший лифт.

## 8. `std::atomic`: когда замок слишком толстый

Заголовок: `<atomic>`.

Атомарная переменная — такая, у которой **одна** операция
(прочитать, записать, прибавить) не рвётся посередине. Другой поток
видит либо старое значение, либо новое, никогда «половину».

```cpp
std::atomic<int> counter{0};
counter.fetch_add(1);   // атомарный ++
int v = counter.load();
counter.store(7);
```

Для счётчика продаж `fetch_add` закрыл бы задачу 02 без мьютекса.
Мьютекс там нужен специально: чтобы почувствовать гонку и замок.
Атомик не заменяет мьютекс для *набора* полей: два атомарных `int`
по отдельности не делают атомарной структуру из них двоих.

### Одна операция ≠ две

Безопасно:

```cpp
highscore.store(score);
```

Небезопасно как «обновить, если больше»:

```cpp
if (score > highscore.load()) {   // прочитали 150
    highscore.store(score);       // ...а сосед уже записал 300,
}                                 // и мы затираем 300 числом 200
```

Каждый шаг атомарный. Пара «решил по старому снимку → записал» — уже
нет. Между ними влезает другой поток. Это задача **05**.

### CAS: compare-and-swap

«Запиши новое, **только если** там всё ещё то, что я видел»:

```cpp
int current = highscore.load();
while (score > current &&
       !highscore.compare_exchange_weak(current, score)) {
    // current уже обновлён актуальным значением — крутим снова
}
```

`compare_exchange_weak(current, desired)` атомарно делает:

- если `highscore == current` → записать `desired`, вернуть `true`;
- иначе → записать в `current` то, что реально лежит в `highscore`,
вернуть `false`.

Поэтому цикл естественный: не вышло — у тебя в руках новое «текущее»,
перепроверяешь условие и пробуешь ещё раз. Если пока крутился кто-то
записал ещё больший рекорд, `score > current` станет ложью и ты
корректно выйдешь, не затирая его.

`weak` имеет право вернуть `false` даже когда значение совпало
(ложный отказ, бывает на некоторых CPU). Для цикла это безразлично:
просто ещё одна итерация. `compare_exchange_strong` так не делает,
его берут, когда попытка одна и ложный отказ нельзя пережить.
В цикле обновления рекорда бери `weak` — так и задумано.

Мьютекс в пятой задаче ставить не нужно. Смысл упражнения — собрать
этот цикл, а не спрятать гонку замком.

## 9. Что из этого барьер, а что нет

Коротко, без модели памяти. После этих операций другой поток увидит
записи, которые ты сделал **до** них:


| Операция                               | Кого синхронизирует                                                  |
| -------------------------------------- | -------------------------------------------------------------------- |
| `thread.join()`                        | Всё, что сделал дочерний поток, видно после `join`                   |
| `future.get()` / `promise.set_value()` | Писатель до `set`/`return` → читатель после `get`                    |
| выход из `lock_guard` / `unique_lock`  | То, что сделано под замком, видно следующему, кто этот замок возьмёт |
| `cv.wait` вернулся                     | Вместе с мьютексом: виден флаг, который выставили под тем же замком  |
| атомарный RMW / успешный CAS           | Участники этой атомарной переменной                                  |


`sleep_for` барьером **не** является. «Подождал 50 мс, наверное, тот
поток уже записал» — так тесты не пишут, и ты не пиши.

## 10. `std::move`: отдать вместо скопировать

Заголовок: `<utility>`.

`std::move(x)` **сам ничего не перекладывает**. Это метка: «дальше с `x`
можно обойтись как с временным, содержимое мне больше не нужно».
Компилятор тогда имеет право вызвать *конструктор перемещения* /
присваивание перемещением — «украсть» внутренности вместо копии.

```cpp
std::string a = "длинная строка......";
std::string b = a;              // копия: второй буфер в куче
std::string c = std::move(a);   // буфер ушёл в c, a пустая оболочка
```

После `move` исходный объект ещё жив, но в «опустошённом» виде:
его можно уничтожить или присвоить ему новое значение. Читать `a`
как будто там ещё старая строка — нельзя рассчитывать.

Зачем это на конвейере. `push(T item)` уже получил деталь **по значению** —
она твоя. `q.push(item)` сделает ещё одну копию в очередь. `q.push(std::move(item))`
переложит её на ленту без второго комплекта полей. На `pop`:

```cpp
out = std::move(q.front());  // отдать головную деталь вызывающему
q.pop();                     // снять опустошённую оболочку
```

`pop()` у `std::queue` сам значение не возвращает — только выбрасывает
голову. Сначала забрать (`front` + `move`), потом `pop`.

Где ты это уже встречал, не называя имени:

- `std::thread` **не копируется**. Ручку можно только отдать:
  `workers.push_back(std::move(t))` или сразу `emplace_back(лямбда)`.
  Две ручки на один поток ОС стандарт запрещает — отсюда и abort,
  если временный `std::thread(...)` уничтожился, никуда не переехав.
- `std::function<void()>` в кузнице — та же история: `jobs.push(job)`
  копирует обёртку, `jobs.push(std::move(job))` отдаёт её очереди.

Не всё стоит двигать. `int`, `bool`, маленький `Gadget` из трёх полей —
копия дешевле думать. `move` окупается, когда внутри куча: строка,
вектор, `function`, `unique_ptr`, `thread`. Если у типа нет конструктора
перемещения, `std::move` тихо скатится в копию — метка не магия.

`move` не про потоки и не про барьер. Это про владение ресурсом:
у объекта ровно один хозяин, мы его передаём, а не клонируем.

## 11. Шпаргалка «что взять»


| Хочу                                       | Инструмент                                                         |
| ------------------------------------------ | ------------------------------------------------------------------ |
| Просто выполнить функцию рядом и дождаться | `std::thread` + `join`                                             |
| То же плюс получить `T` / исключение       | `std::async(std::launch::async, ...).get()`                        |
| Несколько потоков портят одну структуру    | `std::mutex` + `lock_guard`                                        |
| Уснуть, пока не случится событие           | флаг + тот же мьютекс + `condition_variable` + `wait` с предикатом |
| Один счётчик / флаг / рекорд без замка     | `std::atomic`, при сложном обновлении — CAS-цикл                   |
| Покрутить паузу в учебном тесте            | `std::this_thread::sleep_for` (это не синхронизация)               |
| Отдать объект без копии (очередь, `thread`)| `std::move`, если внутри куча / объект move-only                   |


В голове держи одну фразу: **нет синхронизации — нет порядка и нет
права на общие данные.**

## 12. Чего в этих пяти задачах нет

Чтобы не расползтись:

- `std::jthread` (C++20) сам делает `join` в деструкторе — удобно,
но задачи на «классическом» `thread`, чтобы жест прочувствовать;
- порядок памяти (`memory_order_relaxed` и компания) — у атомиков
по умолчанию `seq_cst`, этого хватает;
- пулы потоков, очереди задач, `std::latch` / `barrier` — это уже
крупные модули, которые будут после этой пятёрки;
- deadlocks с несколькими замками, lock-free очереди, wait-free.

Если при чтении задачи всплывает слово, которого здесь нет, скорее
всего оно не нужно.

## 13. Как читать задачу

В каждой папке:

- `README.md` — сюжет и критерий успеха;
- `task.hpp` — сигнатура, её не меняй;
- `task.cpp` — единственное место, куда писать код;
- `test.cpp` — можно читать. Это спецификация в виде assert-ов:
какой поток должен отличаться, что не должно зависнуть, какой итог.

Сборка:

```bash
cd multithread
cmake -S . -B build
cmake --build build --target 01_rocket_launch
./build/01_rocket_launch
```

Заготовки компилируются и падают — так и задумано. Когда тест зелёный,
переходи к следующей. По порядку: 01 → 02 → 03 → 04 → 05.

Эталоны лежат в `solutions/`. Имеет смысл открывать их после своей
попытки, даже неудачной: тогда видно, *где* разошлись, а не только
готовый текст.
