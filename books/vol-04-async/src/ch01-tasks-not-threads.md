# Глава 1. Задачи, а не только потоки

## Зачем эта тема

`std::thread` отвечает на вопрос «запусти этот callable **в другом потоке ОС** и дай мне ручку, чтобы дождаться конца». Этого мало, когда тебе нужен **ответ**: число, строка, разобранный JSON, флаг «готово». Можно вручную связать поток с очередью сообщений, mutex и condition variable — но стандарт уже предложил абстракцию **«билет на результат»**: `std::future`.

В голове полезно разделить два уровня. **Поток** — ресурс планировщика: стек, контекст, переключение. **Задача (task)** — единица работы, которую *где-то* выполнят; исполнитель может быть новый поток, поток из пула, отложенный вызов в том же потоке при `get()`, или — в других моделях — coroutine, приостановленная на I/O **(C++20)**. Том 3 учил синхронизировать **общую память**; том 4 учит **передавать результат и ошибку** через типизированный канал без изобретения своего протокола на каждый проект.

Если смешать уровни, появляются типичные боли: «создал thread, но как вернуть `string`?» — и рождается самодельный слот по ссылке; «вызвал async, но всё однопоточно» — реализация выбрала `deferred`. Этот том учит читать **контракт** API, а не только синтаксис.

## Синхронный код и «наложение»

Синхронная функция блокирует вызывающий поток до return. Это просто и предсказуемо для отладки, но если внутри — сеть или диск, ты **платишь простоем**: ядро могло бы крутить другую работу. «Наложить» вычисления можно по-разному: запустить `std::thread` и потом `join`, вызвать `std::async` и позже `future.get()`, отправить job в пул (том 3), или написать coroutine с `co_await` **(C++20)**.

Ни один способ не делает код «бесплатно быстрым». Каждый добавляет накладные расходы и **обязательства по lifetime**: кто владеет данными, пока результат не доставлен, что будет при исключении, кто ждёт кого. Future — договор: «когда-нибудь появится значение типа `T` или исключение; до тех пор `get()` может заблокировать».

Представь поток UI, который синхронно читает конфиг с диска: окно не перерисовывается, пока диск не ответит. Перенос чтения в фон — уже «наложение»; вопрос — **как** вернуть строку в UI без гонки на виджетах. Future доставляет строку; правило «трогай UI только из UI-потока» (глава 9) — отдельный слой.

## Что даёт future без деталей API

Пока ты не открыл `<future>`, достаточно картинки. Есть **общее состояние** (shared state), к которому привязаны ручки писателя и читателя. Писатель кладёт значение или исключение; читатель забирает через `get()`. Операции на ручках синхронизированы — отдельный mutex вокруг «готово / не готово» для одного слота не нужен.

`std::async` — обёртка: «запусти функцию и верни `future` на её `return`». `std::promise` — когда запуск не сводится к одному return: колбэк библиотеки, несколько этапов, ручной поток. Глава 4 разберёт формулировку из **`multithread/THEORY.md`**, §6: «достать promise» = завести ящик самому, когда `async` не к чему прикрутить.

Shared state — не «ещё один глобальный `int`». Это объект внутри реализации STL с протоколом публикации. Поведение: **один** успешный `set_value` / return, **один** `get()` на обычном `future`, happens-before между записью и чтением.

## Поток ОС и задача — на собесе

SMT «6 ядер / 12 потоков» — про **аппаратные** потоки. `std::thread` создаёт **поток ОС**; их может быть сотня. **Задача** — логическая работа; её выполняют на worker’e пула, на новом thread от `async`, или «лениво» при `deferred`. Вопрос «future создаёт поток?» — **сам future** нет; поток создаёт **запуск** — `async`, твой `thread`, worker пула.

## Сценарий «гонец и ответ»

Сюжет oracle: вызывающий поток — дворец; `question` — труд в другом месте; `.get()` — дождаться гонца. Пока гонец не вернулся, `ask_oracle` не делает вид, что ответ есть. API снаружи блокирующий; внутри может идти параллелизм. Можно сохранить `future` и позже `wait_for`, но oracle по контракту ждёт до конца — нормально для учебного упражнения.

## Типичные заблуждения

«Async в C++ = async/await в JS» — в C++17 только future/get; `co_await` **(C++20)**. «Future сам делает программу многопоточной» — без запуска работы future пуст. «Oracle требует promise» — достаточно `async` с `launch::async`; promise — когда return не в одном вызове.

## Развёрнутый разбор: три способа «вернуть int из потока»

Первый способ — **общая переменная и join**, как в начале §6 `THEORY.md`. Ты создаёшь `int slot`, передаёшь в поток ссылку, внутри пишешь результат, снаружи `join` и читаешь. Минусы: слот надо проектировать самому; без `join` чтение — data race или UB; исключение из потока не превращается автоматически в ошибку у читателя — отдельная история с `std::terminate`.

Второй способ — **`std::async` + `future`**. Callable возвращает `int`; стандартная библиотека связывает return с shared state. Снаружи один `.get()` закрывает и ожидание, и доставку. Исключение из callable упаковывается и всплывает в `get()` (глава 6). Для oracle со `string` картина та же: тип `T` меняется, протокол — нет.

Третий способ — **`promise` / `future` вручную**. Ты создаёшь пару ручек, передаёшь promise в поток (move), в потоке `set_value`, снаружи `get()`. Это дублирует то, что `async` делает за тебя, когда есть **один** синхронный return в **одном** запуске. Ручной ящик нужен, когда ответ рождается в **колбэке** или **до** конца функции — см. сценарии в §6 `THEORY.md` и главу 4.

Сравнение на уровне **обязанностей программиста**: thread+slot — ты отвечаешь за барьер и тип канала; async — за политику запуска и lifetime callable; promise — за ровно одну публикацию и за то, кто владеет promise/future.

## Развёрнутый разбор: blocking API снаружи, параллелизм внутри

Многие стандартные функции **блокируют** вызывающий поток: `future.get()`, `thread.join()`, `mutex.lock()`. Это не «анти-async» — это **явная точка синхронизации**. Oracle намеренно блокирует `ask_oracle`, пока не готов ответ: тестам проще, контракт яснее. В UI тот же паттерн часто прячут: фон даёт future, UI-поток периодически `wait_for` и обновляет экран — модель та же, только ожидание дробят.

Важно не путать **блокировку потока** и **блокировку mutex**. `get()` может усыпить поток, не трогая твои mutex’ы. Если внутри worker’а ты держишь mutex A, а main в `get()` потом берёт B, а потом A — классический deadlock уже **твой**, не future.

### Ещё про shared state

Писатель и читатель могут жить в разных потоках; STL синхронизирует публикацию в state. Это не заменяет mutex на ваших vector, если worker и main пишут в один контейнер параллельно с вычислением return.

### join после get в promise-схеме

§6 THEORY: get забрал значение, join всё ещё нужен для std::thread handle. Oracle через async скрывает thread handle внутри runtime — снаружи только get.
