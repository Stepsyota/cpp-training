# Глава 6. Исключения и future

## Зачем эта тема

Исключение, брошенное в callable внутри `std::async` или в `packaged_task`, **не** обязано немедленно рвать стек того потока, который вызвал `async`. Оно упаковывается в shared state и **всплывает в потоке**, который зовёт `future.get()` (или `wait`, после чего `get`). Если этого не понимать, ловишь «тишину» в worker и падение в main, или теряешь исключение, забыв `get()`.

## Путь исключения из async

```cpp
auto fut = std::async(std::launch::async, [] {
    throw std::runtime_error("fail");
});
try {
    fut.get();
} catch (const std::exception& e) {
    // обработка
}
```

`get()` для типа `T` либо возвращает `T`, либо **rethrow** сохранённое исключение. После этого future снова пуст в смысле значения — как после успешного `get`.

Для `future<void>` `get()` только синхронизирует и пробрасывает исключение, если оно было.

## promise::set_exception

В ручном сценарии писатель не бросает в читателя напрямую — кладёт указатель на исключение:

```cpp
try {
    work();
    p.set_value(result);
} catch (...) {
    p.set_exception(std::current_exception());
}
```

`std::current_exception()` и `std::make_exception_ptr` сохраняют исключение для переноса через границу потоков. Читатель по-прежнему узнаёт через `get()`.

## Несколько потоков и один future

Только один поток должен вызывать `get()` на обычном `future` (move-only читатель). Если несколько потоков ждут один результат — `shared_future` и согласованный протокол: все ловят одно и то же исключение при `get()`.

## Исключения в деструкторах и join

Исключение из фонового `async`, до которого никто не дошёл `get()`, может всплыть в **деструкторе `std::future`** при определённых условиях (глава 7) — ещё один повод явно обрабатывать ошибки. Исключение из `std::thread` без перехвата внутри потока — `std::terminate` (том 3). Future **переносит** ошибку; thread **убивает процесс**, если не поймали.

## noexcept и future

Callable с `noexcept` при throw всё равно может завершить программу в потоке выполнения — future не спасает от `std::terminate` в том потоке, где бросили, если это не перехвачено до публикации. На практике в worker’ах пула часто оборачивают `job()` в `try/catch` и логируют — это уже дизайн пула, не спойлер эталона.

## Связь с упражнениями

Oracle обычно не бросает; но любой реальный `compute()` может. Тесты с ожидаемым исключением проверяют, что `get()` бросает то же. В репозитории не подменяй тесты — учись оборачивать `get()` там, где ошибка ожидаема.

## Типичные заблуждения

«Исключение из async теряется» — теряется, если не вызвать `get()` и future уничтожен странно. «catch в main поймает throw в worker без future» — нет, только terminate для thread. «set_exception можно вызвать дважды» — нет.

### exception_ptr

`std::exception_ptr` копируем; хранит тип исключения для rethrow в другом потоке. `set_exception` принимает его; `get` rethrow.

### try/catch в worker vs set_exception

В promise-потоке часто try/catch вокруг work и set_exception в catch — явный контроль. В async — компилятор/runtime упаковывает автоматически.

### Oracle и исключения

Если `question` бросает, `.get()` в ask_oracle должен пробросить — тесты могут проверять. Не глотай исключения в worker без политики.

### future void

Только sync + rethrow; нет return value.

## Краткое резюме

Ошибки из фоновой работы доставляются через shared state в `get()`. `set_exception` для ручного promise. Один читатель на `future`; обработка в том потоке, который ждёт результат. Дальше — ловушки lifetime и политик.
