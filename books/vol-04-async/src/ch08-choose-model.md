# Глава 8. Какую модель выбрать

## Зачем эта тема

В репозитории ты уже видел три «формы» параллелизма: голый `thread` + `join`, `async` + `future`, пул с очередью. Coroutines **(C++20)** добавят четвёртую. Нет одного победителя — есть **несовпадение задачи и инструмента**. Эта глава — decision guide без кода из `solutions/`.

## std::thread

Подходит, когда нужен **долгоживущий** worker с явным циклом: ждать события, крутить очередь, слушать сокет в блокирующем режиме. Ты полностью контролируешь момент `join`, стек, имя потока **(C++20)**. Неудобен, когда на каждую мелочь нужен отдельный поток и когда главному нужен **типизированный результат** без ручного promise.

Сигнал: «один фоновый сервис на процесс» → thread. «Тысяча однотипных вычислений» → не thread на каждую.

## std::async + future

Подходит для **изолированных** вызовов с return: загрузить файл, распарсить, спросить oracle. Мало кода, стандартный канал ошибок. Плохо масштабируется на лавину задач (глава 7), нет стандартной отмены в C++17, нет выбора «выполни на пуле номер 2».

Сигнал: «редко, тяжело, нужен `int`/`string` обратно» → async с явным `launch::async`.

## Пул потоков + очередь

Подходит для **много коротких** job с общим инвариантом очереди, `stopped`, `busy`, ожидания простоя. Результат можно не возвращать через future на каждую задачу — часто достаточно side effect под mutex или batch-результат. Если нужен future на каждую job — `packaged_task` + пул (глава 5).

Сигнал: «постоянный поток работы, лимит потоков = число ядер» → пул (том 3). Связка пул + bounded queue — pipeline (том 3, глава 11).

## promise / колбэк API

Когда источник события **чужой** (GUI toolkit, C библиотека, `epoll` callback), `async` не запускает работу сам — ты получаешь `set_value` в колбэке. Это мост между мирами, не замена пула.

## Coroutines **(C++20)**

Подходят, когда много **последовательных** шагов с ожиданием (I/O, таймеры) и хочется писать линейный код вместо цепочки future + then (которой в STL C++17 нет). Требуют компилятора с поддержкой, типа task/generator, дисциплины lifetime. Не заменяют mutex на shared data.

Сигнал: «десятки `co_await` в одной функции» → смотри главы 11–12. «Только посчитать сумму в 8 потоках» → parallel algorithms или пул, не coroutine.

## Таблица в голове (не широкая в EPUB)

Thread — контроль и долгий цикл. Async — редкий результат. Пул — много мелких job. Promise — чужой колбэк. Coroutine — линейный async I/O **(20+)**. Atomics/mutex — всегда рядом, если есть общее состояние.

## Связь с Parallel STL

`std::execution::par` (том 3, глава 12) — параллелизм **алгоритма** над контейнером, не future на каждый элемент. Комбинируется с тем же процессом: не смешивай неограниченный `par` с неограниченным `async` без плана.

## Типичные заблуждения

«Всё на async» — thread explosion. «Пул всегда быстрее» — overhead очереди для одной задачи. «Coroutines бесплатны» — state machine и аллокации. «Future заменяет mutex» — нет.

**4.** При отладке зависания на `get()` смотри все потоки в gdb (том 6). Если future не спасает от гонки на общих данных — TSan (том 7). Тема главы: Выбор модели concurrency.

**5.** Код в примерах короткий; в проекте дроби длинные цепочки на функции с говорящими именами. Тема главы: Выбор модели concurrency.

**6.** Вопрос «кто владеет объектом до join/get» — тот же, что в томе 2 про capture: init-capture и move часто безопаснее `[&]`. Тема главы: Выбор модели concurrency.

**7.** Политика `std::launch::async` важна там, где тест или контракт требует **другого** `std::thread::id` — как в oracle. Тема главы: Выбор модели concurrency.

**8.** `shared_future` — когда много читателей **одного** значения; очередь — когда каждому нужен свой элемент. Тема главы: Выбор модели concurrency.

**9.** Packaged_task связывает отложенный запуск с future; пул ограничивает число потоков — complementary, не взаимозаменяемые автоматически. Тема главы: Выбор модели concurrency.

**10.** Executor — ответ на «куда submit’ить»; C++17 STL не даёт единого std::execution — пул и Asio закрывают дыру. Тема главы: Выбор модели concurrency.

**11.** Coroutines **(C++20)** — suspend/resume, не «бесплатный поток»; `co_await` зависит от awaitable. Тема главы: Выбор модели concurrency.

**12.** Блокирующий read в worker + future — простой C++17 путь; event loop — масштаб I/O. Тема главы: Выбор модели concurrency.

**13.** К собеседованию: уметь проговорить shared state, broken_promise, деструктор future от async, разницу deferred/async. Тема главы: Выбор модели concurrency.

### oracle vs кузница

Oracle: один ответ, редкий вызов, async. Кузница: поток job, лимит worker, очередь — пул (tom 3). README advanced 06 — submit, не async на каждый заказ.

### parallel_map

Делит диапазон, threads join внутри — не future per element. Tom 3 ch on parallel stl.

### promise GUI/network

Когда источник void callback — promise; oracle не этот case.

### coroutine threshold

Много awaits — coroutine **(20+)**; одна функция return — async.

## Стандарт, ревью, серия (ch08 choose model)

- Стандарт описывает **поведение** API, не конкретный пул потоков libstdc++. На собесе различай «что гарантирует стандарт» и «что делает GCC 14 на Fedora».
- Документация cppreference для `std::async`, `std::future`, `std::promise` — справочник; этот том — narrative поверх §6 `THEORY.md` и oracle.
- При ревью кода ищи: сохранён ли future от async; явная ли политика; не `[&]` на stack; promise set ровно один раз; join thread после ручного worker.
- Упражнение **03_oracle** проверяет контракт потоков; не путай с **02_ticket_office** (mutex) — разные навыки, один трек multithread.
- Если в проекте C++17-only, главы 11–13 помечай как forward-looking; coroutines не обязаны быть в production коде репозитория training.
- Связка **future + UI** часто через message queue или `post` на executor, не прямой touch виджетов из worker — глава 9.
- **Packaged_task** в industrial коде часто спрятан внутри thread pool library; ты можешь пользоваться пулом, не видя тип напрямую.
- **Parallel STL** `par` не возвращает future на элемент; tom 3 — не смешивай ментально с oracle.
- Ошибки concurrency отлаживай слоями: воспроизведи, gdb threads, TSan, потом читай стандарт — tom 6–7.
- Книжный стиль tom 1: абзацы короткие для Kindle, но глава плотная по смыслу — не outline из одной строки на §.
- Идентификаторы в коде английские; prose русский — как в `BOOK-CONTEXT.md`.
- Не используй `vector<int>` в prose вне code block — mdBook HTML; в коде — норм.
- META.md тома 4 фиксирует оглавление; после раздувания обновим строки и EXPANSION-STATUS.
- Репетитор: строка «Том 4 · Глава ch0K» в конце каждой главы для чата.
- Дальше по курсу — ссылка на следующую главу; tom 5 после ch14.
- Broken promise и double get — типичные вопросы на junior/middle собесе по C++.
- Launch deferred на собесе: «выполнится на том, кто ждёт» — ключевая фраза.
- Shared future — «один результат, много читателей»; не путать с broadcast сообщений разного содержания.
- Executor слово в резюме без контекста — уточни: ручной пул, Asio, или P2300.
- Coroutine interview: suspend не equals async I/O unless awaitable says so.
