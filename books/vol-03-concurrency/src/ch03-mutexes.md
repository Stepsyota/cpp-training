# Глава 3. Мьютексы и RAII-замки

## Зачем

Data race лечится **упорядочиванием**: в каждый момент только один поток выполняет критическую секцию над shared данными, или доступ идёт через atomics с явной моделью. В C++ базовый кирпич — **`std::mutex`** (mutual exclusion — взаимное исключение): перед чтением/записью общего состояния поток **захватывает** mutex, другие **ждут**, пока первый **освободит**.

Вручную **`lock`/`unlock`** легко забыть на пути с **`return`** или **`throw`**. RAII-обёртки — **`std::lock_guard`**, **`std::unique_lock`**, с C++17 **`std::scoped_lock`** — привязывают lifetime замка к scope: деструктор всегда отпускает mutex. Эта глава — как пользоваться замком, чем guard отличается от unique_lock, как не устроить **deadlock (взаимную блокировку)**, и почему **`join` worker'а под тем же mutex**, на котором worker ждёт работу, — классический self-deadlock (идея для пулов, глава 10, без разбора эталонного кода).

## `std::mutex` в протоколе

**`std::mutex`** не «запрещает два потока на двух ядрах» — он **блокирует** второй **`lock()`**, пока первый не сделает **`unlock()`**. Один mutex защищает **инвариант** структуры: «очередь согласована», «счётчик совпадает с суммой элементов». Держи mutex **коротко**: не вызывай под ним медленный I/O и не **`join`** других потоков без крайней нужды.

```cpp
#include <mutex>

std::mutex m;
int tickets = 0;

void sell() {
    std::lock_guard<std::mutex> lock(m);
    ++tickets;
}
```

**`lock_guard`** — минимальный RAII: конструктор **`lock()`**, деструктор **`unlock()`**. Нельзя отложить lock, нельзя передать ownership — и это плюс для простых секций.

**`std::mutex`** не recursive по умолчанию: повторный **`lock()`** тем же потоком — **deadlock** (не «вернётся сразу»). Если один метод класса вызывает другой, оба берут **`m_`**, нужен **`recursive_mutex`** или внутренний **`private`** метод без повторного lock — архитектурно второе здоровее.

Размер критической секции: под mutex только то, что защищает инвариант. Тяжёлая работа **вне** lock снижает contention — другие потоки меньше стоят в очереди на **`lock()`**.

## `unique_lock` — гибкость для condition variable

**`std::unique_lock<std::mutex>`** умеет **`defer_lock`**, **`try_lock`**, **`unlock`** до конца scope, **`release`**. Нужен почти всегда с **`std::condition_variable`** (глава 4): **`wait`** атомарно отпускает mutex и засыпает.

Типичная ошибка из практики курса: объявить **`std::unique_lock<std::mutex> lk;`** без аргумента — это **отдельный** объект mutex внутри шаблона (затенение имени), а не твой член класса. Нужно **`std::unique_lock lock(m_);`** где **`m_`** — поле пула или очереди.

```cpp
std::mutex m_;
std::unique_lock<std::mutex> lk(m_);
// cv.wait(lk, pred);  — глава 4
```

## `scoped_lock` (C++17) — несколько mutex сразу

Когда нужны **два замка** (передача из account A в B), порядок **`lock(m1); lock(m2);`** опасен: поток 1 держит m1 ждёт m2, поток 2 держит m2 ждёт m1 — deadlock.

**`std::scoped_lock lock(m1, m2);`** — один вызов, стандарт использует deadlock-free algorithm (как **`std::lock(m1,m2)`** + guards). На Fedora с **`-std=c++17`** это предпочтительнее ad-hoc порядка «всегда сначала меньший адрес mutex».

```cpp
std::mutex ma, mb;
void transfer() {
    std::scoped_lock lock(ma, mb);
    // критическая секция на обоих
}
```

## Deadlock без второго mutex

Deadlock — цикл ожидания: A ждёт B, B ждёт A. Варианты: два mutex; **mutex + join** (ниже); поток ждёт себя. **Recursive mutex** (`std::recursive_mutex`) позволяет повторный **`lock`** тем же потоком — костыль; лучше перестроить API, чем бесконечно вложенные lock.

Избегай: держать mutex A и вызывать callback, который снова берёт A. Документируй порядок захвата в команде: «сначала `queue_m`, потом `stats_m`».

## Never join under the worker's wait mutex

Сценарий фонового worker'а: под **`m_`** он в **`wait`**, пока есть работа или не выставлен **`stopped`**. Главный поток в **деструкторе** хочет: выставить **`stopped`**, разбудить всех, **дождаться** завершения потоков.

Если **деструктор** делает **`join()`** **под тем же `m_`**, пока worker **заблокирован в `wait` на `m_`**, получается deadlock: worker не выйдет из wait, пока mutex не освободят; освободить mutex некому, потому что деструктор держит его и ждёт worker.

Правильная схема (словами): под mutex выставить флаг остановки и **`notify_all`**; **отпустить mutex**; затем **`join`** каждого **`std::thread`** **без** удержания **`m_`**. Worker после пробуждения снова возьмёт mutex, увидит «пусто и stopped», выйдет из цикла, завершится — **`join`** пройдёт.

Это не «деталь реализации пула», а общее правило: **операции, которые ждут завершения другого потока, не держат mutex, на котором тот поток может спать или работать бесконечно**.

С **`std::condition_variable::wait`** worker уже отпустил mutex внутри wait — но если он **не** в wait, а в **`lock()`** в начале цикла, деструктор с **`join`** под тем же mutex всё равно блокирует навсегда. Отличай «спит в cv» от «ждёт lock».

## `try_lock` и backoff

**`mutex.try_lock()`** возвращает сразу: занято — false. Паттерн «попробовал, отступил, сделал другое» — для **lock-free try** очередей; для учебных задач чаще блокирующий lock. **`std::defer_lock`** с **`unique_lock`**: создать lock без захвата, потом **`std::lock(lk1, lk2)`** + **`std::adopt_lock`** — низкоуровневый sibling **`scoped_lock`**.

## Исключения и `lock_guard`

Если тело под **`lock_guard`** бросает исключение, деструктор guard всё равно **`unlock()`** — mutex не остаётся захваченным навсегда. **`std::terminate`** из-за **`~thread`** — другая история (глава 1); mutex при unwind освобождается.

**`std::lock_guard`** не поддерживает **`unlock`** в середине — для «сделать работу без mutex» используй **`unique_lock`** и явный **`unlock()`** перед долгой работой (как в worker: взять задачу из очереди, **отпустить** mutex, выполнить **`job()`**).

## Mutex vs atomic

**`mutex`** защищает **произвольный инвариант** нескольких полей и структур STL. **`std::atomic<int>`** (глава 5) — для узких операций на одном слове; «заменить mutex на atomic» для **`std::vector`** нельзя. Не держи mutex, пока ждёшь **другой** mutex вне fixed order — см. **`scoped_lock`**.

## Reader-writer (обзор)

**`std::shared_mutex` (C++17)** — many readers или one writer. Полезно для read-heavy кэша; writer всё равно exclusive. Для учебных очередей и пулов достаточно обычного **`mutex`**: инвариант «очередь» не разделить на «только читатели» без тонких ошибок.

**`std::shared_lock`** парится с **`shared_mutex`** для read-side; **`unique_lock`** / **`lock_guard`** — для write. Порядок захвата shared + обычных mutex — снова риск deadlock, документируй.

## Задача кассы и видимость после unlock

`02_ticket_office` — минимальный mutex: все пути к `tickets` проходят через один `std::mutex`. После `unlock` следующий `lock` **видит** обновлённое значение не потому, что «int на шине атомарный», а потому что пара unlock/lock создаёт **synchronizes-with** (глава 7). Пока mutex один и инвариант «только под замком» — модель простая.

Если добавить второе поле `revenue` и защищать только `tickets`, второе поле остаётся в зоне гонки — mutex **не** «расползается» на соседние члены автоматически.

## `lock_guard` vs ручной lock в legacy-коде

В старом C++03 коде часто встречается `m.lock(); ... m.unlock();` на каждой ветке — легко пропустить ветку с `return`. `lock_guard` и `scoped_lock` **(C++17)** существуют, чтобы исключение или ранний выход не оставляли mutex захваченным. `unique_lock` нужен, когда mutex **временно** отпускают (worker выполняет job вне очереди — глава 10).

Не вызывай **пользовательский** callback под mutex, если callback может снова запросить тот же mutex — это re-entrancy deadlock, даже без `recursive_mutex`.

## Практика: пустой `unique_lock` (затенение)

В `THEORY.md` и `AGENTS.md` репозитория зафиксирована ошибка: `std::unique_lock<std::mutex> m;` создаёт **внутренний** mutex шаблона, а не блокирует поле класса. Правильно: `std::unique_lock<std::mutex> lk(m_);` где `m_` — член пула или очереди. Если clangd показывает «mutex never locked» — проверь, не затенил ли имя.

Это не pedantry: без lock очередь jobs — data race и UB, тесты могут быть зелёными «случайно».

## Сборка

`<mutex>` не требует отдельного флага кроме **`-pthread`** на Linux для `<thread>`; mutex работает и в однопоточной программе, но смысл — с потоками.

## Типичные ошибки

Забыть **`lock_guard`** на одной из веток **`if/else`**. Долгий **`join`** или **`wait`** на client под mutex worker'а. **`unique_lock` без привязки к полю** — пустой mutex. Два mutex в разном порядке в разных функциях. Думать, что **`const` метод** «только читает» — и вызывать его без mutex, пока другой поток пишет (**`mutable`** кэш — write). Вызывать **`unlock`** без matching **`lock`** (с **`unique_lock`** следи за состоянием).


## Глубже: contention и размер критической секции

**Contention** — когда потоки часто блокируются на одном mutex. Лечение: короче секция, другая гранулярность данных (shard counters), reader-writer для read-heavy **(C++17 shared_mutex)** — только если профиль показал mutex как bottleneck. Преждевременное дробление mutex без инварианта «кто владеет полем» создаёт **логические** гонки между двумя замками.

`try_lock` + backoff — для expert paths; в учебных задачах блокирующий lock проще и **достаточен**.

## Priority inversion (упоминание)

Низкоприоритетный поток держит mutex, высокий ждёт — классическая OS-тема. `std::mutex` не поднимает priority наследника автоматически; для realtime — platform APIs. Для учебного кода достаточно знать, что «долго под mutex» вредит не только другим потокам того же процесса, но и latency.


## Мост к condition_variable

Mutex без cv заставляет либо spin, либо sleep «вслепую». Cv добавляет **ожидание условия** под тем же mutex — глава 4. Пул и очередь — **оба**; не путай «mutex на очередь» с «mutex на весь процесс навсегда».

## Зеркало `AGENTS.md`: join и mutex

В правилах репетитора для `06_thread_pool` подчёркнуто: деструктор join'ит **без** mutex, на котором worker ждёт. Это не частный случай «кузницы», а переносимое правило для любого cv-worker. Если в review видишь `join` внутри `lock_guard` на `m_` пула — стоп.

## Краткое резюме

**`std::mutex`** сериализует доступ к shared данным. **`lock_guard`** — простой RAII; **`unique_lock`** — для **`wait`**, отложенного lock, ручного unlock. **`scoped_lock` (C++17)** — безопасно несколько mutex. Deadlock — цикл ожидания; типичен **join под mutex**, на котором worker спит. Долгую работу и **`join`** делай **без** удержания worker mutex. Следующая глава — **`condition_variable`** поверх **`unique_lock`**.
