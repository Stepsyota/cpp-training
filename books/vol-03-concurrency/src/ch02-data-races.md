# Глава 2. Гонки данных и неопределённое поведение

## Зачем

Два потока в одном процессе могут одновременно читать и писать одну переменную `int counter`. На бумаге «каждый делает ++» должно дать +2. В реальности часто получаешь +1 или странные промежуточные значения. Это не «баг компилятора Fedora» и не «нужно просто `-O2` убрать»: при отсутствии синхронизации стандарт C++ описывает ситуацию как **data race (гонка данных)** и относит программу к **undefined behavior (UB, неопределённое поведение)**.

UB значит: компилятор и железо могут делать **что угодно**, включая «работает на моей машине». Отладка без модели гонок превращается в охоту за призраками. Эта глава даёт **интуицию до формального happens-before** (главы 6–7): что считается одновременным доступом, чем гонка отличается от логической ошибки «мы забыли mutex», и почему «volatile» и «раз в миллисекунду» не лечат.

## Одновременность без календаря

«Одновременно» в стандарте — не «в одну наносекунду на часах». Достаточно, что два **conflicting access (конфликтующих обращения)** к одной области памяти **перекрываются по времени выполнения** и **хотя бы одно — write**. Поток A делает load, поток B в тот же момент store — гонка. Два read без write — не data race (но может быть stale read без синхронизации в более сложных сценариях).

Операция **`counter++`** для не-atomic `int` — это **не одна** машинная инструкция: обычно load → add → store. Между ними другой поток может вклиниться. Ты логически «увеличил один раз», машина сделала три шага — классический **lost update**.

```cpp
// Демонстрация идеи — так в проде нельзя (UB при гонке)
int counter = 0;

void bump() {
    for (int i = 0; i < 100000; ++i)
        ++counter;
}

int main() {
    std::thread a(bump), b(bump);
    a.join(); b.join();
    // counter может быть << 200000
}
```

Даже если на `-O0` в GDB «часто 200000», это **не гарантия** — UB не обязан воспроизводиться.

На x86-64 отдельные load/store часто выглядят «атомарно» на уровне шины, но **RMW** всё равно может развалиться без **`std::atomic`**. На ARM и других архитектурах расхождение заметнее. C++ описывает **машинно-независимую** модель: опираться на «у меня Intel/AMD, значит можно `int`» — ошибка переносимости и формально UB.

## Data race = UB

Стандарт запрещает data race на объектах, для которых нет подходящей **memory synchronization**. Последствия: оптимизатор может удалить «лишние» записи, переупорядочить видимость, держать значение в регистре. **TSan (Thread Sanitizer)** в томе 7 ловит многие гонки на Clang/GCC; без санитайзера зелёный тест не доказывает отсутствие UB.

Важно отделить **data race** от **race condition (состояние гонки)** в широком смысле. Логическая ошибка: «оба потока проверили `if (!file_open)` и оба открыли файл» — может быть исправлена mutex **без** того, чтобы формально был data race на `int` (если проверка и открытие атомарны как протокол). И наоборот: один «неправильный» write без mutex — уже UB, даже если «результат кажется стабильным».

## Наблюдаемые симптомы

Симптомы разнообразны: недосчёт, рваные значения **`uint64_t`** на 32-bit (теоретически), краши внутри STL при concurrent **`vector::push_back`**, редкие assert в debug. **Heisenbug** — баг исчезает под GDB, потому что замедление меняет interleaving. Не путай с **deadlock** (глава 3): там потоки живы, но ждут друг друга; при гонке результат **недeterminирован**.

## Что не является «лекарством»

**`volatile`** не создаёт atomic read-modify-write и не вводит happens-before между потоками (подробнее том 1, глава 4). **`const`** на shared объекте не делает concurrent read безопасным, если другой поток пишет в те же байты через не-const путь или через **`mutable`**.

Поставить **`sleep`** «чтобы успели» — не синхронизация; планировщик не гарантирует порядок. **«У меня один writer»** без барьеров памяти читатель может не увидеть запись без правил (atomics/mutex — позже).

## Первые правила без эталонного кода упражнений

Если несколько потоков трогают **одну mutable переменную** или **одну структуру без инварианта «только один пишет»** — нужен механизм: **`std::mutex`**, **`std::atomic`**, или **разделение данных** (каждый поток пишет в свой кусок, потом join). «Прочитал-modify-записал» три поля подряд без замка — три окна для гонки.

Иммутабельность после публикации помогает: построил данные в одном потоке, **`join`**, потом только read — гонки нет. Shared mutable — место, где C++ требует дисциплины.

## TOCTOU и «проверил без замка»

**Time-of-check to time-of-use**: поток A видит «очередь не пуста» без mutex, поток B между check и use забирает последний элемент — A работает с невалидным состоянием. Формально это и логический баг, и часто **data race** на полях очереди, если оба лезут без синхронизации. Правило: **инвариант проверяй и меняй под одним mutex** (или под одной atomic-структурой с правильным протоколом).

То же с «ленивой» инициализацией static в C++11: **`static std::mutex m;`** внутри функции потокобезопен при первом вызове — compiler guard. Самодельный **`if (!ptr) ptr = new T`** из нескольких потоков без mutex — гонка на указателе.

## Оптимизатор и «лишние» записи

При UB компилятор может решить, что counter в гонке «никто не читает смыслово» и удалить increments в dead analysis — редко, но legal. При **`-O2`** reordering усиливается; **TSan** обычно собирают с **`-O1`** и sanitizer flags. Не доказывай корректность сравнением asm в одной версии GCC.

## Интуиция «до» happens-before

Позже формально: операция A **happens-before** B, если B видит эффекты A. Data race — когда ни A before B, ни B before A для conflicting access. Пока достаточно картинки **упорядочивания**: mutex unlock в одном потоке **синхронизирует-with** lock в другом; atomic release/acquire — то же на другом языке. Без таких «мостов» компилятор и CPU **coalesce** и **reorder** доступы так, как для однопоточного кода «выгодно».

```cpp
// Плохо: флаг без синхронизации
bool ready = false;
int data = 0;

void producer() {
    data = 42;
    ready = true;   // write может быть виден раньше data
}

void consumer() {
    while (!ready) {}
    use(data);      // может прочитать мусор
}
```

Даже «логически» порядок в исходнике верный — без HB между потоками это снова UB (гонка на `ready` и на `data`). Исправления — mutex или atomic с ordering (главы 3, 5–6).

## Отладка на Fedora

Собери с **`-fsanitize=thread`** (Clang чаще; GCC тоже поддерживает на новых версиях): `./a.out` упадёт с отчётом двух стеков. Без TSan воспроизведи на **`-O0`**, уменьши число итераций, добавь счётчик — но помни: отсутствие симптома ≠ отсутствие UB.

## Структуры и STL под concurrent доступом

**`struct Stats { int a, b; }`** — два поля, два потока меняют разные поля без lock: формально **нет** гонки на одном объекте, если байты не пересекаются… только если padding и alignment не создают общую cache line с соседями (глава 9). Один поток **`push_back`**, другой **`operator[]`** на **`vector`** — гонка и UB, даже «мы только читаем индекс 0».

Shared **`std::string`** — один поток **`+=`**, другой **read** — гонка: внутренний указатель и size меняются. «Я знаю, writer закончил» без синхронизации — не аргумент для стандарта.

## Связь с `THEORY.md` и задачей кассы

В `multithread/THEORY.md` гонка на `++` разбирается рядом с mutex: два потока, один счётчик, недосчёт — это **не** «сломанный Ryzen», а отсутствие mutual exclusion. Упражнение `02_ticket_office` просит **только** обернуть инкремент в `lock_guard`; книга объясняет, **почему** без замка стандарт уже не обещает сумму инкрементов.

Не путай **логическую** ошибку «продали больше билетов, чем мест» (бизнес-инвариант) с **формальной** data race: иногда инвариант ломается даже под mutex, если проверка и действие не атомарны как протокол (TOCTOU). Иногда mutex есть, но защищает **не то** поле — гонка остаётся на соседнем `int`.

## Happens-before «на пальцах» до главы 7

Пока достаточно образа **моста**: без mutex, без atomic release/acquire и без `join`/`future::get` между потоками **нет** гарантии, что запись в `main` «дошла» до read в worker. Компилятор может держать значение в регистре, переупорядочить store, слить два increment в один. Это не «баг `-O2`» — это следствие UB.

Когда в главе 7 появится **synchronizes-with**, вернись мысленно к паре `ready`/`data` из этой главы: два plain `bool`/`int` без синхронизации — классический учебный пример **отсутствия** моста.

## Sanitizer как продолжение этой главы

`-fsanitize=thread` (подробно в главе 14 и томе 7) часто **первый** объективный аргумент против «у меня же счётчик сходится». Собери тот же `bump()` из демонстрации с TSan на Fedora — отчёт покажет два стека и адрес `counter`. Помни: **отсутствие** отчёта на одном прогоне не доказывает корректность при UB; гонки **вероятностны**.

Для CI и `check.sh` санитайзер обычно включают отдельной конфигурацией, не вместо release-сборки.

## Связь с практикой курса

Упражнения на **`++` под mutex** и на **atomic CAS** — не магия, а устранение конкретных классов гонок. Пул потоков и очередь (главы 10–11) добавляют **инварианты очереди**: кто может трогать `head`/`tail`, когда `closed`. Книга не подменяет твой код решениями; она объясняет, **почему** тест «200000» иногда зелёный, а программа всё равно неправильна по стандарту.

## Типичные ошибки

Считать «раз на практике сходится — гонки нет». Использовать **`volatile`** для флага готовности между потоками. Думать, что **`std::cout`** thread-safe для произвольной смеси операторов без внешнего mutex (отдельные символы могут не перемешаться, но строки из нескольких << — уже хаос). Проверять **`if (queue.empty())`** без замка и потом **`pop`** — TOCTOU гонка. Путать **UB от data race** с **exception safety** — разные оси.


## Глубже: const, указатели и «только читаю»

Concurrent read plain `int` без write формально не data race, но **read** структуры, которую другой **пишет** без sync, — race на объекте целиком, если поля не независимы по стандарту. `const` метод класса не спасает, если другой поток вызывает non-const или пишет в **`mutable`** кэш без lock.

Публикация «готового» объекта: безопасный паттерн — построить в одном потоке, **join**, потом читать из других **без** mutation. Immutable snapshot после fork/join — простейший «мост» без atomics.

## Статистика и «редкие» гонки

Stress: увеличь итерации, число потоков, запусти в цикле 100 раз в shell — не доказательство, но лучше одного прогона. Гонка на счётчике может проявиться 1 из 10⁶ — CI без TSan всё равно пропустит. Поэтому data race — вопрос **модели**, не частоты симптома.


## Мост к mutex и atomic

Любое исправление гонки — построение **happens-before** (глава 7) или mutual exclusion. Mutex — «тяжёлый мост» для произвольных структур; atomic — «узкий мост» для одного слова с optional ordering. Выбор не по «что моднее», а по **инварианту**: один счётчик vs очередь vs пара полей.

## Краткое резюме

Гонка данных — overlapping conflicting access, хотя бы один write, без синхронизации → **UB**. **`++`** на обычном `int` — не атомарно. Симптомы нестабильны; TSan помогает. **`volatile`/`sleep`/«у меня один core»** — не модель памяти. Лечение: mutex, atomics, ownership, immutability после join. Формальный **happens-before** — в следующих главах; сначала — дисциплина shared mutable.
