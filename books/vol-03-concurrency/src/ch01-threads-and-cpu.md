# Глава 1. Потоки ОС, ядра и `std::thread`

## Зачем

Одна программа на Fedora может занимать один **process (процесс)** — отдельное адресное пространство, файловые дескрипторы, PID в `ps`. Внутри процесса планировщик ядра Linux крутит несколько **threads (потоков ОС)**: у каждого свой стек и регистры, но куча и глобальные переменные **общие**. C++11 дал **`std::thread`** — тонкую обёртку над потоком ОС: ты создаёшь объект, передаёшь callable, и работа идёт параллельно с `main`, пока не сделаешь **`join`** или **`detach`**.

Без картины «сколько реально железа» легко решить, что «создал двенадцать `std::thread` — значит, всё сразу на двенадцати ядрах». На Ryzen 5 5500 часто **6 физических ядер** и **12 логических** из‑за **SMT (Simultaneous Multithreading)** — Hyper-Threading у Intel тот же класс идеи: одно ядро может держать два потока с раздельным контекстом, но делит исполнительные ресурсы. Двенадцать потоков ОС **конкурируют** за шесть ядер; планировщик **переключает** их (preemption), когда поток блокируется на I/O, sleep или просто исчерпал квант времени. Эта глава — фундамент: что такое поток, чем он не равен «ядру», и почему за **`std::thread`** обязан стоять явный **`join`** или **`detach`**.

## Процесс и общая память

Все потоки одного процесса видят одни и те же адреса: указатель, полученный в `main`, валиден в воркере. Это удобно для данных, но опасно без правил синхронизации — об этом глава 2. Стек **не** общий: локальная переменная в `main` живёт только пока выполняется `main` на своём стеке; передать её адрес в другой поток без гарантии lifetime — классическая ошибка (к ней вернёмся с захватом в лямбдах, том 2).

Глобальные и статические объекты инициализируются до входа в `main` (с нюансами порядка между translation units); **`thread_local`** даёт отдельный экземпляр на поток — полезно для кэша без mutex, но не для «быстрого shared счётчика».

## Ядра, SMT и планировщик

**CPU core (ядро)** — независимый исполнитель инструкций с кэшем и конвейером. **Logical CPU** в `/proc/cpuinfo` или `lscpu` на 5500 часто показывает 12: это 6 ядер × 2 потока SMT. Два потока на одном ядре **не** удваивают FP/ALU; они прячут задержки, когда один ждёт память, второй может крутиться.

Планировщик ядра **не** обязан закрепить твой `std::thread` за конкретным ядром. Поток A крутился, получил page fault или `mutex` — ядро сняло A, поставило B. «Отдать ядро» в разговорной речи — не «я создал ровно 12 потоков», а «планировщик перестал давать мне CPU в этот момент». Искусственный **`std::this_thread::yield()`** лишь намекает; гарантий нет.

Для CPU-bound задачи разумно ориентироваться на число **физических** ядер или чуть больше, если есть простои; для I/O-bound — потоков может быть больше ядер, потому что многие спят в ожидании диска или сети.

Утилита **`taskset`** или affinity в коде (`pthread_setaffinity_np`) — продвинутый уровень; для учебных программ достаточно понимать, что OS сама раскладывает потоки по ядрам. Если все потоки CPU-bound и их больше, чем логических CPU, ты платишь за **context switch** — переключение стека и сброс кэша, а не за «бесплатные» ядра.

## Несколько потоков и `hardware_concurrency`

Частый шаблон: создать **`std::vector<std::thread>`**, запустить **`n`** воркеров, в конце **`join`** каждого. Число **`n`** не обязано равняться 12: для эксперимента возьми 2, 4, 8 и сравни wall time на одной задаче — увидишь насыщение после нескольких ядер.

```cpp
std::vector<std::thread> pool;
for (int i = 0; i < n; ++i)
    pool.emplace_back(worker, i);
for (auto& t : pool)
    t.join();
```

**`std::thread::id`** и **`std::this_thread::get_id()`** помогают в логах отличить, кто печатает; это не «номер ядра», а идентификатор потока в runtime. **`std::this_thread::sleep_for`** блокирует **текущий** поток, не весь процесс — другие `std::thread` продолжают крутиться.

## `std::thread` как ручка

Объект **`std::thread`** — это **handle (ручка)** на поток ОС, не «сам поток как объект в памяти C++». Создание:

```cpp
#include <thread>
#include <iostream>

void worker(int id) {
    std::cout << "id=" << id << '\n';
}

int main() {
    std::thread t(worker, 1);
    t.join();
}
```

Callable может быть free function, функтор или лямбда. Аргументы после callable копируются или перемещаются в новый поток (как при вызове function wrapper). На Fedora собери с **`-pthread`** (GCC/Clang): и линковка, и макросы POSIX для стандартной библиотеки.

Пока `t` **joinable** — поток ещё ассоциирован с ручкой. **`join()`** блокирует вызывающий поток, пока `worker` не завершится; ресурсы ОС освобождаются. **`detach()`** отвязывает ручку: поток живёт сам по себе, `std::thread` больше не управляет им. Detach уместен для «fire-and-forget» с осторожностью: процесс не должен завершиться, пока detached поток ещё пишет в `std::cout` или в общие данные без синхронизации.

## Деструктор и `std::terminate`

Если **`~std::thread()`** вызывается для **joinable** потока (не было ни `join`, ни `detach`), стандарт вызывает **`std::terminate()`** — немедленное аварийное завершение программы. **`catch` исключений это не перехватывает**: terminate идёт вне обычного unwind. Частая ошибка новичка: локальный `std::thread` в блоке `{ ... }` выходит из scope без `join` — abort.

Terminate здесь — не «убили поток ОС», а «нарушили контракт владения ручкой». Поток мог ещё крутиться; стандарт не оставляет программу в подвешенном состоянии. Правило на каждый `std::thread`: в конце жизни ручки либо **`join`**, либо **`detach`**, либо **`std::move`** в другой объект, который потом сделает одно из двух.

```cpp
std::thread t([] { /* work */ });
// ~t() здесь → std::terminate(), если не join/detach/move
```

Перемещение **`std::thread`** передаёт ownership: старый объект становится not joinable, новый обязан завершить протокол.

Конструктор **`std::thread`** принимает аргументы callable **by value** по умолчанию. Если нужна **ссылка** на существующий объект, оберни **`std::ref(x)`** — иначе получишь копию или не скомпилируешь. Ссылка на локальную из `main` в detached потоке — use-after-return; копия **`std::string`** или move в lambda безопаснее для фона.

Завершение **`main`** при joinable/detached потоках: стандарт требует **`std::exit`** или return из main только когда поведение определено. Практически **`join` всех** worker'ов перед return — норма; с detached — убедись, что они не трогают stack/объекты, которые уже уничтожены.

## `join` vs `detach` в сценариях

**Join** — когда результат или порядок завершения важен: дождались воркеров, потом читаем общий буфер (уже под mutex или после join без гонок на «жив/мертв»). **Detach** — фоновый логгер, если lifetime процесса длиннее и нет обращения к уничтожаемым объектам.

Нельзя **`join`** дважды и нельзя **`join`** после **`detach`**. После успешного `join` поток not joinable. Если воркер бросил необработанное исключение, **`join`** в `main` **rethrow** — исключение «переплывает» в joiner; в production часто ловят внутри воркера и сигналят через канал ошибок.

## Отличие от «просто async»

**`std::async`** (том 4) — другой уровень абстракции: future, политика запуска, не обязательно новый поток на каждый вызов. **`std::thread`** всегда означает «запусти поток (если ОС смогла)». Для учебного трека многопоточности thread — базовый кирпич; пулы и очереди (главы 10–11) строятся из многих joinable workers.

## Сборка и первый запуск на Fedora

```bash
g++ -std=c++17 -pthread -Wall -O0 -g thread_demo.cpp -o thread_demo
./thread_demo
```

**`-O0 -g`** помогут в GDB (том 6): видно, в каком потоке стоишь. **`std::thread::hardware_concurrency()`** возвращает hint «сколько потоков может иметь смысл»; на 5500 часто 12 — это логические CPU, не «12 независимых ядер».

## Потоки и исключения

Исключение, вылетевшее из callable **`std::thread`**, не попадает в `main` автоматически: стек unwinding идёт в **воркере**, и если там нет **`catch`**, вызывается **`std::terminate`**. **`join()`** в вызывающем потоке **перебрасывает** сохранённое исключение — удобно для тестов, в сервисах чаще ловят внутри worker и пишут в канал ошибок.

Не смешивай **`terminate` от ~thread** с **`terminate` от исключения в worker** — разные пути, оба аварийные. Надёжный worker оборачивает границу **`try { job(); } catch (...) { log; }`**, не полагаясь на «кто-нибудь join поймает».

## Связь с томом 2

Лямбда **`[capture] { ... }`** — типичный способ передать тело в `std::thread`. Захват **`[&]`** на локальные из `main` опасен, если поток переживёт stack frame. **`[x]`** копирует, **`[this]`** в методе класса — указатель на объект; lifetime объекта должен покрывать lifetime потока.

## Практика курса: ракета и первый join

Упражнение `01_rocket_launch` в `multithread/beginner/` — не про оптимизацию, а про **контракт ручки**: создать `std::thread`, передать callable, **дождаться** завершения через `join`. В `THEORY.md` (начало конспекта) та же линия: поток ОС живёт отдельно от `main`, пока ты явно не синхронизируешься. Если после этой главы ты всё ещё путаешь «12 потоков в `htop`» с «я создал 12 `std::thread` и все сразу на ядрах» — вернись к разделу про SMT: логические CPU — это **слоты** планировщика, не двенадцать независимых вычислителей.

Полезный мысленный эксперимент: запусти два CPU-bound потока на машине 6C/12T и посмотри `top` — оба могут показывать ~100% CPU, но суммарно ты всё равно делишь **физические** ресурсы. Ускорение появляется, когда работа **параллелится** без лишней синхронизации, а не когда «просто больше потоков».

## `hardware_concurrency` и размер пула (задел)

`std::thread::hardware_concurrency()` возвращает **unsigned** hint; для `0` стандарт не обещает «угадай сам» — придётся выбрать число эмпирически. В главе 10 пул фиксирует число воркеров при создании; здесь важно лишь, что **нет** формулы «всегда равно hardware_concurrency»: I/O-bound сервисы держат больше блокируемых потоков, CPU-bound batch — часто около числа ядер.

На Fedora можно сравнить hint с выводом `lscpu` и с `nproc --all` — они отвечают на разные вопросы (логические процессоры vs affinity mask). Книга не требует affinity; достаточно помнить, что OS **мигрирует** поток между ядрами, и это нормально для учебных программ.

## Detach и lifetime: когда не join

`detach` редко нужен в учебном треке, но встречается в сервисах «фоновый heartbeat». Правило остаётся жёстким: detached поток **не должен** трогать stack `main`, локальные объекты вызывающего и статику, которая уже уничтожается при `exit`. `std::cout` при завершении процесса — отдельная гонка с flush; в тестах репозитория обычно **join** всех worker'ов до return из `main`.

Если callable бросает исключение, `join` в главном потоке **перебрасывает** его — для `01_rocket_launch` это не центрально, для будущих модулей с `try/catch` в worker (глава 10) — да.

## Типичные ошибки

Путать **число `std::thread`** с **числом ядер** и ждать линейного ускорения на 12 CPU-bound задачах при 6 ядрах. Забыть **`join`** перед выходом из `main` или из scope — **`terminate`**. Думать, что **`terminate`** «ловится» как обычное исключение. Вызывать **`detach`** и затем уничтожать объекты, к которым detached поток ещё обращается. Передавать по ссылке локальную переменную в `std::thread` без **`std::ref`** и с надеждой, что ссылка переживёт поток — data race и UB по lifetime (глава 2).


## Глубже: стек, куча и границы callable

Поток получает **свой** стек — обычно мегабайты, задаётся при создании pthread. Большие массивы «на стеке» в каждом из восьми worker'ов умножают RSS; для больших буферов используй **кучу** или **static/thread_local** осознанно. Куча процесса **общая**: `new` в worker и `delete` в другом потоке legal только с согласованным протоколом владения (queue передаёт владение деталью — глава 11).

Callable для `std::thread` не должен возвращать ссылку на локальные данные **этого** потока наружу без синхронизации — получатель может уже не существовать. Для результата — `promise`, shared state или запись в память, опубликованную до `join` (том 4 для future).

## Чтение `htop` и ожидания от CPU-bound

В `htop` один процесс с несколькими потоками показывает несколько полос CPU — это **не** «каждый поток = своё ядро навсегда». Полосы скачут при migration. Если двенадцать потоков крутят tight loop без I/O, суммарная загрузка может быть высокой, но **wall time** задачи перестаёт падать после числа ядер — закон Амдала в быту.


## Резюме связей с последующими главами

Mutex и cv ещё впереди, но уже сейчас ясно: **shared mutable** без правил — глава 2. Лямбда в `std::thread` — тема тома 2; здесь — **lifetime** захвата. Пул (глава 10) создаёт потоки один раз — экономия на создании OS thread. Parallel map создаёт потоки на фазу — другой trade-off. Обе модели начинаются с **`join`**, не с detach.

## Практика на бумаге

Нарисуй timeline: main создаёт thread T, T пишет в global, main join, main read global — где HB? Ответ: через join, не «потому что global».

Сформулируй вслух: «12 logical CPU на Ryzen 5500 — это не 12 независимых ALU для моих 12 CPU-bound threads».

## Краткое резюме

Потоки одного процесса делят память, но не стек. Ядер меньше, чем логических CPU при SMT; планировщик preemptively переключает потоки. **`std::thread`** — joinable ручка: **`join`** ждёт завершения, **`detach`** отпускает. Joinable деструктор без **`join`/`detach`** → **`std::terminate`**. Собирай с **`-pthread`**. Следующий шаг — что ломается, когда два потока трогают одну переменную без правил.
