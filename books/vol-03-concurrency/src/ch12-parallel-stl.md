# Глава 12. Parallel STL и execution policies

## Зачем эта тема

До C++17 параллелить «просто цикл по vector» означало либо свой `parallel_map` (как в упражнении архива), либо OpenMP, либо ручной пул. **Parallel STL (C++17)** добавляет перегрузки стандартных алгоритмов с аргументом **execution policy (политика выполнения)** — договор, *как* библиотека может разбить работу между потоками или даже векторными инструкциями. Это не замена продуманному пулу или очереди: другой уровень абстракции, другие ловушки.

Глава опирается на то, что ты уже знаешь про **data race** (глава 2), **mutex** (глава 3) и **false sharing** (глава 9). Parallel STL **не** синхронизирует твои лямбды за тебя: если тело алгоритма пишет в общий счётчик без защиты, UB остаётся UB, только быстрее.

## Заголовок и три политики C++17

Подключение:

```cpp
#include <execution>
#include <algorithm>
#include <numeric>
```

Пространство имён **`std::execution`** (C++17) содержит объекты политик:

| Политика | Смысл (упрощённо) |
|----------|-------------------|
| **`seq`** | Как обычный последовательный алгоритм: один поток, порядок как в классической версии. |
| **`par`** | Можно выполнять **параллельно** в нескольких потоках; элементы/блоки обрабатываются concurrently. |
| **`par_unseq`** | Можно и **параллельно**, и **vectorize (SIMD)**; итерации могут быть **переставлены** и выполняться в одном потоке несколькими «lanes». |

Вызов выглядит так:

```cpp
std::sort(std::execution::par, v.begin(), v.end());
std::for_each(std::execution::par_unseq, v.begin(), v.end(), f);
```

Не у каждого алгоритма есть parallel-перегрузка; в C++17 среди частых — `sort`, `stable_sort`, `partial_sort`, `nth_element`, `merge`, `for_each`, `transform`, `reduce`, `transform_reduce`, `count`, `find`, `copy`, `fill`, `replace`, `generate` и др. (точный список — таблица в стандарте / cppreference). Если перегрузки нет, остаётся свой код или пул.

**`seq`** нужен явно, когда хочешь сравнить с baseline или когда передаёшь политику в обобщённый шаблон «иногда par, иногда seq». **`par`** — «разрешено разбить на потоки». **`par_unseq`** — строже к твоему коду: побочные эффекты и зависимости между итерациями недопустимы сильнее, чем при `par`.

## Что ты обещаешь библиотеке

Для **`par`** и **`par_unseq`** стандарт накладывает требования на **function object** и доступ к памяти:

- Нельзя полагаться на **порядок** обхода, как в однопоточном `for`.
- **Data race** в пользовательском коде — UB; библиотека не делает твой `counter++` атомарным.
- Для **`par_unseq`**: не должно быть **data races** даже с учётом того, что несколько элементов обрабатываются «как бы одновременно» в одном потоке (vectorization). Практически: не трогать соседние элементы из других итераций без синхронизации, не использовать указатели/ссылки, которые alias между итерациями неожиданно.

Чтение только своего элемента, запись только в `out[i]` по индексу итерации — типичный безопасный паттерн. Запись всех потоков в один `std::vector` через `push_back` — **нет**, нужен pre-sized output или локальные буферы + merge.

## Когда ускорения нет (или его мало)

Parallel STL не гарантирует speedup. Частые причины разочарования:

**Маленький объём работы.** Накладные расходы на создание задач, деление диапазона и синхронизацию внутри библиотеки съедают выигрыш на `n = 100` или на дешёвой лямбде «прибавить 1». Имеет смысл включать `par` только когда профилирование показывает, что тело тяжёлое или `n` велик.

**Память и bandwidth.** Параллельный `sort` или `reduce` упирается в пропускную способность RAM и кэша; на больших массивах scaling часто sublinear. **False sharing** (глава 9) при записи в соседние счётчики убивает и parallel, и ручной parallel_map.

**Несбалансированная нагрузка.** `for_each` с телом «иногда секунда, иногда наносекунда» даёт простаивающие потоки; нужен другой разбиение (chunk по индексу vs dynamic scheduling — у stdlib своя эвристика, ты её не контролируешь напрямую).

**Уже занятые потоки.** Вызов `sort(execution::par, ...)` из воркера **уже** работающего пула может размножить потоки (см. ниже) — вложенный параллелизм без лимита.

**Алгоритм sequential по сути.** Некоторые стадии `sort` плохо масштабируются; иногда выигрывает другой алгоритм или свой parallel_map с известной формой данных.

Правило практика: сначала **корректный `seq`**, замер, потом **`par`** на том же железе; смотреть не только wall time, но и загрузку CPU и allocators.

## «Взрыв потоков» (thread explosion)

Реализация Parallel STL **зависит от стандартной библиотеки**. Libstdc++ (GCC) и libc++ (Clang) используют **backend** (часто на базе TBB или встроенного thread pool в новых версиях), но детали менялись между релизами. Важно для архитектуры:

- Вызов **`std::sort(execution::par, ...)`** может временно создать **много задач** и задействовать **пул или новые потоки** — не «ровно один дополнительный поток».
- **Вложенные** вызовы `par` из нескольких внешних `std::thread` умножают конкуренцию: 8 ваших потоков × каждый зовёт `par` sort → десятки workers ОС, oversubscription, context switch storm.
- Это не баг STL, а **отсутствие глобального бюджета потоков** в C++17 API: политика не знает, что ты уже внутри `ThreadPool`.

Отсюда практики: не вызывать **`par`** из каждого воркера пула «по умолчанию»; на верхнем уровне — либо пул + ручное разбиение (глава 10, упражнение parallel_map), либо один уровень Parallel STL; для nested parallelism в индustry часто TBB с **limited concurrency** или **`std::async` с политикой** на верхнем уровне — но это уже граница с **томом 4**.

На Fedora проверяй версию libstdc++ / наличие TBB в документации дистрибутива; линковка иногда требует `-ltbb` для старых связок GCC+parallel STL.

## Сравнение с ручным `parallel_map`

Упражнение **архив** учит **явно**: сколько потоков, какие индексы, `join`, тип `invoke_result_t`. Parallel STL прячет разбиение — удобно для **stateless** map по random-access контейнеру, хуже когда нужны:

- фиксированный **лимит** потоков под SLA;
- **очередь** и backpressure (глава 11);
- **deterministic** порядок side effects;
- интеграция с **stop_token** **(C++20)** в своих воркерах.

Оба инструмента законны: Parallel STL — для bulk numeric / STL-native; свой код — для pipeline и пула.

## Связь с `08_parallel_map` и `THEORY.md`

Упражнение архива учит **явное** разбиение: `begin = i * size / n_threads`, `end = (i+1) * size / n_threads` (умножение до деления), join, тип `vector` результатов через `invoke_result_t`. Parallel STL **скрывает** нарезку — удобно для `transform` на random-access, но не снимает ответственность за **гонки** в теле.

`THEORY.md` предупреждает: тесты `08` делятся нацело — зелёный прогон **не** доказывает, что формула кусков без остатка полная; то же относится к доверию «`par` сам разобьёт правильно» без проверки на «кривых» размерах.

## Execution policy и исключения

Если лямбда под `par` бросает, поведение зависит от алгоритма и реализации — часть работы могла уже выполниться. Для учебного кода предпочитай **noexcept** тела или локальный catch; production иногда собирает `exception_ptr` из задач пула — ближе к тому 4.

## Аллокатор и parallel sort

Parallel `sort` может временно требовать дополнительной памяти и потоков; на embedded или с лимитом потоков это может быть неожиданностью. Читай документацию libstdc++/libc++ для своей версии на Fedora.

## `reduce`, ассоциативность и `par_unseq`

`std::reduce(execution::par, ...)` может суммировать блоками в произвольном порядке. Для **float** это меняет округление относительно левого-направо `accumulate`; для операций, не ассоциативных в float, результат **не bitwise** как у seq — это ожидаемо. Для `int` сложение ассоциативно математически; для пользовательского `op` ты обязан понимать ассоциативность и нейтральный элемент.

`transform_reduce` с `par_unseq` — мощный, но требует самого чистого тела transform.

## Типичные заблуждения

«**Parallel STL** делает программу thread-safe» — только если **твоё** тело без гонок. «**par** всегда быстрее» — часто медленнее на малых `n`. «Порядок вызовов лямбды сохранится как в seq» — для `par` **нет**. «**par_unseq** — просто “ещё параллельнее”» — это ещё и **перестановка** итераций с SIMD. «Количество потоков = `hardware_concurrency`» — реализация может создавать **больше** задач и переиспользовать pool.


## Глубже: policy type erasure

Политики `std::execution::par` — объекты типа `parallel_policy`; их передают первым аргументом алгоритма. Шаблон «algorithm(policy, begin, end, f)» — единый стиль; не все алгоритмы перегружены.

## Determinism и side effects

`for_each(par)` не гарантирует порядок вызова f; логирование «строго по индексу» сломается. Side effects в file или socket — нужна sync или seq policy.


## Сценарий выбора API

Bulk sort миллиона int на машине разработчика — кандидат на `execution::par` после baseline. Pipeline завода — **не** Parallel STL, а queue + threads. Oracle из `03_oracle` — async, том 4. Не смешивай уровни абстракции в одном модуле без причины.

## Execution policy в generic коде

Шаблон `template<class Exec> void run(Exec&& policy)` может принимать `seq` или `par` — удобно для A/B тестов. Не hardcode `par` в библиотеке, если caller не знает, что уже внутри пула.

Документируй: «не вызывать из N worker threads без limit concurrency».

## Краткое резюме

**C++17** даёт **`std::execution::seq`**, **`par`**, **`par_unseq`** для многих алгоритмов. Ты отвечаешь за отсутствие гонок и за семантику побочных эффектов; **`par_unseq`** строже. Ускорение не гарантировано: малый объём, bandwidth, imbalance, nested **`par`**. **Thread explosion** — риск при вызове parallel algorithms из многих потоков без глобального лимита. Для pipeline, пула и явного контроля — главы 10–11 и свой код; для bulk STL — **`execution::par`** после замеров.
