# Глава 14. Отладка гонок, чеклист и итоги тома

## Зачем эта тема

Многопоточный код **компилируется** с теми же зелёными галочками, что и однопоточный. **Data race** и часть нарушений happens-before — **undefined behavior (неопределённое поведение)**: программа может «работать годами» и падать в проде на другом ядре. Том 3 дал модель и паттерны; без **инструментов** и **привычек** ты возвращаешься к printf-отладке и ложным «я добавил mutex, значит, безопасно».

Эта финальная глава связывает том с **томом 7** (санитайзеры), даёт **чеклист** перед merge и **сводку типичных ошибок** всей книги. Практика по-прежнему в `multithread/` и `check.sh`; здесь — как не обманывать себя после зелёного теста.

## Thread Sanitizer (TSan) — обзор и куда углубляться

**Thread Sanitizer (TSan)** — инструмент времени выполнения (обычно Clang/GCC на Linux), который **отслеживает happens-before** между потоками и **сообщает о data race**: два конфликтующих доступа к одному адресу, хотя бы один записывающий, без синхронизации между ними.

Типичный цикл на Fedora:

```bash
g++ -std=c++17 -pthread -fsanitize=thread -g -O1 -o app main.cpp
./app
```

(Для CMake-проекта флаг добавляют в **Debug**-конфигурацию или отдельную цель; детали флагов, взаимодействие с ASan, CI — в **томе 7 — санитайзеры**, `books/vol-07-sanitizers`.)

TSan **не доказывает** отсутствие всех багов: он ловит **гонки по памяти**, не deadlock (хотя иногда видны симптомы), не логические ошибки «закрыли очередь и выбросили хвост», не ошибки memory order **между atomics** так же наглядно, как классический race на `int`. Зато для «два потока трогают vector без mutex» — первый друг.

Ложные ожидания: TSan **замедляет** и **увеличивает** память; гонки **недетерминированы** — прогон `./check.sh` без санитайзера может быть зелёным, с TSan — красным. Имеет смысл гонять **stress** (больше итераций, больше потоков), когда учебный тест делится нацело и не ловит off-by-one в разбиении (глава 12, архив).

Полная глава про TSan, отчёты, suppressions и связку с UBSan — **не здесь**, а в томе 7; запомни: **TSan = первый ответ на «подозреваю гонку»** после code review.

## Чеклист перед «готово»

Пройди пункты **вручную** на своём diff, даже если тесты зелёные:

**Потоки и lifetime (главы 1–2, том 2).**

- У каждого **`std::thread`** есть **`join`** или **`detach`** до уничтожения joinable ручки; иначе **`std::terminate`** в деструкторе `thread`.
- Нет **`[&]`** на локальные переменные, которые умирают раньше потока.
- **`[this]`** в задачах пула/очереди: объект-владелец живёт до конца работы воркеров.

**Mutex и cv (главы 3–4).**

- Общие mutable данные под **`mutex`** или **`atomic`**, не **`volatile`**.
- **`condition_variable::wait`** только с **предикатом**; учтён **spurious wakeup** и **lost wakeup** при раннем **`notify`**.
- **`unique_lock`**: вызван **`lock(mutex_поля)`**, не пустой lock на другом объекте (затенение).
- **`join`** воркеров **не** под mutex, который воркер ждёт в цикле (deadlock в пуле).

**Atomics и memory order (главы 5–7).**

- Для флагов «готово» между потоками — **`std::atomic`**, не plain `bool`.
- Если используешь **`memory_order`**, осознанно: default **`seq_cst`**; ослабление — только с пониманием **happens-before** / **synchronizes-with**.
- CAS-циклы (рекорд): не «load; if; store» на plain или без compare.

**Паттерны (главы 8–11).**

- **False sharing**: горячие счётчики разных потоков не в одной cache line без нужды.
- Пул: **`stopped`** и «очередь пуста» — формула выхода **не** выкидывает задачи; **`submit`** после stop игнорирует или по контракту.
- Очередь: **`cap_`** — ёмкость; **`close`** — drain хвоста; **`pop` false** только **`closed && empty`**.
- Parallel map / STL: нет **`par`** с общим **`push_back`** без синхронизации.

**Parallel STL (глава 12).**

- Тело алгоритма **reentrant** по памяти; nested **`execution::par`** осознан.

**C++20 (глава 13).**

- Если используешь **`jthread`**, stop — **кооперативный**; очередь всё равно закрывают явно.

**Сборка.**

- Хотя бы один прогон с **`-fsanitize=thread`** на изменённом бинарнике (когда настроишь по тому 7).

## Сводка типичных заблуждений тома

Краткая «стена shame» — чтобы перечитать перед собесом или перед code review:

| Миф | Реальность |
|-----|------------|
| Потоки ОС = ровно `hardware_concurrency()` | Можно создать больше; планировщик time-slice; oversubscription. |
| `volatile` для sync между потоками | Нет happens-before; нужен **atomic** или **mutex**. |
| Зелёный тест = нет гонки | Гонки недетерминированы; тест может не делить хвост данных. |
| `notify` только вне mutex | Для **cv** notify под mutex **OK**; **join под mutex** воркера — нет. |
| `close` очереди = сразу стоп worker | Нужно **доопустошить** очередь. |
| `if (stopped) return` в пуле | Выход когда **stopped и jobs пуста** (и аналоги). |
| Parallel STL = thread-safe код | Thread-safe должно быть **тело** лямбды. |
| Слабый memory order «для скорости всегда» | Сначала корректность **seq_cst**, потом профиль. |
| `async` всегда новый поток | Политика и реализация (том 4). |
| Lock-free «быстрее всегда» | Сложность, ABA, часто mutex достаточно (глава 8). |

## GDB и «Heisenbug» (мост к тому 6)

Под GDB потоки **медленнее** меняют interleaving — гонка «исчезает». Это не оправдание UB; это аргумент за TSan и за stress-тесты. В томе 6 разберут `info threads`, breakpoint на всех потоках, типичный hang = deadlock vs livelock. Здесь запомни: **зелёный под GDB** ≤ **зелёный без инструментов** по надёжности доказательства.

Для зависшего `join` смотри стеки: все в `cv.wait`? кто держит mutex? главный в `join` под тем же mutex?

## Регрессия `check.sh` vs concurrency-уверенность

`multithread/check.sh` гоняет функциональные тесты упражнений — must-have перед «сдал». Он **не** заменяет TSan на изменённом коде и **не** ловит все ordering-баги. Идеальный цикл: локально `cmake --build` + `./check.sh`, затем отдельная сборка с `-fsanitize=thread` на том же бинарнике или цели (том 7).

## Глубже: что делать после отчёта TSan

Отчёт даёт два stack trace и адрес. Исправление: один mutex, atomic, или разделить данные. Suppression — последнее средство для legacy; в учебном коде — **fix**, не suppress.

## Deadlock detection

TSan **не** заменяет deadlock detectors; hang с полными стеками в `mutex.lock` — смотри lock order (глава 3). Для учебного пула — checklist join/mutex.
