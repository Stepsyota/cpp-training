# Глава 6. Memory order у atomics

## Зачем эта тема

После [главы про atomics](./ch05-atomics.md) ты уже видел `std::atomic` как способ обновить счётчик или рекорд без mutex: операции **атомарны** — другой поток не увидит «половину» записи. Но атомарность **не** отвечает на вопрос: *в каком порядке* мои обычные записи в память станут видны соседнему потоку? Компилятор и процессор вправе переставлять инструкции, пока это не ломает **однопоточную** семантику. Между потоками без правил вы получаете «работает на моей машине» и необъяснимые баги на другом железе.

**Memory order** — это контракт: какие перестановки допустимы вокруг atomic-операции и какие **отношения видимости** вы создаёте между потоками. По умолчанию C++ даёт самый строгий вариант; ослаблять его имеет смысл только когда вы понимаете модель памяти и измерили выигрыш.

## Пять порядков в C++17

У `std::atomic` операции load, store, read-modify-write (RMW) принимают необязательный аргумент `std::memory_order`. Имена отражают роль операции в протоколе «опубликовал данные — другой прочитал флаг».

**`memory_order_relaxed`** — атомарность есть, **синхронизации нет**. Подходит для чистого счётчика статистики, где другим потокам не нужно «увидеть» ваши предыдущие записи в обычную память — только итог RMW. Пример: `fetch_add` на числе посещений без передачи связанного буфера.

**`memory_order_acquire`** — обычно на **load** (или RMW, который читает). Всё, что **после** acquire-load в этом потоке, не будет переупорядочено **раньше** load. Смысл: «я прочитал флаг готовности — теперь имею право читать данные, которые другой поток опубликовал до release».

**`memory_order_release`** — обычно на **store** (или RMW, который пишет). Всё, что **до** release-store в этом потоке, не уйдёт **после** store. Смысл: «сначала заполнил буфер, потом store в флаг — читатель с acquire увидит буфер целиком».

**`memory_order_acq_rel`** — для RMW, которая и читает, и пишет (например compare-exchange): acquire на чтении и release на записи одной операцией.

**`memory_order_seq_cst`** — **sequentially consistent**: и атомарность, и глобальный порядок всех seq_cst-операций, с которым согласуются все потоки. Это «режим по умолчанию» для atomics в C++ если не указать иное. Проще рассуждать, дороже на некоторых архитектурах (лишние fence на ARM и т.д.).

Схема «один флаг + буфер» без mutex часто выглядит так: писатель заполняет данные, делает `store(true, release)`; читатель в цикле делает `load(flag, acquire)` и только при `true` читает буфер. Relaxed на самом флаге **без** пары release/acquire **не** даёт такой гарантии для буфера.

```cpp
// Писатель
data = 42;
ready.store(true, std::memory_order_release);

// Читатель
while (!ready.load(std::memory_order_acquire)) { /* spin */ }
int x = data; // видим 42 при корректном протоколе
```

## Когда что выбирать (практическая лестница)

Начинай с **`seq_cst`** или с **mutex**: вы платите немного производительности, но получаете понятную историю для отладки. Переходите к acquire/release, когда протокол явный: один (или несколько) «каналов» публикации через atomic-флаги или указатели, остальная память защищена этим протоколом.

**Relaxed** — только если вы документировали, что **нет** передачи связанных данных, только сам atomic. Классика: метрика, счётчик ошибок, где читателю не важен точный момент согласования с другими полями.

**Acquire/release** — типичный lock-free «handoff»: узел очереди, статус задачи, «буфер готов». Не смешивайте «relaxed на флаге + обычная запись в vector без барьера» — это не тот же контракт, что mutex.

**Acq_rel** — CAS-циклы, где успешный обмен и публикует, и потребляет предыдущее состояние (рекорд «максимум», счётчик с проверкой).

**Seq_cst** — когда нужен простой глобальный порядок (редко несколько atomics в одной логике) или вы ещё не готовы доказывать корректность слабее.

## Значение по умолчанию и API

Если вызвать `load()`, `store()`, `operator++` на `std::atomic` **без** явного order, стандарт требует **`memory_order_seq_cst`**. Это сознательный выбор языка: первый рабочий вариант должен быть безопасным для рассуждений, а не самым быстрым на paper. Когда в книге или в чужом коде видите голый `flag.store(true)`, мысленно допишите `seq_cst`.

Некоторые обёртки (например `atomic<bool>::wait` **(C++20)**) — отдельная история блокировки потока; в C++17 привычнее spin на load или `condition_variable` рядом с mutex. Memory order у wait/notify **(C++20)** согласован с моделью памяти, но для курса репозитория достаточно помнить: «atomic + cv» — разные механизмы, их не подменяют друг другом без протокола.

## Связь с compare_exchange

`compare_exchange_weak` / `strong` тоже принимают success и failure order. На успехе часто `acq_rel` или `seq_cst`; на неудаче иногда достаточно `relaxed`, если неудача не открывает доступ к связанным данным. Ошибка новичка: CAS с relaxed на успехе, а потом чтение «защищённой» структуры без acquire — снова дыра в happens-before (подробно в следующей главе).

## x86 и «кажется, что работает»

На многих десктопах с Intel/AMD **TSO** (total store order) делает поведение «похожим» на seq_cst для многих naive паттернов: store не перепрыгивают друг друга так свободно, как на ARM. Отсюда классическая ловушка: код с relaxed или даже с data race на `data` **годами** проходит тесты на Fedora/x86 и падает на телефоне или сервере Ampere. Memory order в стандарте описывает **все** conforming реализации, а не ваш текущий CPU.

Компилятор при этом **всё равно** может переупорядочить обычные load/store, если между ними нет happens-before. `-O2` и LTO не «уважают» ваши намерения без atomics и барьеров. Поэтому аргумент «я не вижу бага в GDB» не отменяет необходимость order.

## Несколько atomics: не путать с mutex

Mutex гарантирует, что **все** поля под замком согласованы. Если вы защищаете структуру **двумя** relaxed-счётчиками без общего протокола, инвариант «sum частей = целому» может быть нарушен в наблюдаемом состоянии. Либо один mutex, либо одна точка публикации (release) и одна точка потребления (acquire), либо doc lock-free алгоритма на бумаге. Смешивать «mutex на A, relaxed на B, обычный int на C» без диаграммы потоков — приглашение к гонке.

## Fence (кратко)

`std::atomic_thread_fence` — отдельный **барьер**, не привязанный к одной переменной. Режимы `memory_order_acquire`, `release`, `acq_rel`, `seq_cst` задают, какие перестановки запрещены относительно fence. В прикладном коде на C++17 чаще хватает **явных** order на load/store atomic, чем ручных fence. Fence появляются в низкоуровневых lock-free структурах и при портировании алгоритмов с других языков. Если вы не пишете библиотеку очереди — знайте, что они существуют, но не начинайте с них.

## Чего memory order не делает

Порядок **не** заменяет mutex для составного инварианта на нескольких полях, если протокол не выстроен целиком на atomics и release/acquire. Порядок **не** лечит data race на **не**atomic переменных: одновременная запись в `int` без atomic или без синхронизации — по-прежнему UB.

`volatile` — не memory order и не atomic; для потоков используйте `std::atomic` с осмысленным order или mutex.

## К собеседованию: формулировки одной фразой

**Relaxed** — «этот atomic целостен, но не тянет за собой видимость соседних полей». **Release** — «всё до меня видно тому, кто сделает acquire на этой же atomic». **Acquire** — «после меня можно читать то, что другой отпустил release-ом». **Seq_cst** — «как будто все потоки по очереди нажимали кнопку на одной ленте операций» — сильнее, чем нужно многим алгоритмам, но слабее, чем «я не знаю модель памяти».

Интервьюер часто просит нарисовать двух потоков и стрелки: где release, где acquire, где обычная память. Если стрелок нет — вы не доказали отсутствие гонки на неatomic данных.

## Сценарий на Fedora

Собери маленький бинарник с двумя потоками: «флаг + int» с relaxed на флаге и без барьеров — иногда «проходит» из-за случайного порядка на x86 (TSO сильнее, чем ARM). Это **не** доказательство корректности. Для обучения полезнее `-fsanitize=thread` (том 7): TSan ловит гонки на `data`, даже если флаг atomic.

С `-std=c++17 -pthread` явно указывай order в коде, который учишь читать: так в disassembly (objdump) виднее, где компилятор вставил барьеры на слабых ISA при кросс-сборке.

## Связь с mutex (мост к главе 7)

Mutex lock/release в стандарте тоже создаёт synchronizes-with; многие программы **вообще** не задают memory order вручную — и это нормально. Atomic с order нужен, когда вы **снимаете** замок с одного hot path или строите lock-free handoff. Сравнение: mutex «опубликовал всё под замком»; release на флаге «опубликовал всё **до** store». Нельзя смешивать модели в одном инварианте без явного моста.

Если сомневаетесь между «ещё один mutex» и «relaxed + надеюсь» — выбирайте mutex или seq_cst, пока не нарисуете цепочку happens-before.

## Типичные заблуждения

«Atomic сам по себе синхронизирует всё» — только с правильной парой release/acquire (или seq_cst, или mutex). «Relaxed быстрее — возьму везде» — быстрее, но часто **неверно**. «На x86 можно не думать» — ваш код может уехать на ARM; плюс компилятор всё равно переупорядочивает. «Seq_cst — медленно, значит всегда acquire/release» — преждевременная оптимизация без профиля и без доказательства.

## Store-load пары и «как будто одна кнопка»

Иногда в статьях встречается пример «thread 1: store A; store B; thread 2: load B; load A» и «удивительный» порядок. **Seq_cst** на всех участвующих atomics запрещает «увидеть B новым, а A старым» для **этих** atomics. Для **смешанных** atomic и неatomic полей правила другие: неatomic `A` и `B` без синхронизации по-прежнему гонка.

Практический вывод: если в структуре два поля должны обновляться **согласованно** для читателя, одного release на «главном» флаге мало, пока читатель не знает протокол «сначала флаг, потом оба поля под ним». Mutex делает это автоматически для всего, что под замком.

## Карта ordering для типичных паттернов курса

| Паттерн | Частый order | Замечание |
|---------|--------------|-----------|
| Глобальный счётчик метрик | relaxed | Нет публикации связанных данных |
| Флаг «буфер готов» + plain buffer под mutex | release/acquire на флаге **или** только mutex | Не смешивать без документа |
| CAS max (highscore) | seq_cst или acq_rel на success | Relaxed на success только если нет связанных полей |
| Очередь на mutex | order не задаёшь вручную | HB через unlock/lock |
| Idle/busy счётчик пула | под mutex или atomic + протокол | Не «relaxed на busy + plain queue» |

Таблица — шпаргалка для **review**, не призыв ослаблять всё подряд.

## Consumer-producer на одном atomic (учебный микро-пример)

Когда mutex избыточен **только** для одного слова и протокол «один writer — один reader» формализован, иногда используют single-producer single-consumer ring с atomics — это уже глава 8 territory. Для C++17 курса достаточно **mutex + cv** на очереди; memory order вручную понадобится, если ты **читаешь** lock-free статьи или оптимизируешь hot path **после** профиля.

Если в коде появляется `memory_order_relaxed` — в комментарии одной строкой **зачем** (только счётчик / только статистика / доказанный протокол).

## Компилятор, CPU и «на x86 работает»

Даже на TSO x86 **компилатор** может переупорядочить plain access относительно atomic, если между ними нет HB. `-O2`, LTO и autovectorization не «знают» ваши намерения по plain `data`. TSan ловит гонки на plain; **не** ловит все ошибки ordering между atomics — нужен код-review и тесты на слабых моделях (litmus), если вы на that level.

Fedora CI на x86_64 не освобождает от модели C++ для ARM серверов и мобильных.

## Read-modify-write и счётчики

`fetch_add`, `fetch_sub`, `operator++` на atomic — RMW. Для глобального «сколько задач осталось» часто хватает `fetch_sub(1, relaxed)` на последнем шаге, если **никто** не читает связанные структуры по значению счётчика без acquire. Если же «когда счётчик стал 0 — читай буфер результатов», нужен release на последнем decrement или отдельный флаг готовности с парой acquire/release.

Рекорд «максимум» через CAS-цикл (как в учебной задаче на highscore) обычно использует `compare_exchange` с `acq_rel` или `seq_cst`: вы читаете текущий max, предлагаете больший, при неудаче перечитываете. Relaxed на success может быть OK **только** если других данных, зависящих от max, нет — только сам atomic.


## Глубже: litmus-тесты в голове

Классический litmus: W1: store A; store B; W2: load B; load A — какие комбинации значений **допустимы** при разных order? Для seq_cst atomics A и B — «странные» комбинации ограничены; для plain A,B без sync — **data race**, litmus не про «допустимо», а про UB.

Не путай учебный litmus с **production** кодом: если сомневаешься — mutex или seq_cst.

## Store buffering и интуиция release/acquire

Release говорит: «все мои предыдущие записи **видны** тому, кто сделает acquire и увидит мой store». Это не «flush всего кэша CPU» в буквальном смысле, но правильная **абстракция** для reasoning.


## Мост к happens-before

Order на atomic — **способ** создать synchronizes-with. Без HB между потоками plain memory остаётся в UB. Mutex — альтернативный способ не думать о five orders на каждой строке.

## Single-producer single-consumer (SPSC) и ordering

Классический SPSC ring buffer использует **release** на индекс producer после записи слота и **acquire** на индекс consumer перед чтением — или symmetric пара. Это **не** упражнение репозитория, но язык для чтения статей. Ошибка: relaxed на индексах и plain read слота — снова дыра.

В C++17 курсе bounded queue на **mutex** проще и достаточна; SPSC atomics — оптимизация **после** профиля.

## `memory_order_consume` (историческая справка)

В стандарте был `consume` — ослабленный acquire; на практике реализации часто mapping на acquire. **C++17** deprecate consume для упрощения; в новом коде не используй — думай **acquire/release** или seq_cst.

## Краткое резюме

Memory order описывает, как atomic-операции участвуют в **видимости** обычной памяти между потоками: relaxed — только атомарность; acquire/release — типичная пара «прочитал флаг — вижу данные»; acq_rel — RMW; seq_cst — строгий глобальный порядок по умолчанию. Fences — редкий инструмент поверх той же модели. Для учебных задач и первых lock-free протоколов держись seq_cst или mutex, пока не можешь нарисовать happens-before цепочку.
