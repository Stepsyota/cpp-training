# Глава 10. Паттерн пула потоков (теория)

## Зачем эта тема

Запуск `std::thread` на каждую мелкую задачу дорог: создание потока, настройка стека, давление на планировщик. **Пул потоков** держит фиксированное число **воркеров**, которые в цикле забирают работу из **очереди** и выполняют callables. Клиентский код не создаёт поток на каждый запрос — он **submit**-ит задачу и (опционально) ждёт простоя.

[False sharing](./ch09-false-sharing.md) напоминает: даже идеальный протокол пула можно испортить layout полей. В репозитории `training` есть практика на этот паттерн; **эта глава не разбирает готовую реализацию** и не подставляет код из `solutions/`. Здесь — поля, инварианты, shutdown и типичные deadlock, которые ты проверяешь на своём коде.

## Роли компонентов

**Workers** — `std::thread`, стартующие в конструкторе пула (или лениво — реже). Каждый воркер крутит **бесконечный цикл** до сигнала остановки: «есть работа — выполни; нет — усни, но проснись при новой задаче или shutdown».

**Очередь jobs** — контейнер callables (`std::function<void()>` или шаблон с move-only closure). **Submit** кладёт задачу под mutex (или через lock-free очередь в продвинутых системах; в учебнике — mutex + cv). Владение задачей **передаётся** в очередь (move), а не ссылкой на локальную лямбду вызывающего.

**Mutex** защищает очередь, флаги состояния и счётчики, которые читаются вместе с очередью. **Condition variable** будит спящих воркеров, когда появилась работа или изменился режим shutdown.

**Флаг stopped** (или `shutdown`) говорит: новых задач не принимаем, воркеры должны **доработать** уже лежащие в очереди и выйти из цикла. Submit после stopped — игнор или ошибка по контракту API.

**Счётчик busy** (или аналог) — сколько воркеров **прямо сейчас** выполняют job **вне** критической секции очереди. Нужен для `wait_idle`: «все задачи не только вынуты из очереди, но и **закончили** выполнение».

## Предикат wait воркера

Воркер не должен крутить busy-wait на пустой очереди. Типичный паттерн с `condition_variable`:

- Захватить mutex.
- Ждать, пока **не** `( !jobs.empty() || stopped )`.
- Если `stopped && jobs.empty()` — выйти из цикла (завершить поток).
- Иначе снять job из очереди, **увеличить busy**, **отпустить mutex**, вызвать `job()`, поймать исключения если нужно по контракту, снова захватить mutex, **уменьшить busy**, при необходимости **notify** тем, кто ждёт idle.

Формула «спать, пока пусто **и** не остановлены» важна: если ждать только `!empty`, при shutdown с пустой очередью воркер **никогда** не проснётся, чтобы выйти — зависание join. Если выходить при `stopped` **без** «и очередь пуста», можно **выкинуть** задачи, ещё лежащие в очереди — другая классическая ошибка.

```cpp
// Схема предиката (не полный пул)
queue_cv.wait(lock, [&] {
    return !jobs.empty() || stopped;
});
if (stopped && jobs.empty())
    break; // выход из цикла воркера
```

## Выполнение job вне mutex

Пока воркер выполняет `job()`, он **не** должен держать mutex очереди — иначе submit и другие воркеры стоят. Поэтому busy обновляют так: `++busy` под mutex, unlock, `job()`, lock, `--busy`. Waiters на idle смотрят на `jobs.empty() && busy == 0` (и иногда другие условия).

## Shutdown: порядок сигналов

Деструктор или явный `shutdown()`:

1. Под mutex выставить **stopped = true** (и больше не принимать submit).
2. **`notify_all`** на cv — все спящие воркеры должны перепроверить предикат; часть увидит оставшиеся jobs, часть — пустую очередь и stopped и выйдет.
3. **Join** каждого worker **без** удержания mutex, который воркеру нужен для `--busy`.

Третий пункт — отдельная ловушка, её разберём ниже.

## Deadlock: join под тем же mutex

Сценарий: главный поток в `wait_idle` держит mutex и ждёт `busy == 0`. Воркер закончил `job()`, пытается зайти в mutex, чтобы `--busy` и notify. Главный не отпускает — воркер не может decrements busy — главный ждёт вечно. **Join** воркеров из деструктора **под тем же mutex**, который воркер берёт в конце job — та же семейство deadlock: воркер ждёт lock для `--busy`, деструктор ждёт join, воркер не завершился.

**Правило:** join worker threads **никогда** не выполнять, удерживая mutex, который им нужен для нормального завершения итерации (включая декремент busy и выход из цикла). Деструктор: флаг stopped, notify_all, **unlock**, затем join всех handles.

`notify` под mutex при wait — **нормально**: пробуждённый поток сначала пытается взять mutex; спящий уже отпустил его внутри wait. Путать это с «join под mutex» нельзя — разные протоколы.

## Submit и гонки

Submit: lock, если stopped — return, иначе push job, notify_one (или notify_all). Notify будит одного воркера — часто достаточно; при fairness иногда all.

Задачи с захватом `[&]` на стек вызывающего **недопустимы**, если submit возвращается до выполнения. `[this]` на объекте пула — живёт, пока жив пул и пока job не переживёт деструктор; shutdown должен **drain** очередь или отменять контракт.

Исключения из `job()`: решите, глотает ли пул, логирует или пробрасывает — но воркер **не** должен умереть без join, иначе снова `std::terminate` от joinable thread.

## wait_idle и клиентский код

Клиент после серии submit может ждать: очередь пуста **и** busy ноль. Это отдельный wait с предикатом на cv (часто та же cv, что у воркеров, или вторая — «idle»). Предикат проверяет под mutex. Опять же: не вызывать join внутри этого wait.

## Связь с лямбдами (том 2)

Воркер часто запускается как `[this] { ... }`, чтобы видеть поля пула. Lifetime: поток joinable → деструктор `std::thread` → terminate. Пул обязан join до уничтожения полей, которые job использует.

## Связь с false sharing (глава 9)

Поля `busy`, размер очереди, stopped — разная частота записи. Если несколько воркеров часто трогают соседние atomics/int на одной cache line, профиль покажет странное. На первом проходе mutex достаточно; при оптимизации — layout.

## notify_one vs notify_all

**notify_one** будит одного waiter — достаточно, когда любой свободный воркер заберёт job. При shutdown нужен **notify_all**, иначе часть воркеров может спать, не увидев `stopped`. После batch submit иногда будят all, чтобы разгрести очередь быстрее — trade-off с thundering herd.

Пробуждение под mutex **не** означает, что waiter мгновенно бежит: он сначала снова берёт mutex. Это нормально и не отменяет правило «не join под mutex воркера».

## Исключения и состояние пула

Если `job()` бросает, воркер должен остаться живым (catch, log), иначе `--busy` не выполнится и idle wait зависнет. Политика «exception propagates to submitter» требует `packaged_task` / future — ближе к тому 4. Для `void()` jobs в учебном пуле обычно глотают или std::terminate по контракту README — но **осознанно**, не случайно.

## Отличие от «просто vector of thread»

Запустить N потоков один раз на фазу работы и join — похоже на пул, но без очереди: кто какую задачу взял, зашито при создании (как в parallel map с нарезкой диапазона). Пул **динамически** раздаёт jobs из общей очереди — другой баланс нагрузки, другой shutdown. Не путайте паттерны при чтении чужого кода.

## `wait_idle` и клиентские гонки

Клиент, ждущий «все jobs выполнены», должен ждать **`jobs.empty() && busy == 0`** (или эквивалент по контракту), не только пустую очередь: job может **выполняться** после pop. Держать mutex idle-wait и блокировать worker на `--busy` — deadlock из раздела выше.

## `std::function` и move-only задачи

Очередь часто хранит `std::function<void()>`, которое **копируемо** только если callable копируем; move-only closure требует `packaged_task`, custom wrapper или шаблонной очереди — за пределами минимального учебного API. Move при push **обязателен** по смыслу: задача **передана** пулу, не одолжена по ссылке.

## Размер пула и потоки ОС

Число воркеров не обязано равняться «12 SMT» на Ryzen: CPU-bound задачи часто ставят около числа **физических** ядер; I/O-bound — выше. Пул не создаёт новых ядер — он переиспользует потоки. Лишние воркеры на одном CPU конкурируют через планировщик (см. главу 1).

## Чего пул не решает

Не заменяет bounded queue на конвейере (глава 11): там back-pressure и **close** канала. Пул ограничивает **число потоков**, не обязательно глубину очереди — переполнение очереди submit без лимита может съесть память. Production добавляет max queue size или отказ.

## Типичные заблуждения

«notify без mutex всегда OK» — для вашего протокола с cv обычно notify **после** изменения очереди под lock. «stopped — сразу exit» — без drain очереди теряете jobs. «busy не нужен — пустая очередь значит idle» — job может **выполняться** после pop. «detach воркеров при shutdown» — теряете контроль и lifetime.

Проверь свой код по чеклисту главы: predicated wait с `stopped`; drain очереди; job вне mutex; `--busy` не под join mutex; submit после stopped; join всех workers в деструкторе. Если пункт проваливается — это не «стиль», а баг, который всплывёт под нагрузкой или в деструкторе.


## Глубже: fairness и starvation клиента

`notify_one` может theoretically starve worker, если OS unfair — редко в учебных тестах. Batch submit + notify_all — грубее, но иногда проще отладить shutdown. Production выбирает по метрикам.

## Graceful shutdown vs abrupt

`stopped` + drain — **graceful**: задачи в очереди выполняются. «Отмена» задач, не начатых worker'ом, — другой контракт (future cancel **(C++20)** / stop_token). Не смешивай термины в API пула.


## Сценарий «день из жизни» пула (словами)

Утро: конструктор поднимает N кузнецов, каждый в wait. Клиент submit'ит десять заказов — десять notify или меньше, если воркеры уже бодрствуют. Полдень: submit после stopped — no-op. Вечер: деструктор ставит stopped, notify_all, join без mutex. Ни один кузнец не `--busy` под замком, который ждёт main в join.

## Краткое резюме

Пул: N воркеров, очередь callables, mutex + cv, stopped, busy. Wait-предикат: работа есть **или** shutdown; выход когда stopped **и** очередь пуста. Job выполняется **без** mutex; busy отражает executing. Shutdown: stopped, notify_all, join **без** mutex, который блокирует `--busy`. Submit передаёт владение задачей. Это карта для проверки своего кода, не эталонная строка в строку.
