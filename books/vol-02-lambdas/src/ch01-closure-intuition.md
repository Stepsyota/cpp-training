# Глава 1. Замыкание и объект-функция

## Зачем эта тема

Представь, что нужно отсортировать заказы по приоритету, который зависит от **внешней** переменной `boost_vip`: для VIP-заказов вес выше. В C до C++11 ты бы написал функцию `compare_orders` и как-то передала бы `boost_vip` через глобальную переменную или через неудобный `void*` в `qsort`. В C++ долгое время писали **класс-функтор** с полем `boost` и `operator()`. С C++11 тот же смысл укладывается в лямбду рядом с вызовом `sort` — но под капотом это **тот же функтор**, только сгенерированный компилятором и без имени типа в исходнике.

Если не понять эту эквивалентность, лямбда кажется «магией из STL» или «синтаксисом для молодых». На самом деле это **closure (замыкание)**: исполняемый код плюс **захваченное окружение** (поля объекта). Ошибки с `[&]` и висячими ссылками — ошибки **lifetime** захваченных сущностей, а не «лямбда сломалась». Эта глава закладывает модель, на которой держатся захват, `mutable`, generic lambda и передача callables в потоки в следующих главах.

## Callable: что вообще просит алгоритм

Стандартные алгоритмы и многие API принимают не «функцию» абстрактно, а **callable** — сущность, которую можно **вызвать** с аргументами. Это может быть free function, указатель на функцию, объект с `operator()`, `std::function`, результат `bind` (легаси). Компилятор на этапе шаблона подставляет конкретный тип и генерирует вызов.

Лямбда попадает в ту же категорию, что и именованный функтор: у неё есть **тип** (closure type) и **operator()**. Разница только в том, что тип **unnamed** — ты не пишешь его в заголовке, а хранишь через `auto` или передаёшь в `template<typename F>`.

## Объект-функция до лямбды

Классический **function object (объект-функция)** — тип с перегруженным `operator()`:

```cpp
struct ByPriority {
    int boost;
    bool operator()(int a, int b) const {
        return (a + boost) < (b + boost);
    }
};
```

Создаёшь `ByPriority cmp{10};` и передаёшь `cmp` в алгоритм. Компилятор знает **конкретный тип** `ByPriority`; вызов может быть встроен (inline), как у обычной функции с известным адресом.

Плюсы: явное имя типа, можно переиспользовать в заголовке, положить в `.h` как policy class. Минусы: для одноразового сравнения в одной функции писать целый `struct` в namespace — шум и лишний символ в отладчике. Лямбда — компромисс: поведение **локально**, тип **скрыт**, но объект на стеке или в куче всё равно **есть**.

В больших кодовых базах именованные функторы живут годами: `std::less`, custom comparators в контейнерах. Лямбда не вытеснила их — она закрыла нишу **локального** callable.

## Что компилятор делает с лямбдой

Запись

```cpp
int boost = 10;
auto cmp = [boost](int a, int b) { return a + boost < b + boost; };
```

примерно соответствует генерации класса вроде (упрощённо, для понимания):

```cpp
struct __lambda_1 {
    int boost;
    __lambda_1(int b) : boost(b) {}
    bool operator()(int a, int b) const {
        return a + boost < b + boost;
    }
};
auto cmp = __lambda_1{boost};
```

Имя `__lambda_1` выдумано; в реальности оно уникально (часто с номером и именем функции) и не предназначено для набора пальцами. Важно: **`boost` внутри лямбды — поле объекта**, копия или ссылка в зависимости от способа захвата (глава 3). Вызов `cmp(1, 2)` — это `cmp.operator()(1, 2)`.

Отсюда следствия, которые новички упускают:

- У каждой лямбды **свой** тип; две лямбды с одинаковым текстом в **разных** строках — **разные** типы для `decltype` и присваивания.
- Размер объекта зависит от захваченных данных: пустая `[]{}` может быть пустым struct; лямбда с `[big_string]` тянет размер `std::string` в каждый экземпляр closure.
- Лямбду можно передать в шаблон `template<typename F> void run(F f)` — **конкретный closure type**, не «тип лямбды вообще».

## Замыкание в смысле языка

**Closure** — связка **кода** (тело лямбды) и **состояния** (захваченные сущности). В функциональных языках (Lisp, Haskell, JavaScript) это привычная модель; в C++ состояние — поля compiler-generated class. Лямбда без захвата `[]() { return 42; }` всё равно closure type, просто без полей; её можно конвертировать в указатель на функцию **только** в узком случае без capture (глава 2).

Замыкание **не копирует весь стек** функции: захватываешь только то, что перечислил в `[...]` или что попало под default `[=]` / `[&]`. Остальные локальные переменные для лямбды **не существуют** — классическая ошибка: думать, что лямбда «видит всё», как вложенная функция в Python. В C++ видит только захват, static и глобальные имена.

Аналогия: функтор — чемодан с наклейкой `ByPriority`; лямбда — такой же чемодан, но наклейку с именем типа сняли. Содержимое (поля) и замок (`operator()`) те же.

## Где живёт объект closure

Лямбда, присвоенная в `auto f = [...]`, обычно лежит на **стеке** или в регистрах, как локальная переменная. Если положить closure в `std::vector` или передать в очередь задач, объект **копируется** или **move'ится** в кучу вместе с контейнером — захваченные строки и `unique_ptr` едут с ним. Lifetime closure = lifetime **его полей** плюс правила для ссылок (глава 10).

## Лямбда vs указатель на функцию

```cpp
void plain(int x);
void run(void (*fp)(int));
```

Указатель на функцию не хранит состояние: нельзя «захватить boost» без глобальной переменной или `void* user_data` в стиле C. Лямбда с захватом **не** превращается в `void (*)(int)` без потери состояния. Если видишь `.target` у `std::function` или C-style cast — это другой механизм (глава 7).

Для колбэков в C API по-прежнему нужны функции с `void*` контекстом; лямбда с захватом туда напрямую не ляжет без обёртки (static trampoline + heap context — паттерн за рамками тома).

## Лямбда vs `std::function`

`std::function<void(int)>` — **type erasure (стирание типа)**: один именованный тип обёртки, внутри может сидеть лямбда, функтор или free function. Удобно в заголовках публичного API: «принимаю любой callable с такой сигнатурой». Цена: возможная индирекция, аллокация в куче для больших closure, хуже inline на горячем пути.

Не путай: «написал лямбду» ≠ «использую std::function». Лямбда — синтаксис **создания** объекта; `std::function` — **контейнер** для callable. Можно создать лямбду и ни разу не оборачивать в `function`, передавая в шаблон.

## Где лямбды живут в твоём обучении

В `03_oracle` и дальше по треку multithread лямбды появляются как **работа**, которую уносит другой поток или `async`. Там критично, **что** попало в захват: копия `std::string` или ссылка на локальную переменную, которая уже уничтожена к моменту выполнения. Пока достаточно правила: захват по значению живёт **внутри** объекта closure; захват по ссылке — пока жив referent.

В главе 9 вернёмся к потокам без разбора кода пула: только инварианты захвата и join.

## Связь с томом 1

- Keyword **`mutable`** — можно менять поля closure в `const operator()` (глава 5).
- **`auto`** у переменной с лямбдой — вывод closure type (том 1, глава про storage и `auto`).
- **`this`** в захвате `[this]` — указатель на объект, не копия всего `*this` (глава 10).
- **`template`** и generic lambda — главы 6 и фон из тома 1.

## История: зачем C++11 принёс лямбды

До стандарта 2011 года программисты писали функторы или использовали Boost.Lambda / bind — с тяжёлыми ошибками и без единого стиля в стандартной библиотеке. Комитет добавил **lambda expressions** в язык, чтобы алгоритмы STL и новые API (`std::thread`) могли принимать локальную логику без макросов. Синтаксис `[capture](params){}` зафиксировали так, чтобы компилятор **всегда** мог построить closure type — это не runtime feature, а чисто compile-time sugar.

С C++14/17/20 sugar обогатили: init-capture, generic lambda, `constexpr` lambda, `[*this]`, template lambda. Модель «объект с operator()» не менялась — менялась только грамматика списка захвата и параметров.

## ODR-use и «использую ли я переменную в capture»

Компилятор захватывает имена, которые **odr-used** в теле: чтение значения, вызов через имя, присваивание. Если написать лямбду, которая **не** обращается к локальной `x`, `x` не попадёт в closure даже при `[=]`. Это помогает понимать сообщения «variable not captured» и избегать лишних копий: не упоминай лишние имена в теле.

## Конвертация в указатель на функцию (крайний случай)

Лямбда без capture и с телом, совместимым с function pointer, может **implicitly convert** к указателю на function. Это узкий bridge к C API. Как только появился `[x]` — мост рушится. В главе 2 и 7 вернёмся к условиям; здесь достаточно помнить: **state ломает conversion**.

## Практика на Fedora: посмотреть тип closure

Скомпилируй с `-std=c++17` маленький `.cpp` с одной лямбдой и включи `-fdiagnostics-show-template-tree` или просто спровоцируй ошибку шаблона, передав лямбду в `template<typename T> void foo(T)` — в сообщении GCC/Clang часто видно **реальное** имя closure type. Это убеждает, что тип не «void()», а уникальный struct.

## К собесу и code review

Интервьюер часто спрашивает: «Что такое лямбда под капотом?» — ожидают **unnamed class + operator() + members**. «Можно ли присвоить две разные лямбды одной переменной без `std::function`?» — нет, если типы closure различаются. «Чем лямбда отличается от указателя на функцию?» — state. Эти ответы напрямую из модели этой главы.

## Сценарий: логирование с контекстом request id

HTTP-handler знает `request_id` и хочет передать в асинхронный logger callable «дописать строку с id». Функтор `LoggerCtx { string id; void operator()(string msg); }` работает. Лямбда `[id = request_id](std::string msg) { ... }` — то же: **id** — поле closure. Если передать `[&id]` в очередь и handler завершится — id на стеке умрёт. Сценарий повторяется везде, где «локальный контекст + async» — не только в потоках, но и в `post()` event loop.

## Сценарий: тест с mock и expectation

В unit-test часто делают `bool called = false; mock.on_call([&]{ called = true; });` — `[&]` OK, пока mock синхронно вызывает callback в том же тесте. Если mock **отложит** вызов — тест flaky. Capture `called` by reference опасен при deferral; иногда захватывают `std::shared_ptr<bool>` или вызывают sync API в тесте.

## Разбор ментальной модели «функция первого класса»

C++ не имеет функций первого класса в смысле JavaScript: free function не объект. **Closure object** — ближайшая стандартная замена «функция + env». `std::function` — второй слой, value type с polymorphic inside. Цепочка: syntax lambda → concrete closure → optional erasure.

## Чтение assembly (опционально)

На `-O2` вызов closure часто inline'ится в место call — в disassembly не увидишь отдельной «lambda function», только код тела. Это подтверждает модель «объект, не функция ОС».

## Запрет копирования closure

Если capture holder non-copyable, closure may be non-copyable — тогда только move в queue. Init-capture move-only — глава 4.

## Типичные заблуждения

«Лямбда — это функция» — нет, это **временный объект** с `operator()`. «Две одинаковые лямбды — один тип» — нет, если closure types различаются (разный захват или место в коде). «Лямбда всегда быстрее функтора» — одинаково, если сгенерирован эквивалентный код. «Пустые `[]` значит ничего не захватываю» — верно для локальных имён, но тело всё равно может читать globals и вызывать free functions.

## Замыкание и именованные namespace function

Free function `bool cmp(int a,int b)` не может держать `boost` без global. Namespace function + global state — антипattern. Функтор/лямбда инкапсулируют state **в объекте**, который передаётся явно. Это и есть «замыкание» в C++: state не в globals, а рядом с callable.

## Передача в шаблон algorithm

```cpp
template<typename It, typename Cmp>
void my_sort(It b, It e, Cmp cmp);
```

`Cmp` может быть closure type. Алгоритм не знает имя типа — только сигнатуру `operator()`. Это основа generic programming в STL до concepts.

## Книжный вывод главы 1

Прежде чем спорить о `[&]` vs `[=]`, убедись, что ты принимаешь: **лямбда = объект**. Все остальные главы — частные случаи этого утверждения.

## Краткое резюме

Лямбда — синтаксис для unnamed closure type: `operator()` плюс поля захвата. Это та же идея, что класс-функтор, с локальностью в исходнике. Closure связывает код и состояние; без захвата состояния нет. Указатель на функцию state не хранит; `std::function` — отдельная обёртка с erasure. Понимание модели нужно до `[&]` и потоков.
