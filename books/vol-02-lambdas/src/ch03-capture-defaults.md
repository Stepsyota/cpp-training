# Глава 3. Захват по умолчанию: `[=]` и `[&]`

## Зачем эта тема

Квадратные скобки в начале лямбды — не декорация. В них ты решаешь, **какие имена** из окружающей области видимости станут полями closure object и **копией** или **ссылкой** на оригинал. Default capture **`[=]`** и **`[&]`** — shorthand: «захвати всё, что использую в теле, одним правилом». Удобно в маленьких лямбдах на три строки, пока не превращается в ловушку lifetime или неожиданную копию тяжёлого `std::string`.

В треке multithread воркер с `[this]` — осознанный выбор: метод и поля объекта пула. Слепой `[&]` вокруг `std::thread` — классический путь к dangling. Эта глава разбирает правила default и **явного** захвата по имени, смешивание режимов и `this`, чтобы ты читал чужой код и писал свой без «захватил случайно пол-стека».

## Что значит «захватить» имя

Когда тело лямбды обращается к переменной `x` из внешней функции, компилятор должен положить `x` **внутрь** объекта лямбды (копия или ссылка) или отклонить программу, если `x` нельзя захватить. **Глобальные** и **static** переменные захватывать не нужно: к ним доступ и так есть через обыные правила lookup.

После захвата **копией** изменения внутри лямбды (без `mutable` на полях-копиях — см. главу 5) не меняют внешний `x`. После захвата **по ссылке** `&x` тело видит тот же объект; если внешний `x` уничтожен, вызов лямбды — **undefined behavior (UB)**.

Компилятор захватывает только **odr-used** имена: если в теле написали `sizeof(x)` без чтения значения, правила могут отличаться — на практике ориентируйся на «обращался к переменной — она в capture или ошибка».

## `[=]` — default capture by copy

```cpp
void demo() {
    int a = 1;
    std::string s = "hi";
    auto f = [=]() {
        return a + static_cast<int>(s.size());
    };
    // a и s скопированы в closure
}
```

Компилятор захватывает **по значению** каждое используемое имя из тела, не перечисленное явно иначе. Явный список можно смешивать: `[=, &log_stream]` — всё по копии, кроме `log_stream` по ссылке. Обратное: `[&, x]` — default by reference, но `x` — копия.

Копия `std::string` в closure может быть дорогой по памяти и времени. Если лямбда живёт долго (очередь задач, `std::function`), подумай о явном списке, `[&]` только на безопасный lifetime или init-capture с `std::move` (глава 4). На hot path с тысячами задач `[=]` с большой строкой бьёт по аллокатору.

Сценарий: логирование в `for_each` с `[=]` — каждая итерация не создаёт новую лямбду, но **один** объект closure уже содержит копии; если цикл создаёт лямбду заново каждый раз — копии множатся.

## `[&]` — default capture by reference

```cpp
void demo() {
    int total = 0;
    auto add = [&](int n) { total += n; };
    add(1);
    add(2);
    // total == 3
}
```

Все используемые имена — **ссылки** на внешние объекты. Пока `add` вызывается только пока `total` живёт в той же функции — нормально. Передать `add` в поток, который переживёт `demo`, нельзя: ссылка на `total` станет висячей.

Правило для review: **`[&]` в API, которое уходит «наружу»** (return, callback, `std::thread` без join в той же области) — красный флаг, пока не докажешь lifetime письменно в комментарии или тестом.

`[&]` в синхронном алгоритме над локальным контейнером — идиома для аккумулятора (`total`, `found`). Это один из немногих «безопасных по умолчанию» случаев, и то пока callable не утекает.

## Явный захват по имени

```cpp
int key = 42;
auto f = [key](int x) { return x + key; };           // копия key
auto g = [&key](int x) { return x + key; };          // ссылка
```

Явный список читается лучше default в больших лямбдах: видно, что именно тащится в объект. Стиль многих code style guides запрещает default capture в production-коде из-за читаемости и скрытых ссылок.

Дублирование имени в списке запрещено. Захват `key` и `&key` одновременно — ошибка.

## `this` в capture list

```cpp
struct Worker {
    int n = 0;
    void spawn() {
        auto job = [this]() { ++n; };
        job();
    }
};
```

`[this]` захватывает **указатель** на текущий объект, не копию `*this`. Эквивалентно захвату указателя, через который видны поля. Если лямбда переживёт объект `Worker`, инкремент — UB.

**(C++17)** `[*this]` захватывает **копию** объекта — реже, но спасает при async, если объект копируемый и копия осмысленна (не для типов с mutex внутри).

Связь с пулом на уровне идей: воркер часто пишет `[this]`, чтобы звать методы и читать поля пула; ответственность — не уничтожить пул, пока в очереди задачи с `[this]`, и join воркеров до конца жизни объекта.

## Захват членов без `this`

До C++20 нельзя написать `[n]` для поля `n` struct снаружи метода без `this`. Внутри метода `[n]` **(C++20)** или `[this]` / обращение через захваченный `this` — см. стандарт для твоей версии. На C++17 в методе пишут `[this]` и используют `n` как `this->n`.

## Что не захватывается default

Параметры функции не «захватываются» — они видны как параметры вложенной логики только если лямбда объявлена внутри функции и использует их по имени: параметр `foo` в scope, для лямбды это как локальная переменная для правил capture. Имена типов, `constexpr` без odr-use — свои правила. Если тело пустое и ничего не использует, `[]` достаточно.

## Захват `this` и неявный доступ к членам

Внутри метода класса тело лямбды может обращаться к `member` **без** явного `[this]` в C++14+: неявный capture `this` при odr-use члена. Явный `[this]` всё равно предпочтителен в review: сразу видно, что closure привязан к объекту. В static method неявного `this` нет.

## Захват static и consteval контекст

`static int s;` в функции — не захватывается; лямбда использует `s` как static duration. **`constexpr`** переменные в constexpr lambda — отдельные правила C++17; capture constexpr by value может участвовать в compile-time evaluation.

## Производительность: копия vs ссылка

Копия малого `int` дешевле indirection. Копия `std::string` может аллоцировать. Ссылка избегает копии, но тянет aliasing: компилятор хуже оптимизирует, если не доказано, что referent не alias с другими данными. На micro-benchmark разница редко решающая; **correctness lifetime** важнее.

## Антипаттерн: `[&]` в stored callback

GUI и сетевые фреймворки иногда принимают `std::function<void()>`. Записать `[&]() { use(local); }` и положить в очередь событий — классический баг после выхода из handler. Правильно: `[local = std::move(local)]` или захват by value нужных полей.

## Сравнение default capture (в prose)

**`[=]`** — «я беру снимок значений на момент создания лямбды». Хорошо для передачи в другой поток **копий** примитивов и строк. **`[&]`** — «я смотрю на живые объекты снаружи». Хорошо для локального аккумулятора. Смешанный `[=, &out]` — «всё копирую, кроме одного выходного параметра» — частый осознанный паттерн.

## Упражнение для пальцев: предсказать capture list

Функция с локальными `int a`, `std::string b`, static `int c`. Лямбда `[=]{ return a + b.size() + c; }` — захватятся **a** и **b** by value, **c** не захватывается. Лямбда `[&]{ return a; }` — только **a** by ref. Проговори вслух перед компиляцией — привычка для review.

## Default capture в nested scope

Внутренний блок `{ int x; auto L = [&]{ use(x); }; }` — `L` не должен escape блока, если `[&x]`. Если `L` return из блока — UB. Outer function capture другой истории: `L` живёт в outer scope, `x` inner — не compile если inner не visible; если `x` outer — см. lifetime.

## const и capture by value

Захваченная копия `const int n` в init `[n = 5]` — поле const в closure; без mutable не меняется. Default `[=]` копирует текущее value; последующие изменения внешнего `n` не видны внутри, если не `[&n]`.

## Enclosing function lifetime

Lambda stored in local `auto f` dies with function exit unless returned or moved out — capture refs must not outlive unless moved container owns closure.

## Code review phrase

Replace «capture everything [&]» with explicit list in PR comments — teach teammates.

## Типичные заблуждения

«`[=]` значит const» — нет, копии можно менять в `mutable` лямбде. «`[&]` не копирует, значит быстрее» — не всегда; aliasing и инвалидация кэша; главное — lifetime. «Захватил `this`, значит объект не уничтожится» — нет, указатель не продлевает жизнь. «Default capture захватит то, что не использовал» — только odr-used имена.

## Capture и coroutine **(C++20, только ориентир)**

Coroutines в томе 4; здесь одна фраза: lambda capture rules **не** переносятся на coroutine frame автоматически. Не смешивай «co_await в лямбде» и «capture в async thread» — разные механизмы.

## Захват параметров pack **(variadic templates)**

В variadic template function лямбда внутри может захватывать `[&...]` parameter pack через init-capture from tuple — advanced; достаточно знать, что capture list **не** variadic, но init может вызывать fold.

## Резюме для практики multithread

Когда пишешь воркера: спроси «этот callable переживёт ли stack frame?» Если нет — value capture или move. `[this]` — «я привязан к объекту пула». Default `[&]` в submit — почти всегда нет.

## Краткое резюме

`[=]` — default by copy; `[&]` — by reference. Явный список предпочтительнее в больших лямбдах и в коде, который уходит в потоки. `[this]` — указатель на объект; lifetime на тебе. Смешивание `[=, &x]` и `[&, x]` допустимо по правилам стандарта.

## Разбор типичного фрагмента «воркер ждёт работу»

На уровне идей (не эталон): поток крутится в цикле, под mutex проверяет очередь, при пустой очереди и флаге «закрыто» выходит, иначе снимает задачу и **вызывает её вне mutex**. Лямбда `[this]` позволяет телу цикла читать `jobs`, `stopped`, `busy` как поля объекта. Capture **не** заменяет mutex: он только даёт доступ к полям. Если бы воркер захватил `[&jobs]` на локальную переменную очереди внутри функции — это была бы другая, неверная модель. Запомни разделение: **capture = как достучаться до данных**, **mutex = как не гоняться**.

При review своего кода спроси: «Мой capture привязан к объекту с известным lifetime или к stack frame?» Ответ определяет `[this]` vs `[=]` vs init-move.
