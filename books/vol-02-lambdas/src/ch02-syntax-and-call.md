# Глава 2. Синтаксис и вызов

## Зачем эта тема

Лямбда в исходнике выглядит как четыре скобки: **capture**, **parameters**, **mutable/opt**, **body**. Пока синтаксис не разложен по частям, легко перепутать `()` в списке параметров с вызовом, забыть `()` после списка параметров при немедленном вызове или не заметить **trailing return type** и **exception specification**, которые лямбда тоже поддерживает.

Новички часто пишут `[](int x) { return x; }` и ждут, что это «объявление функции» — компилятор же создаёт **выражение**, результат которого — объект. Другая ошибка: сохранить лямбду и вызвать без скобок, как будто это указатель на функцию. Эта глава идёт по грамматике C++17: как **создать** closure object, как **вызвать** его сразу или сохранить, когда тело может быть `constexpr`, и почему пустая лямбда — не «ничего», а объект, часто нулевого размера. После неё захват в главе 3 читается как осознанный выбор, а не как магия в квадратных скобках.

## Четыре части лямбды

Общая форма:

```cpp
[capture](parameters) specifiers -> return_type { body }
```

Части, которые чаще всего пишут на практике:

1. **`[capture]`** — что войдёт в объект (глава 3–4). Может быть пусто `[]`.
2. **`(parameters)`** — как у функции; можно опустить типы с `auto` **(C++14)** в generic lambda (глава 6).
3. **Спецификаторы** — `mutable`, `constexpr` **(C++17)** на `operator()`, `noexcept` (том 1).
4. **`-> T`** — возвращаемый тип, если не выводится; иначе можно опустить.
5. **`{ body }`** — тело.

Пример с явным возвратом и `noexcept`:

```cpp
auto safe_div = [](double a, double b) noexcept -> double {
    return b != 0.0 ? a / b : 0.0;
};
```

Компилятор генерирует `operator()` с соответствующей сигнатурой. Для простых тел return type выводится из `return expr;` как у обычной функции. Если в теле несколько `return` с разными типами, вывод может сломаться — тогда явный `-> common_type` или приведение.

Порядок спецификаторов важен: `mutable` и `constexpr` стоят **между** `)` параметров и телом `{`, не внутри capture list.

## Немедленный вызов (IIFE)

**Immediately invoked lambda expression** — лямбда, которую вызывают в той же строке:

```cpp
int answer = [](int x) { return x + 1; }(41);
```

После закрывающей `}` **тела** (и всего объявления лямбды) идут **аргументы вызова** `(41)`. Это удобно для локальной инициализации сложной константы: создали closure, сразу вызвали, именовать объект не обязательно.

Сценарий: построить lookup-таблицу один раз при входе в функцию, не вынося helper в namespace:

```cpp
const auto& table = [] {
    static std::array<int, 256> t = make_table();
    return t;
}();
```

Здесь IIFE возвращает ссылку на static внутри — паттерн осторожный, но показывает, зачем «вызвать на месте».

Не путай с объявлением переменной:

```cpp
auto f = [](int x) { return x + 1; };  // объект f
auto y = [](int x) { return x + 1; }(1);  // y == 2
```

## Вызов сохранённой лямбды

```cpp
auto inc = [](int& x) { ++x; };
int n = 0;
inc(n);
```

`inc` — объект; `inc(n)` — `inc.operator()(n)`. Если `operator()` объявлен `const` (по умолчанию для лямбды без `mutable`), нельзя менять поля захвата в теле — только `mutable` или захват по ссылке на внешний объект (глава 5).

Передача в алгоритм:

```cpp
std::vector<int> v{3, 1, 2};
std::sort(v.begin(), v.end(), [](int a, int b) { return a > b; });
```

Третий аргумент — **временный** closure object; типичная реализация `sort` принимает компаратор по const reference и вызывает **много раз** — компаратор должен быть дешёвым и не держать висячих ссылок.

## Пустая capture и размер объекта

```cpp
auto noop = [] {};
```

Тело пустое, захвата нет. Тип всё равно уникальный closure type. Размер часто **1** байт (placeholder) или **0** с padding — зависит от ABI и empty base optimization; не полагайся на `sizeof` между компиляторами для переносимости. Для perf-мышления «пустая лямбда дешёвая» — верно.

Пустая лямбда **без захвата** иногда конвертируется в указатель на функцию — только если нет capture и выполнены условия стандарта. На практике редко нужно; если C API просит `void(*)()`, лучше явная free function.

## `constexpr` лямбда (C++17)

Если тело и capture допускают compile-time evaluation, можно пометить:

```cpp
constexpr auto sq = [](int x) { return x * x; };
static_assert(sq(10) == 100);
```

**`constexpr` на `operator()`** расширяет использование в `constexpr` контекстах. Это не делает каждую лямбду constexpr автоматически: захват указателя на runtime-данные — уже нет. Пустая лямбда без capture часто constexpr-friendly.

## Копирование и присваивание closure

Closure object **копируемый**, если все захваченные члены копируемы; **move-constructible** при move-friendly capture. Присваивание лямбд — **C++17**, если поля поддерживают assign.

```cpp
auto a = [x = 1](int y) { return x + y; };
auto b = a;       // копия поля x
```

Init-capture `x = 1` — **(C++14)**; синтаксис разберём в главе 4, здесь важно, что копирование `b` копирует захваченное состояние, а не «ссылку на a».

Две переменные с **разными** лямбда-выражениями в инициализаторе — **несовместимые** типы, даже если текст совпадает.

## Attributes и расширения (кратко)

На closure можно вешать attributes **(C++11)** на `operator()`, как на функцию — например `[[nodiscard]]` на результат вызова через обёртку редко, но `noexcept` — частый спецификатор. **GNU** `__attribute__` на лямбдах — не переносимо; в учебнике опираемся на стандарт.

## Что не является частью лямбды

- **Шаблон** вокруг лямбды — шаблон функции, внутри которой лямбда; сама лямбда не `template` до **C++20** template parameters в `[]`.
- **`decltype`** для типа: `decltype([](int i){ return i; })` — тип closure в unevaluated context; правила сложные (глава 7).

## Ошибки синтаксиса в GCC/Clang

- Забыли `()` у параметров: `[]( int x {` — parse error.
- Поставили `;` между `]` и `(` параметров: `[](int x); {` — неверно.
- Путают init-capture с default capture: `[=x]` неверно; нужно `[x = expr]` **(C++14)**.

Сообщения «no match for call» часто значат: объект не callable или неверные аргументы к `operator()`. «Cannot convert lambda to ...» — неверный контекст (function pointer, несовместимая сигнатура).

## Опущение параметров и возвращаемого типа

Если лямбда не принимает аргументов, скобки **обязательны**: `[]() { }`, не `[] { }` (второе — синтаксическая ошибка в C++). Если не возвращаешь ничего осмысленного, return type — `void`. Если один `return expr`, тип выводится. Пустое тело `{}` — `void`.

Лямбда как argument default в function declaration — не про лямбду как such; но лямбда как **default argument** к параметру функции возможна: capture выполнится при вызове функции, не при объявлении — отдельный corner case для review.

## Лямбда внутри лямбды

Внутренняя лямбда захватывает **свою** внешнюю область: может захватить внешнюю лямбду by reference или захватить поля внешней функции. Типы closure **вложены** концептуально: два уровня unnamed types. Читаемость страдает — при двух уровнях часто выносят именованный функтор.

## Trailing return и decltype(auto)

Когда return type зависит от параметров:

```cpp
auto dedupe = [](auto a, auto b) -> decltype(a) {
    return a < b ? a : b;
};
```

Явный trailing return снимает неоднозначность, если тело использует несколько `return`. **`decltype(auto)`** **(C++14)** в return — редко в лямбдах, но возможно для perfect forwarding внутри generic lambda.

## Сценарий: callback в локальном RAII

```cpp
ScopeGuard on_exit([&] { cleanup(); });
```

Здесь лямбда живёт ровно scope guard; `[&]` безопасен, пока `cleanup` и referents живут до вызова деструктора guard. Паттерн показывает **короткий** lifetime ссылки — противоположность async.

## Связь с томом 1

Спецификатор **`noexcept`** на лямбде — keyword из тома 1; влияет на move в контейнерах, если callable хранится внутри. **`mutable`** — глава 5 тома 2.

## Attribute [[nodiscard]] на результате вызова

Если лямбда возвращает error code, обёртка может помечать `[[nodiscard]]` return type через trailing — редко на anonymous lambda; чаще named alias или function.

## Лямбда в constexpr if контексте

В C++17 `if constexpr` в **function template**, не внутри arbitrary lambda body до C++23 extensions — не путай: lambda body может использовать `if constexpr` **(C++17)** в generic lambda member — работает как в шаблоне.

## Сравнение с указателем на member function

`std::mem_fn` + bind legacy vs `[obj = &o](...) { o->method(); }` — лямбда explicit. Lifetime `obj` pointer — как `[this]`.

## Empty parameter list vs void

`[]()` и `[](void)` — в C++ для lambda `()` достаточно; `(void)` C-style redundant.

## Lambda in unevaluated operand

`decltype`, `sizeof` closure — advanced; для daily code достаточно `auto`.

## Типичные заблуждения

«После `}` тела лямбда уже вызвана» — нет, только если написал `(args)`. «Лямбда без имени не создаёт объект» — создаёт временный. «Return type всегда выводится» — кроме случаев с несколькими `return` разных типов.

## Whitespace and formatting style

Some teams put capture on new line for long lists — readability. Trailing return on new line — Google style vs LLVM; pick one in project.

## Lambda as default member initializer **(C++14+)**

Data member `std::function<void()> cb = [this]{...};` — capture this in class — lifetime of object; dangerous if cb outlives partial construction. Prefer init in constructor body after members ready.

## Краткое резюме

Лямбда: `[capture](params) specs -> ret { body }`. Вызов — `operator()` объекта; IIFE — `(args)` сразу после объявления. Пустой `[]` — всё равно тип. C++17: `constexpr` лямбды, присваивание. Синтаксис отделён от захвата; следующая глава — `[=]` и `[&]`.
