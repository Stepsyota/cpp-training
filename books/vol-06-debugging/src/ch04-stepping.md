# Глава 4. Шагание по коду

## Зачем эта тема

На breakpoint ты «внутри» программы. **Step** заходит в вызовы, **next** перешагивает через них — путаница между ними убивает час на «почему я в libc». **finish** выводит из текущей функции до return.

## Карта решений: step или next

Перед каждым шагом задай вопрос: «мне **нужно** внутри этой функции?» Если вызов — **`std::lock`**, **`notify`**, **`push`**, и ты проверяешь только «доехали ли до следующей строки caller» — **`next`**. Если отладка **тела** твоей lambda или member function — **`step`**. Если случайно зашёл не туда — **`finish`**, не **`next`** десять раз подряд в STL.

Ошибка новичка — **`step`** из **`main`** через весь **`std::thread`** constructor runtime. Поставь break **внутри** worker lambda и **`continue`** до неё — быстрее, чем выstep'ать runtime.

## step (s)

```
(gdb) step
```

Выполнить **одну** строку исходника; если строка — вызов функции, **зайти внутрь**. В лямбде или `std::` вызове можешь углубиться в стандартную библиотеку — **`next`** или **`set print pretty on`** не спасут; используй **`finish`** или **`disable stepping`** в uninteresting code.

## next (n)

```
(gdb) next
```

Выполнить строку, **не заходя** в вызываемые функции (over-step). Для «вызвали `submit` — что дальше в caller» — `next`.

## finish

```
(gdb) finish
```

Бежать, пока текущая функция не вернётся. Быстрый выход из `vector::_M_push_back` после случайного `step`.

## until

```
(gdb) until 50
```

Бежать до строки 50 в текущем файле (без гарантии при циклах). Реже `next` в цикле for.

## stepi / nexti

Шаг по **ассемблерным** инструкциям — когда исходник врёт из-за `-O2` (глава 13).

## Шагание и потоки

Пока ты делаешь `next` в потоке A, поток B может взять mutex и изменить очередь.

Если нужно «как будто один поток» — на **короткий** участок **`set scheduler-locking step`** (глава 7), посмотрел locals — **`set scheduler-locking off`**, иначе привыкнешь к невозможному миру. Не сдавай упражнение, проверенное только с locking: **`check.sh`** без GDB — финал. Симптом: «только что `empty()` было false, а теперь true». Это не обязательно баг отладчика — **конкуренция**. Иногда помогает остановить все потоки (`set scheduler-locking on` в GDB — все threads не run пока один step; меняет поведение, только для локального анализа).

## Связь с упражнениями

В `04_elevator` шагай по предикату в `wait`: зашёл ли в wait, сработал ли notify. В `03_oracle` — не углубляйся в `async` internals без нужды; `finish` из runtime.

## Типичные заблуждения

«step и next одно и то же» — нет. «finish завершит программу» — только текущую функцию. «шагание безопасно для гонок» — меняет тайминг.

## Краткое резюме

`s` внутрь, `n` через вызов, `finish` до return. Осторожно в STL и в threads. Дальше — print и locals.

## Когда step уводит в libstdc++

Вызов **`push`**, **`lock`**, **`notify_one`** — один **`step`** может зайти в заголовок STL. Не паникуй: **`finish`** до return в **твой** frame, или **`disable`** stepping внутрь через **`skip -gfi`** (новые GDB) / **`set step-mode on`** off. Практичный приём: **`next`** на строке с вызовом, если inside STL не нужен.

## until и циклы

**`until 40`** бежит до line 40 **в текущем frame**; если цикл между текущей и 40-й строкой — можешь крутиться долго. **`while`** без тела в исходнике (оптимизация) — until врёт. На **`-O0`** until предсказуемее.

## stepi / nexti

Когда исходник «прыгает» между строками на **`-O2`**, **`stepi`** показывает инструкции. Связь с главой 13. Для C++17 курса на Debug stepi почти не нужен.

## scheduler-locking подробнее

**`set scheduler-locking on`** — только текущий thread run при continue/step. **`step`** — только при step. **`off`** — default. Помни: включил locking — **изменил** repro гонки; это инструмент **понимания**, не верификации.

## Сценарий: oracle и async

Не step’ай через entire **`std::async`** runtime. Поставь break **после** `.get()` или на lambda body **в твоём** файле. **`finish`** из внутренностей thread launch — быстрый выход.

## Сценарий: parallel map

**`08`**: break на границе куска (твоя формула индексов). **`print begin, end`**. **`next`** по присвоению в **`out`**. Если кусок пустой — edge case из README. Step по всем потокам сразу GDB не делает — переключай **`thread`**.

## Ошибка: думать, что next «атомарен»

**`next`** over call всё равно **выполняет** call atomically с точки зрения текущего thread; другие threads в это время **могут** работать. «Я на одной строке» ≠ «мир стоит».

## Резюме шагов для hang

Не step'ай бесконечно в **`wait`**: Ctrl+C → **`thread apply all bt`**. Step — когда программа **прогрессирует**, но не туда.

## reverse-next (упоминание)

**record full** / reverse debugging — GDB feature, overhead huge; не для multithread курса. Знай границу возможностей.

## return value finish

После **`finish`**, **`print $`** — иногда результат функции (ABI dependent). Редко нужно в курсе.

## step через macro

Макросы без `-g3` expand weirdly. В multithread макросов мало.

## stepping в destructor

**`~ThreadPool`** — step показывает порядок join. Ошибка join order видна **до** terminate.

## coordination с continue

После inspect на breakpoint **`continue`** до следующего hit — типичный цикл; **`next`** line-by-line только на подозрительном участке.

## visual: один thread stepped

Нарисуй на бумаге: thread A on step, B runs — поле **`size`** меняется. Привыкай к diagram (том 3) + GDB snapshot.

## advance (clang gdb)

Some builds alias; stick to **`next`/`step`** from book.

## skip file

**`skip file libstdc++`** — GDB 8+ skip stepping in file; спасение от STL.

## count loop iterations

Manual: **`display i`**, **`continue`**, watch **`i`** grow — без changing code.

## step into your lambda only

Break on `{` line inside lambda body in your `.cpp` — clearer than stepping from **`std::thread`** ctor site.

## Дополнительный сценарий: «застрял в STL»

Ты нажал **`step`** на строке с **`jobs.push(...)`** или **`lock_guard`**, и оказался внутри libstdc++. Не трать время на чтение чужого кода: **`finish`**, пока frame не вернётся в твой `.cpp`, или **`disable`** breakpoint внутри STL через **`skip file`**. Альтернатива — поставить breakpoint **после** вызова и использовать только **`next`** на call line. Запиши себе правило: «в multithread advanced я не step'аю в STL без причины».

## Шагание и condition_variable

На **`wait`** **`next`** не «перешагивает ожидание» мгновенно — поток блокируется, GDB ждёт wakeup. Это нормально: либо другой поток должен **`continue`**, либо прерви и смотри **`all bt`**. Путаница «next завис» часто означает, что ты **на блокирующем** вызове, а не что GDB сломался.

## Практическое закрепление (5–10 минут)

Открой Debug-сборку любого **зелёного** target из `multithread/build/`. Запусти GDB, поставь **`break main`**, **`run`**, выполни **`next`** пять раз, **`bt`**, **`info locals`**, **`quit`**. Повтори на другом target — muscle memory важнее заучивания глав. Если что-то не совпало с текстом главы, проверь cwd и путь к exe: nine из десяти «GDB сломан» — неверный путь или сборка без **`-g`**.

## Связь с главой тома 3 без спойлера кода

Вернись мысленно к инварианту упражнения, которое отлаживаешь: что должно быть истинно перед выходом из **`wait`**, когда очередь считается пустой, когда **`submit`** должен молчать. GDB показывает **момент**, когда инвариант уже нарушен или ещё не достигнут. Исправление остаётся в голове и в **`task.cpp`**, не в команде **`continue`**.
