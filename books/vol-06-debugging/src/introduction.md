# Введение

**Том 5** серии «Cpp Training» разобрал цепочку сборки на Fedora: от исходника до бинарника, флаги **`-std=c++17`**, предупреждения, различие **Debug** и **Release**, и главное для нас — зачем в учебной сборке нужен **`-g`**. Символы отладки не делают программу «медленнее по смыслу», они оставляют в ELF-файле карту: какой адрес инструкции соответствует какой строке в `task.cpp`, как называется локальная переменная, где лежит параметр функции. Без этой карты **GDB** (GNU Debugger) видит только память и регистры — отладка превращается в угадайку.

**Том 6** отвечает на следующий вопрос: бинарник уже собран с `-g`, тест красный или «висит», поведение не сходится с ожиданием — **что делать руками**, без бесконечного `std::cout` в каждой ветке. Мы учимся останавливать процесс на строке, шагать по коду, смотреть значения, читать **backtrace** (цепочку вызовов), переключаться между **потоками** и разбирать **зависания**, которые в треке `multithread/` встречаются чаще, чем классический segfault. Это тот же инструментарий, который на собеседовании спрашивают в формулировке «как отладите deadlock в production».

Эталон среды — **GDB** из пакета `gdb` на Fedora (`sudo dnf install gdb gcc-c++`). Команды в книге приведены для интерактивного сеанса `(gdb)`; сокращения (`r`, `n`, `bt`) совпадают с тем, что используют опытные разработчики. Параллельно мы кратко затронем **cgdb** — текстовую оболочку с панелью исходника поверх GDB, удобную в SSH и на ноутбуке без тяжёлой IDE — и запуск **того же GDB** из Cursor или VS Code через тип конфигурации **`cppdbg`** и файл `launch.json`. Под капотом на Linux это по-прежнему GDB по протоколу MI; разница только в том, ставишь ли breakpoint мышкой или командой `break`.

Важная граница: отладчик **не заменяет** санитайзеры. **Data race** — когда два потока трогают одну память без синхронизации и хотя бы один пишет — GDB часто **не покажет** как «гонку»: потоки могут по очереди пройти через ваш breakpoint, и картина будет выглядеть правдоподобно. Для доказательства гонки и многих видов **undefined behavior (UB)** в серии есть **том 7** (AddressSanitizer, UndefinedBehaviorSanitizer, **ThreadSanitizer**). Том 6 дополняет том 7: логика «почему счётчик неверный», «почему main не выходит из `wait`», «кто держит mutex», post-mortem **core dump**, когда процесс уже упал без терминала под рукой.

Практикуй на своих **зелёных** сборках упражнений `multithread/beginner` и `multithread/advanced`, на Debug-таргетах из `cmake --build build`. Для экспериментов с намеренно сломанным кодом заводи **копию** в отдельной ветке или папке — так ты не испортишь сданную работу. Эталоны в `multithread/solutions/` в этой книге **не процитируем**: мы говорим о паттернах (пул, bounded queue, parallel map), о типичных ошибках из `multithread/THEORY.md` и тома 3, но не подставляем готовые реализации.

Стиль тома — **связные абзацы**, как в эталонном томе 1: мало «голых» списков в середине главы, больше сценариев и мотивации. Идентификаторы C++ и команд GDB — **английские**; пояснения — по-русски. Код в примерах короткий; длинные фрагменты из репозитория лучше открыть в редакторе параллельно с Kindle.

В конце **каждой** главы — блок **«Вопросы для самопроверки»**, строка для чата с репетитором (**«Обсуждение с репетитором»** с указанием тома, номера главы и имени файла) и ссылка **«Дальше по курсу»**. Репетитор упражнений и автор книги по договорённости серии — разные чаты: здесь можно спросить «объясни ещё раз `thread apply all bt`», но не просить написать за тебя `task.cpp`.

## Соглашения в тексте

Команды GDB в **`моноширинном`** виде; приглашение **`(gdb)`** опускаем, если ясно из контекста. Пути вида **`multithread/build/`** — относительно корня репозитория **`training`**. Имена targets (**`06_thread_pool`**, **`04_elevator`**) совпадают с CMake; номера **`01`–`08`** — порядок **`check.sh`**, не номера глав книги.

**Оглавление:** четырнадцать глав — от мышления отладчика и первого сеанса GDB до breakpoints, шагания, данных, стека, потоков, зависаний, core, cgdb, IDE, pretty-print STL, отладки под **`-O2`**, и финального резюме с мифами и мостом к том 7.

## Карта глав тома 6

Первые две главы — мышление и **`run`**. Третья–пятая — breakpoints, шагание, **`print`**. Шестая — **`backtrace`**. Седьмая–восьмая — потоки и зависания (сердце связи с `multithread/`). Девятая — **core**. Десятая–одиннадцатая — **cgdb** и IDE. Двенадцатая–тринадцатая — STL в GDB и **`-O2`**. Четырнадцатая — итог и мост к **тому 7**. Можно читать линейно; для hang после advanced сразу допустим jump к главам 7–8, затем возврат к главам 3–5.

## Требования к окружению

Рабочая установка **mdbook** для сборки EPUB описана в **`books/README.md`**. Для отладки упражнений достаточно **gdb**, Debug-бинарников из CMake и терминала. Kindle-чтение не требует GDB на самом Kindle — только на машине, где ты собираешь **`training`**.

Предполагается, что ты уже прошёл или параллельно читаешь **том 3** (mutex, cv, atomics) и собирал **`multithread/`** с **`-pthread`**. Том 6 не учит «что такое mutex» с нуля — он учит **увидеть** mutex в **`backtrace`**, когда тест не выходит из ожидания. Если terminology плавает, открой **`multithread/THEORY.md`** и вернись к соответствующей главе tom 3, затем продолжай GDB.

## Как читать том на Kindle

Главы длинные для узкого экрана, но абзацы короткие. Команды GDB лучше **прогонять на машине** параллельно: один абзац — одна команда в терминале. Не обязательно проходить все четырнадцать глав перед практикой: после глав 2–3 открой свой зелёный **`02_ticket_office`**, после глав 7–8 — любой advanced, где уже был hang в прошлом.

## Связь с AGENTS.md и репетитором

Корневой **`AGENTS.md`** запрещает репетитору подсовывать готовый код, пока ты не просишь проверку. Этот том даёт **теорию инструмента** — репетитор может сказать «сними `thread apply all bt` и принеси вывод», не раскрывая эталон. Строка **«Обсуждение с репетитором»** в конце глав — готовый заголовок чата.

## Что не входит в том

Reverse debugging, eBPF probes, rr, Windows WinDbg, remote gdbserver на embedded — за scope. **MSVC** debugger — другой UI; на Fedora фокус на GDB. **Kernel** debugging — нет.
