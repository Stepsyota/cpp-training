# Глава 2. Первый сеанс GDB

## Зачем эта тема

Пока не отработан цикл **запустил → дождались события → посмотрели → вышли**, GDB кажется чатом с приглашением `(gdb)`, где «ничего не понятно». На самом деле первый сеанс — это десять минут: указать путь к бинарнику, один раз **`run`**, при необходимости **`list`**, и **`quit`**. Все breakpoints и потоки — позже; без уверенного **`run`**/`**quit** ты будешь бояться «зависшего» терминала.

В треке `multithread/` каждое упражнение — отдельный executable в `build/`. Ты уже собираешь их через CMake (том 5). Отладчик **не вызывает** компилятор: после правки `task.cpp` нужен **`cmake --build`** в другом окне или **preLaunchTask** в IDE (глава 11). GDB лишь запускает **уже собранный** файл.

## Установка и версия на Fedora

Пакет **`gdb`** тянет минимально необходимое; для C++ полезен **`gcc-c++`** (символы libstdc++). Проверка:

```bash
gdb --version
which gdb
```

Обычно **`/usr/bin/gdb`**. В книге команды для **CLI**; cgdb (глава 10) и IDE вызывают тот же бинарник. Если версия старее дистрибутива — редко ломает базовые команды; для MI в IDE иногда важен match с расширением C++.

## Приглашение (gdb) и echo

GDB не печатает твой **`std::cout`** отдельно — stdout inferior смешивается с терминалом. Если вывод теста «тонет», перенаправь лог (**`run > log.txt`**) или смотри только код возврата. **`set pagination off`** — must-have в `.gdbinit` для длинных **`thread apply all bt`**.

## Запуск: путь к программе

Из каталога, где лежит exe:

```bash
cd /home/you/training/multithread/build
gdb ./02_ticket_office
```

GDB загружает символы и показывает приглашение `(gdb)`. Программа **ещё не бежит** — только загружена в адресное пространство inferior. Первый старт:

```
(gdb) run
```

Сокращение **`r`**. Для зелёного beginner-теста программа отработает до конца и GDB напишет что-то вроде «exited normally» — это успех: ты доказал, что символы есть и exe запускается под отладчиком.

Если забыл собрать Debug — всё равно может работать, но **`list`** и breakpoints хуже; вернись к **`CMAKE_BUILD_TYPE=Debug`**.

## Аргументы командной строки

Тесты репозитория часто без argv; advanced может принимать. Два способа:

```bash
gdb --args ./build/08_archive arg1 arg2
```

Флаг **`--args`** говорит: всё после него — argv для inferior. Внутри сеанса:

```
(gdb) run arg1 arg2
```

Повторный **`run`** снова передаёт те же аргументы, если не указать новые. Переменные окружения задают **`set env VAR value`** перед **`run`**.

## Останов, kill и выход

**Ctrl+C** в терминале с GDB прерывает **работающий** inferior (не всегда мгновенно, если поток в syscall). Полезно, когда тест «висит» — ты получишь `(gdb)` и сможешь **`thread apply all bt`** (глава 8).

**`kill`** убивает inferior без выхода из GDB — чистый перезапуск с **`run`**. **`quit`** (**`q`**) выходит; если процесс жив, GDB спросит подтверждение. Не путай **Ctrl+C** (прервать inferior) с **Ctrl+D** (EOF, иногда выход).

После изменения исходника:

```
(gdb) run
```

GDB **не** пересобирает. Привычка: терминал 1 — `cmake --build build --target ...`, терминал 2 — GDB.

## Где мы в коде: list

```
(gdb) list
```

Показывает окно исходника вокруг текущей позиции (до **`run`** — часто `main`). **`list main`**, **`list file.cpp:25`**, **`list +`** / **`list -`** листать вперёд-назад. Если GDB пишет «No source» — нет `-g` или неверный путь к исходнику.

**`info sources`** — какие файлы известны; редко нужно в курсе, но спасает, когда breakpoint «не там».

## Повторный run и состояние

**`run`** после первого прогона спрашивает «Run from start?» — **`y`**. Breakpoints (когда появятся) сохраняются; watchpoints тоже. Глобальные переменные процесса **сбрасываются** — новый процесс с нуля. Для воспроизведения гонки это важно: каждый **`run`** — новый шанс на другой interleaving.

## attach к живому процессу

**`gdb -p PID`** — прицепиться к уже работающему процессу. Нужны права (часто тот же user). В учебных exe проще **`run`** с нуля. attach полезен в production; для `check.sh` — избыточен.

## TUI в чистом GDB

**Ctrl+X A** переключает **TUI** — split с исходником, если терминал поддерживает. На узком экране Kindle-ноута не всегда удобно; альтернатива — **cgdb** (глава 10). Команды те же; меняется только отображение.

## Сценарий: oracle под GDB

Упражнение **`03_oracle`** — async и future (том 4). Минимальный сеанс без спойлера логики:

1. Debug-сборка target **`03_oracle`**.
2. `gdb ./build/03_oracle`
3. `break main` — breakpoint появится в главе 3; пока можно просто **`run`** и убедиться, что тест проходит.
4. При падении — **`bt`** (глава 6).

Ты не «отлаживаешь async» магией — ты смотришь **свой** код в `task.cpp` в момент остановки.

## Связь с CMake и путями

`workspaceFolder` в IDE может быть `training` или `training/multithread`. GDB не знает CMake — только строка пути к exe. Если **`run`** пишет «No such file» — проверь cwd: **`pwd`** в GDB, **`cd`** в `(gdb) cd` не меняет каталог shell, но **`set cwd`** / запуск из правильной папки при старте gdb решает относительные пути к данным теста.

## § К собесу

Спросят: как передать аргументы, чем **`run`** отличается от запуска `./a.out` в shell (надстройка: signals, breakpoints, controlled restart). Знай термин **inferior** — отлаживаемая программа.

## Типичные заблуждения

«**gdb** сам найдёт exe в PATH» — нет, путь явный. «**run** пересобирает» — нет. «**quit** оставит процесс в фоне» — обычно нет, но **`&`** и detach — отдельная история. «Нужен root для своего бинарника» — нет.

## Краткое резюме

`gdb ./binary`, **`run`**, argv через **`--args`** или **`run ...`**. Пересборка снаружи. **`list`** для контекста, **Ctrl+C** при hang, **`quit`** для выхода. Дальше — breakpoints.

## Переменные GDB и .gdbinit

**`show args`** — какие argv увидит следующий **`run`**. **`set args`**. **`show environment`**. Для повторяющихся упражнений положи в **`~/.gdbinit`**:

```
set print pretty on
set pagination off
```

**`pagination off`** — длинный **`bt`** не ждёт «Press return». Не клади в `.gdbinit` команды с побочными эффектами (`run` при старте) — сломаешь attach-сценарии.

## Запуск из корня репозитория

Если cwd — `training/`, путь к exe **`multithread/build/02_ticket_office`**. Ошибка «file not found» часто из‑за cwd, не из‑за GDB. В IDE **`cwd`** в launch.json задаёт рабочий каталог для inferior — важно для тестов, читающих файлы рядом (в multithread обычно не критично).

## Сигналы и run

По умолчанию GDB ловит некоторые сигналы и останавливает inferior. **SIGSEGV** — останов, можно **`bt`**. Для учебного assert → **SIGABRT** — аналогично. **`handle SIGPIPE nostop`** — продвинутое; в курсе не требуется. Знай, что **`run`** после сигнала снова стартует **с нуля**.

## Несколько терминалов — рабочий паттерн

Терминал A: `watch -n0.5 'ps -L -p $(pgrep -n ticket)'` — редко нужно. Обычно достаточно A = build, B = gdb. Не запускай два GDB на один inferior.

## Разбор «Exited normally» vs код возврата

**`run`** завершился — GDB показывает код. Если тест внутри exe возвращает non-zero, shell после gdb тоже; внутри GDB смотри **`echo $?`** в shell после **`quit`** или **`info proc`** — для курса достаточно вывода тестового framework в stdout.

## Связь с check.sh

**`check.sh`** гоняет все targets подряд. Отладка — **один** target. Собери только нужный: `cmake --build build --target 06_thread_pool` — экономит время цикл «правка → run».

## § Дополнительно: batch и non-interactive

**`gdb -batch -ex run -ex bt --args ./exe`** — для скриптов CI не заменяет тест, но для воспроизведения crash в лог — полезно. Интерактив учи сначала; batch — потом.

## history и повтор команд

**Ctrl+R** в shell ищет bash history; в GDB **`show commands`** для breakpoint commands. Сам GDB на Fedora может читать **`~/.gdb_history`** — удобно для повторяющихся **`break file:line`**.

## directory command

Если исходник переехал, **`directory /path/to/src`** подсказывает GDB, где искать файлы для **`list`**. Для `multithread` пути стабильны — редко нужно.

## shell escape

**`shell cmake --build build --target 02_ticket_office`** из GDB — ленивый способ не переключать tmux pane. Осторожно: долгая сборка блокирует GDB UI.

## start / starti

**`start`** — run до `main` и stop. **`starti`** — до первой инструкции. Для C++ с static init иногда **`start`** удобнее, чем break на main вручную.

## Многократный run и flakiness

Если баг flaky, **`run`** 20 раз подряд в GDB утомителен. Напиши shell loop с **`gdb -batch`** или вернись к sanitizer. GDB не обязан ловить 1/1000 без условий.

## Работа рядом с clangd

clangd (том 5) показывает типы статически; GDB — runtime values. Расхождение «clangd думает int, print показывает мусор» → UB или неинициализированность (UBSan, tom 7).

## readline и editing

Стрелки в `(gdb)` — history команд. **`set editing on`**. Tab completion on symbols sometimes works after **`run`**.

## logging output

**`set logging on`**, **`set logging file gdb.log`** — сохранить сессию для репетитора. **`set logging redirect on`** — только файл, не экран.

## exec-wrapper

**`set exec-wrapper env LD_PRELOAD=...`** — advanced; не трогай в multithread без tom 7 context.

## confirm off

**`set confirm off`** — quit/run без вопросов; осторожно, удобно для скриптов.

## Практическое закрепление (5–10 минут)

Открой Debug-сборку любого **зелёного** target из `multithread/build/`. Запусти GDB, поставь **`break main`**, **`run`**, выполни **`next`** пять раз, **`bt`**, **`info locals`**, **`quit`**. Повтори на другом target — muscle memory важнее заучивания глав. Если что-то не совпало с текстом главы, проверь cwd и путь к exe: nine из десяти «GDB сломан» — неверный путь или сборка без **`-g`**.

## Связь с главой тома 3 без спойлера кода

Вернись мысленно к инварианту упражнения, которое отлаживаешь: что должно быть истинно перед выходом из **`wait`**, когда очередь считается пустой, когда **`submit`** должен молчать. GDB показывает **момент**, когда инвариант уже нарушен или ещё не достигнут. Исправление остаётся в голове и в **`task.cpp`**, не в команде **`continue`**.
