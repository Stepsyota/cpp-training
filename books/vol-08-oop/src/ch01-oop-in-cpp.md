# Глава 1. ООП в C++

## Зачем эта тема

Если спросить десять программистов, что такое «ООП», ты услышишь десять пересекающихся ответов: классы, наследование, полиморфизм, инкапсуляция, сообщения между объектами, UML-диаграммы, паттерны из книги GoF. В **Java** или **C#** картина ещё и подкреплена runtime: почти всё — ссылка на объект в куче, базовый тип `Object`, reflection. В **C++** картина другая: язык **мультипарадигменный**. Ты уже писал многопоточный код с `mutex` внутри класса, лямбды без единого «корня Object», и `parallel_map` как шаблон — это тоже C++, и это не «анти-ООП».

Том 8 для тебя — место, где разрозненные куски (class, virtual, RAII из тома 1, границы пула из тома 3) складываются в **осознанный дизайн**. Не чтобы нарисовать иерархию из пяти уровней, а чтобы отвечать на вопросы: **кто владеет данными**, **кто гарантирует инвариант**, **где граница изменений** при новой фиче. SOLID в конце тома — не абстрактная мораль, а язык для code review, который станет понятнее после этой главы.

## Что значит «объект» в C++

В повседневной речи «объект» часто означает «экземпляр класса в куче по указателю». В стандарте C++ объект — **область хранения** с типом и lifetime. Твой `int n` на стеке — объект. Элемент `std::vector<std::string>` — объект. Временный результат выражения — объект с ограниченным lifetime.

**Класс** и **struct** описывают тип: как устроена память, какие операции допустимы. Когда ты пишешь `Counter c;`, создаётся объект типа `Counter`. Его **копирование**, **перемещение** и **уничтожение** — не детали «ниже пояса», а часть публичного контракта (том 1, special members). ООП в C++ начинается с мысли: **тип = инвариант + операции**, а не с обязательного `new` и `virtual`.

Пример агрегата без «магии»:

```cpp
struct Point {
    int x{0};
    int y{0};
};

Point p{3, 4};
Point q = p;  // копия; оба объекта независимы
```

Здесь нет наследования и нет полиморфизма — но это полноценное «объектное» мышление: данные и тип связаны, компилятор проверяет операции.

## class и struct — не «просто синтаксис»

Единственное **языковое** различие по умолчанию: у `struct` члены **public**, у `class` — **private**. Идиома сообщества:

- **struct** — когда тип в основном **набор полей** с прозрачной семантикой (`Point`, `Color`, параметры запроса).
- **class** — когда есть **скрытое состояние** и клиент обязан вызывать методы, чтобы не сломать правило (`BoundedQueue` с `cap_` и mutex внутри).

Это не закон компилятора, а **сигнал читателю**. Очередь с инвариантом «длина не превышает cap_, все доступы под mutex» оформляют как `class`, даже если технически можно было бы оставить public поля — и сразу потерять гарантию.

## C++ — не Java

Краткий список отличий, который спасает от ложных ожиданий:

**Нет единого корня.** В Java почти всё наследует `Object`. В C++ нет обязательного базового класса для всех типов. Полиморфизм включают **осознанно** через `virtual`, а не «по умолчанию для всего».

**Значения, а не только ссылки.** `std::string`, `std::vector`, твой `struct` — часто хранятся **по значению**. Копия дорогая? — move **(C++11)**, `unique_ptr`, ссылки. Модель «всё в куче по указателю» — не дефолт C++.

**Шаблоны и constexpr** — отдельная ось абстракции. `parallel_map` не обязан быть иерархией `MapperBase` / `MapperDerived`; он может быть шаблоном на `F`. Это не «отказ от ООП», а выбор инструмента.

**Алгоритмы и свободные функции.** `std::sort(v.begin(), v.end(), cmp)` — идиома STL. Метод `v.sort()` для vector есть, но общий стиль — **алгоритм + итераторы + callable** (том 2). ООП не требует засовывать каждую операцию в метод класса.

**Множественное наследование** классов разрешено. Используют редко, но это часть языка; «интерфейсы» часто моделируют абстрактным классом с чистыми virtual (глава 4).

## ООП как граница в multithread

Ты уже делал **ThreadPool** и **BoundedQueue** (идея, не разбор эталона). Там ООП — не «нарисовать BaseThreadPool», а **спрятать протокол**:

- очередь не торчит наружу без замка;
- `submit` и воркер согласованы через один mutex и `condition_variable`;
- деструктор пула не оставляет joinable `std::thread`.

Это **инкапсуляция инварианта** в многопоточной среде. Том 3 учил **как** синхронизировать; том 8 учит **почему** не размазывать mutex по всему проекту, а держать внутри типа с узким API.

Аналогия: класс — **сейф с правилами**. Клиент нажимает кнопки `push` / `pop` / `submit`; не лезет руками в `deque` и не держит `mutex` снаружи «для ускорения».

## Процедурный код vs объекты — ложный конфликт

Хороший C++ проект смешивает:

- **функции** для чистых преобразований (`normalize`, `parse_int`);
- **классы** для состояния и инвариантов (`Connection`, `Journal`, `ThreadPool`);
- **namespace** для группировки без состояния.

Ошибка новичка — «переписать всё в классы `Utils::...` со static методами». Static method bag — часто маскировка namespace с лишним ceremony. Ошибка другого края — «всё в `main` на 500 строк» — нет границ, нет тестируемых единиц, SRP нарушен (глава 9).

## Зачем SOLID именно после инструментов

**S**ingle responsibility бессмысленно обсуждать, если ты не видишь, как **гонка** ломает инвариант. **L**iskov substitution — если не понимаешь **virtual** и slicing. **D**ependency inversion — если не отличал **конкретный** `SqliteDatabase` от интерфейса хранения.

Порядок серии 0–8 не случайен: сначала язык и concurrency, потом gdb и TSan, потом «как резать классы». Ты читаешь том 8 **медленно**, с паузами: после каждой главы SOLID попробуй назвать одно место в **своём** (не эталонном) коде курса, куда принцип aplicable.

## Мини-сценарий: первый рефакторинг в голове

Допустим, в одном файле смешаны: чтение конфига, запуск потоков, вывод в консоль. Тесты тяжёлые, любая правка формата лога ломает запуск потоков. Это не «плохой C++», это **смешанные причины для изменения** (намёк на SRP). Разделение на `load_config()`, `WorkerPool`, `Logger` — уже ООП-дизайн, даже без единого `virtual`.

## Value semantics как «объектность» C++

Многие типы в твоём коде — **values**: копируешь или move'ишь, объект живёт в стеке или внутри vector. `std::thread` — **move-only**; `mutex` — не копируется. ООП в C++ — это не только указатели на базовый класс. Когда выбираешь «класс или struct с полями» vs «иерархия Shape*», спроси: **нужен ли runtime выбор типа** или достаточно шаблона/variant?

## Сценарий: «переписали на классы, стало хуже»

Команда обернула каждую free function в `class StaticHelper { public: static int add(int,a,int b); };`. Поведение то же, тесты те же, но навигация по проекту **тяжелее** — ложное ООП. Правило большого пальца: **состояние + инвариант** → class; **чистое преобразование** → function в namespace.

«Чем C++ ООП отличается от Java?» — value semantics, нет Object root, RAII, multiple inheritance, templates. «Что такое инкапсуляция?» — инвариант, не private ради private. Эти ответы открывают главы 2–7.

## Абстракция без class

Namespace `math` с `double hypot(double x, double y);` — абстракция **операции**, не объекта. Файловая система ОС — объекты для C, но в твоём коде `fopen`/`fclose` — процедурный RAII через `std::fstream`. ООП в C++ — **спектр**: от POD struct до polymorphic hierarchy. Не стыдись free functions там, где нет инварианта состояния.

## Данные и поведение вместе

Класс `BankAccount` с `withdraw` **рядом** с `balance_` — изменение правила овердрафта в **одном** месте. Anemic `BankAccount { double balance; }` + `BankService::withdraw` — два файла, риск рассинхрона. Не догма «всё в class», но **поведение, защищающее инвариант**, логично жить у данных (глава 2).

## Типичные заблуждения

«ООП = наследование и override» — наследование **один** инструмент; композиция часто уместнее (глава 6).

«Без virtual не ООП» — инкапсуляция и RAII — ядро C++ ООП.

«C++ ООП устарело, пишут только functional» — в индустрии по-прежнему классы, интерфейсы, RAII; плюс лямбды и алгоритмы.

«Публичные поля проще» — ломают инвариант и многопоточность.

«ООП против многопоточности» — наоборот, mutex внутри класса **выражает** инвариант.

## Краткое резюме

В C++ объект — значение с типом и lifetime. `class` / `struct` — сигнал инкапсуляции. Язык не Java: value semantics, шаблоны, free functions — норма. Твой пул и очередь — ООП как граница sync. SOLID дальше опирается на virtual, lifetime и опыт томов 3–7. Читай том 8 как практикум мышления, не как список определений.
