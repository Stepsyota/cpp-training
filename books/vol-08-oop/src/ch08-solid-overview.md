# Глава 8. Обзор SOLID

## Зачем эта тема

**SOLID** — пять принципов, которые в индустрии называют при code review, на собеседованиях и в статьях про «чистую архитектуру». Они **не** часть стандарта C++ и **не** компилируются. Это **критерии качества** модульных границ: кто за что отвечает, как расширять систему, что значит «подтип», как не раздувать интерфейсы, от чего зависит высокоуровневый код.

Ты указал ООП как слабое место — SOLID часто звучит абстрактно, пока не привязать к **конкретным файлам**. Дальше пять глав — по одному принципу с примерами «плохо / лучше», связью с `multithread/` и мини-упражнениями для головы. Эта глава — карта и **как читать** остальное.

## История и ожидания

Роберт Мартин (Uncle Bob) и сообщество сформулировали акроним для **объектно-ориентированного** дизайна. В C++ принципы переносятся на **классы, namespace, free functions, шаблоны**. «Модуль» в SRP — не только class: это может быть `.cpp` файл, namespace, функция.

SOLID **не** требует:

- десятков интерфейсов на три строки кода;
- virtual на каждом углу;
- отказа от `struct` и шаблонов.

SOLID **требует** думать перед тем, как разрастётся код.

## Пять букв — развёрнуто

**S — Single Responsibility Principle (единственная ответственность).**  
У модуля должна быть **одна причина для изменения**. Не «одна функция», а «один стейкхолдер изменений»: формат лога, протокол сети, правила mutex. Нарушение: God class.

**O — Open/Closed Principle (открыт/закрыт).**  
Расширяй поведение **добавлением** (новый класс, новая стратегия, новый template parameter), а не **правкой** стабильного кода full of switches. Нарушение: `switch(type)` на каждый новый кейс.

**L — Liskov Substitution Principle (подстановка Лисков).**  
Подтип должен **сохранять контракт** базового типа для клиента. Нарушение: Square наследует Rectangle и ломает setWidth/setHeight.

**I — Interface Segregation Principle (разделение интерфейсов).**  
Клиент не должен зависеть от методов, которые не использует. Нарушение: один `IWorker` с eat/sleep/report для робота.

**D — Dependency Inversion Principle (инверсия зависимостей).**  
Высокоуровневая политика не зависит от деталей (SQLite, TCP); оба зависят от **абстракций**. Нарушение: `new Sqlite` внутри `Service`.

## SOLID и пройденный стек

| Принцип | Намёк в курсе training |
|---------|-------------------------|
| S | Пул vs очередь vs стадия pipeline |
| O | `submit(Job)` vs switch по типу задачи |
| L | Редко is-a в multithread; важно для будущих API |
| I | Узкий callable vs жирный interface |
| D | Тесты с подменой storage (идея) |

## SOLID vs паттерны GoF

Паттерны (Factory, Strategy, Observer) — **конкретные решения**. SOLID — **критерии**, почему Strategy лучше giant switch. Том 8 не проходит все паттерны; после SOLID можешь читать GoF с фильтром «какой принцип это усиливает».

## SOLID vs тестируемость

SRP → маленькие unit-тесты. DIP → mock. OCP → новый тест на новый derived, старые тесты не трогаешь. TSan (том 7) не заменяет дизайн: гонка в God class останется, даже если «всё в одном mutex».

## Как учить, если ООП слабое

1. Прочитай главу S–D **с карандашом**: один пример из жизни, один из курса (словами).
2. После каждой главы открой **свой** `task.cpp` (не solutions) — найди **одно** возможное нарушение или **одно** хорошее решение.
3. Не пытайся «переписать весь проект под SOLID» за вечер — один класс, один границы.
4. Обсуди с репетитором строку «Том 8 · Глава» — другой чат, как в томе 0.

## Анти-догматизм

Учебный `task.cpp` на 40 строк может смешивать всё — **нормально** для обучения синтаксиса. SOLID становится важным, когда файл живёт месяцами и в него лезут пятеро разработчиков. Цель тома — **язык** для роста, не вина за учебник.

## К собесу (превью)

На собеседовании часто: «Что такое SOLID?», «Приведи пример SRP», «Чем композиция лучше наследования в контексте LSP». После глав 9–13 вернись сюда и проверь, можешь ли ответить **без шпаргалки** двумя предложениями на букву.

## Типичные заблуждения

«SOLID только для Java» — нет.

«Один класс = одна функция» — карикатура SRP.

«SOLID заменяет тесты и TSan» — нет.

«Virtual обязателен для OCP» — шаблоны и function тоже.

## Сценарий: один PR ломает пять модулей

Представь сервис «заказы» в одном классе `OrderHub`: парсит JSON, пишет в SQLite, шлёт email, логирует в файл, считает метрики для Prometheus. Продукт просит **новый формат JSON** — ты правишь `OrderHub`. В том же PR случайно ломаешь SQL-запрос: падают интеграционные тесты, которые поднимали всю «вселенную». Это не «плохой программист», это **пять причин для изменения** в одном типе (SRP). Отдельный `OrderRepository`, `Mailer`, `MetricsSink` — пять файлов, но **один** PR по JSON трогает только парсер.

SOLID не гарантирует отсутствие багов. Он снижает **радиус взрыва** при эволюции. После томов 3–7 ты уже знаешь, что гонка в God class не исчезнет от «красивой диаграммы» — TSan всё равно нужен. SOLID и санитайзеры **дополняют** друг друга: первый про границы, второй про фактические data races.

## Матрица «принцип → симптом в review»

Когда читаешь чужой diff или свой код через неделю, полезно иметь **запахи**:

| Запах | Часто про | Что спросить |
|-------|-----------|--------------|
| Файл растёт во все стороны | S | Кто просит следующую фичу в этом классе? |
| Новый `case` в центральном switch | O | Можно ли добавить тип без правки switch? |
| `dynamic_cast` в бизнес-логике | L | Подтип правда substitutable? |
| Реализация с пустыми `override` | I | Клиенту нужны все методы интерфейса? |
| `new ConcreteDb` внутри сервиса | D | Где composition root? |

Это не чеклист для робота — иногда switch из трёх значений **нормален**. Но на **границе** модуля (публичный API библиотеки, plugin host) OCP и DIP окупаются быстрее.

## SOLID и C++-идиомы (мост к главам 5–7)

**Virtual destructor** — не буква SOLID, но **предпосылка** полиморфного OCP и DIP: `unique_ptr<IStorage>` без `virtual ~IStorage()` — UB при уничтожении. **RAII** — способ держать инвариант SRP внутри маленького класса: mutex + deque не торчат наружу. **Rule of Five / Zero** — чтобы «сервис с ресурсом» не копировался случайно и не удваивал владение тем же файлом.

Шаблонный сервис `ServiceT<Repo>` — DIP **на этапе компиляции** (глава 13). `std::function` в `submit` — OCP **без** иерархии `JobBase`. Не своди SOLID к «надо нарисовать UML с десятью интерфейсами».

## Сквозной мини-проект (мысленный, без кода курса)

Допустим, ты пишешь **симулятор кузницы** (не advanced 06, а свой учебный):

1. **S:** `ThreadPool` только про jobs; `Smithy` только про «заказ → результат»; конфиг — отдельно.
2. **O:** новый тип заказа — новая функция-обработчик в `submit`, не правка ядра пула.
3. **L:** если введёшь `IExecutor`, mock в тестах должен вести себя как пул (не «иногда игнорировать submit»).
4. **I:** воркеру не нужен API `wait_idle` — только callable.
5. **D:** `Smithy` принимает `IExecutor&` или callback, создаёт пул `main`.

Пройди этот список **устно** после глав 9–13. Если застрял на букве — вернись к соответствующей главе, не к YouTube-ролику на 3 минуты.

## Антипаттерн «SOLID-театр»

Иногда видишь: пять интерфейсов по одному методу, DI-контейнер на 10 строк кода, `AbstractFactoryFactory`. Формально буквы соблюдены, смысл утонул. **YAGNI** и SOLID не враги: сначала **второй** реальный вариант поведения или **второй** стейкхолдер изменений — потом абстракция.

Учебный `task.cpp` на 40 строк **не обязан** быть эталоном enterprise. Том 8 учит **замечать**, когда файл перерос порог «можно держать в голове целиком».

## Связь с собеседованием (как готовиться)

Типичный формат: «Расскажи про SOLID» → «Пример SRP» → «Rectangle/Square» → «Зачем DIP». Подготовка: на каждую букву **два предложения** + **один** пример из C++ (не из Java Spring). Свяжи OCP с `std::function` и шаблоном — это выделит тебя среди кандидатов, которые повторяют только «Strategy pattern».

## Порядок чтения S→D и обратные связи

SRP **первый**, потому что без границ модулей остальное абстрактно: OCP бессмыслен на God class — некуда «добавлять» без риска. LSP проверяет **наследование**, которое OCP часто вводит. ISP сужает **интерфейсы**, появившиеся после DIP/OCP. DIP **замыкает** цикл: зависимости должны смотреть на абстракции **между** SRP-модулями.

Если читаешь второй раз — иди **D→S**: с composition root назад к ответственностям. Так видно, почему `FakeRepo` требовал отдельного `IRepo`, а не «просто public метод save в Sqlite».

## SOLID и code review (как формулировать комментарий)

Вместо «плохой код» на review полезно:

- «Здесь две причины для изменения (конфиг + сеть) — предложу вынести ConfigLoader (SRP)».
- «Новый case в switch — можно зарегистрировать handler (OCP)».
- «Mock не может реализовать eat/sleep — разделим IWorkable (ISP)».
- «Sqlite внутри сервиса — перенесём в main (DIP)».

Тон **конструктивный**; принцип — **аргумент**, не дубинка. На учебном коде 40 строк review-комментарий про DIP может быть ранним — **контекст** решает.

## Ещё раз: C++ idioms в одном абзаце

Полиморфная иерархия: **virtual dtor**, `override`, `unique_ptr<Base>`, delete copy или protected copy. Расширение без иерархии: **`std::function`**, шаблонный алгоритм, `variant`+visit. Владение: **RAII**, Rule of Zero, move в очередь. Границы: **инкапсуляция** mutex, **composition** вместо наследования STL. SOLID сидит **поверх** этих idioms, не вместо них.

## FAQ по SOLID в C++ (короткие ответы)

**Нужен ли SOLID в header-only библиотеке?** — Да, на границах public API; внутренние detail namespace могут быть грязнее.

**SOLID и performance?** — Virtual и indirection стоят денег; hot path может остаться template — OCP другим способом.

**SOLID в single-file учебнике?** — Думать полезно; применять жёстко — когда файл живёт дольше недели.

**С чего начать рефакторинг?** — SRP (разрезать God), затем DIP (вынести concrete в main), затем OCP (убрать switch), LSP/ISP по мере иерархий.

**Связь с multithread?** — SRP: sync отдельно от домена; LSP: mock executor честен; инвариант под mutex — инкапсуляция, не буква SOLID.

## Краткое резюме

SOLID — пять критериев границ и зависимостей. Читай S→D с примерами. Связывай с multithread словами, не спойлерами. Учи постепенно. Дальше — SRP глубоко.
