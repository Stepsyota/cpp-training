# Глава 9. Single Responsibility

## Зачем эта тема

**Single Responsibility Principle (SRP):** *A class should have one, and only one, reason to change.*  
На русском удобнее: у модуля **одна зона ответственности** — один **источник** правок при эволюции системы. Это **самый** частый принцип на практике и **самый** неправильно понимаемый: его сводят к «класс должен делать одну вещь», и начинают дробить `Calculator` на `Adder` и `Printer` без смысла.

Для твоей слабой зоны в ООП SRP — **входная дверь**: научись видеть **смешение ролей** в одном файле и **разделять** их без фанатизма.

## «Одна причина для изменения» — что это

**Причина** — не баг в компиляторе. Это **роль** или **актор**:

- изменился **формат конфига** → меняется только загрузчик конфига;
- изменилась **политика логирования** → меняется logger;
- изменился **протокол синхронизации очереди** → меняется bounded queue, не логика «покраски» детали.

Если один класс меняется и когда просят JSON вместо YAML, и когда просят epoll вместо blocking — **две причины** → SRP нарушен.

## Пример God object

```cpp
class Application {
    void load_config(const std::string& path);
    void connect_database();
    void run_http_server();
    void render_ui();
    void send_weekly_report_email();
};
```

Любая фича в UI ломает сборку сервера. Тестировать «только HTTP» невозможно без поднятия UI. **Разрез:**

- `ConfigLoader`
- `Database`
- `HttpServer`
- `UiApp`
- `ReportScheduler` + `EmailSender`

`main` или `ApplicationFacade` **координирует**, но не содержит всю логику.

## SRP и файлы

Один `.cpp` на 2000 строк с пятью несвязанными namespace — тот же запах. SRP применим к **функции**: `parse_and_save_and_log` — три причины; разбей на три функции или три класса.

## ThreadPool — одна ответственность?

Публичные методы: `submit`, `wait_idle`, деструктор с `join`. **Одна роль:** жизненный цикл **фоновых job** и воркеров. Не парсит JSON, не пишет в socket.

Если бы внутри пула был код «разобрать HTTP запрос» — SRP нарушен. Кузница (smithy) в advanced **использует** пул, а не смешивает протокол HTTP с mutex очереди.

## BoundedQueue — другая ответственность

Очередь отвечает за **буфер с потолком** и **блокировки** producer/consumer. Стадия «покрасить Item» — **другая** причина изменения (бизнес-правило цвета). Смешать в `PaintAndQueue` — при смене `cap_` трогаешь краску.

Pipeline в курсе **разделяет** стадии и очереди — это SRP на уровне архитектуры, даже если ты не называл принцип.

## parallel_map

Одна ответственность: **параллельно применить** `F` к диапазону с корректным разбиением. Не знает, что `F` считает — только контракт `F` и потоки. Изменение алгоритма суммирования **не** должно править `parallel_map.hpp`.

## Как резать без over-engineering

**Шаг 1:** выпиши, **кто** просит изменений (продукт, инфра, безопасность).  
**Шаг 2:** отметь в классе методы, относящиеся к разным «кто».  
**Шаг 3:** вынеси группу в отдельный тип или namespace.  
**Шаг 4:** оставь тонкий координатор.

Не делай интерфейс `IAdd` с одним методом, если сложность не выросла.

## SRP и многопоточность

Класс «и синхронизация, и бизнес-логика» иногда смешивают «для скорости». Лучше: **синхронизированная очередь** + **чистая** функция обработки `process(Item)` снаружи lock (вызывается из воркера **под** протоколом пула). Бизнес меняется без правки mutex-логики очереди.

## Мини-кейс для размышления

`main` в учебнике: парсит argv, создаёт потоки, печатает результат. Три причины. Рефакторинг в `int main` только: `auto cfg = load(argc, argv); run(cfg);` — уже лучше.

## Сценарий: «ReportGenerator» с тремя начальниками

Класс генерирует PDF-отчёт. Его меняют:

- **Отдел аналитики** — новые колонки и формулы;
- **Инфраструктура** — переход с SMTP на API почты;
- **Безопасность** — маскирование PII в отчёте.

Три независимых источника правок в одном `.cpp` — классический SRP-провал. Разрез:

```cpp
struct ReportData { /* поля */ };
ReportData build_report(const SalesDb& db);
std::string render_pdf(const ReportData& d);
void send_via_mailer(const std::string& pdf, IMailer& m);
```

`build_report` меняется от аналитики; `render_pdf` — от layout; `send_via_mailer` — от транспорта. Координатор `WeeklyReportJob` **склеивает** три шага — у него своя, четвёртая, но **тонкая** ответственность «оркестрация раз в неделю».

## Антипаттерн: «Utils» как свалка

```cpp
namespace utils {
    void parse_json(...);
    void send_tcp(...);
    int hash_string(...);
}
```

Один namespace — **много** причин для изменения. SRP на уровне файлов: `json_io.cpp`, `net_tcp.cpp`, `hash.cpp`. Namespace не создаёт границу компиляции; раздельные единицы трансляции — создают.

## SRP и тестируемость (развёрнуто)

God object заставляет поднимать «пол-программы» в unit-тесте: БД, сеть, filesystem. Маленький `ConfigLoader` тестируется **файлом-фикстурой** на диске. `OrderService` с `FakeRepo` — **без** SQLite. SRP — не про «мало строк», а про **узкий** mock boundary.

В multithread тест `06_thread_pool` проверяет **контракт пула**, не smithy. Если smithy и HTTP в одном классе с пулом — тест пула начинает тянуть HTTP — запах.

## Граница «одна ответственность» vs «одна функция»

Класс `BoundedQueue` имеет `push`, `pop`, `close`, возможно `front` — **несколько** методов, **одна** ответственность: «согласованный буфер producer/consumer». Не дроби на `Pusher` и `Popper` классы, если **все** клиенты всегда используют оба полушария — это ISP (глава 12), а не SRP.

Вопрос SRP: «Если завтра изменят **только** политику блокировки при `close`, сколько **несвязных** мест придётся трогать?»

## Рефакторинг SRP по шагам (без big bang)

1. Выдели **pure function** без состояния (парсинг, формула) — zero risk.
2. Вынеси **I/O** за интерфейс (намёк на DIP) — тесты без диска.
3. Оставь **facade** со старым API, делегирующий новым типам — не ломай call sites сразу.
4. Удали facade, когда call sites мигрировали.

Так работают реальные PR, а не «переписал всё за выходные».

## SRP и многопоточность (ещё раз, глубже)

Антипаттерн: «для скорости» держим `mutex` в `main` и передаём «голую» очередь в потоки. Тогда **инвариант очереди** и **инвариант бизнес-стадии** смешаны в голове программиста. Правильнее: очередь **сама** serializes доступ; стадия `process(Item)` **не знает** про mutex очереди — только про Item.

SRP здесь: класс очереди меняется от **sync protocol**; функция `process` — от **доменного правила** покраски.

## К собесу — развёрнутые ответы

**«Может ли класс иметь 10 методов и соблюдать SRP?»** — да, если все десять обслуживают **одну** причину изменения (например, протокол TCP-сессии: connect, send, recv, close — меняется от RFC/продукта сети, не от PDF).

**«SRP vs микросервисы?»** — родственная идея на уровне деплоя; в одном процессе SRP — про **классы и файлы**. Не путай «один сервис = один класс».

**«Где SRP в STL?»** — `std::mutex` не парсит JSON; `std::vector` не пишет в socket. Маленькие типы с одной ролью — неформальный SRP стандартной библиотеки.

## Cohesion (связность) — соседняя идея

**Cohesion** — насколько элементы модуля **дружат** друг с другом. SRP про **одну причину изменения**; высокая cohesion — симптом, что причина одна. Низкая cohesion + много «кто» в review — сигнал резать. Не путай cohesion с «как можно меньше методов» — пустой класс cohesion формально высокая, пользы ноль.

## Типичные заблуждения

«SRP = один public метод» — нет.

«Маленький класс всегда правильный» — может быть бессмысленная дробь.

«SRP не для учебных task» — думать SRP полезно всегда, применять жёстко — когда код растёт.

«God class быстрее писать» — сначала да, потом дорого.

## К собесу

Сформулируй SRP. Приведи God class и разрез. Объясни, почему пул и очередь — разные ответственности. Ответь: «Может ли класс иметь 10 методов и SRP?» — да, если одна причина изменения.

## Практика: аудит одного файла (15 минут)

Открой **любой** свой `.hpp` из advanced (не solutions). Выпиши **все** `#include` и **все** public методы. Рядом с каждым методом — одно слово «кто попросит изменить» (продукт, sync, I/O, тесты). Если **три и больше** разных «кто» — файл кандидат на разрез **после** сдачи задачи, не во время первого прохождения курса. Цель — тренировать глаз, не переписывание ради книги.

## Связь с главой 7 (RAII)

Класс, который **и** владеет файлом, **и** парсит JSON, **и** шлёт UDP — три ресурса/роли. RAII говорит «закрой файл в dtor»; SRP говорит «парсер не должен знать про UDP». Раздели: `UdpSender` + `JsonParser` + `FileReader` — три маленьких RAII-типа или Rule-of-Zero struct.

## Краткое резюме

SRP = одна причина для изменения на модуль. God object — антипример. Пул, очередь, стадия pipeline — разные роли. Резать по стейкхолдерам, не по числу строк. Дальше — OCP.
