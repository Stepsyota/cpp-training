# Глава 2. Инкапсуляция

## Зачем эта тема

**Инкапсуляция** — не синоним «сделать поля private из принципа». Это договор: **внутреннее представление** и **правила перехода между состояниями** скрыты; снаружи доступен **узкий интерфейс**, через который инвариант **невозможно** нарушить обычным использованием. В однопоточном коде инвариант — «баланс не отрицательный», «индекс в пределах». В `multithread/` — «очередь согласована», «не pop из пустой без close», «счётчик busy отражает реальность».

Если клиент может сделать `queue.q.push_back(x)` мимо mutex, инкапсуляция провалена, даже если поле называется `private` у друга класса через `friend` без дисциплины. Том 3 учил **механику** lock; том 8 учит **почему** API очереди — `push`/`pop`, а не «вот тебе deque».

## Инвариант — центральное слово

**Инвариант** — условие, которое **всегда** истинно для «валидного» объекта между вызовами публичных методов (и внутри них, пока метод не завершён). Примеры:

- `BoundedQueue`: `q.size() <= cap_`; все мутации `q` только под `m_`.
- `BankAccount`: `balance_ >= 0` (если овердрафт запрещён).
- `ThreadPool`: каждая задача в `jobs` либо выполняется воркером, либо ждёт; после `stopped` и пустой очереди воркеры выходят по контракту.

Публичные методы — **единственные** легальные способы изменить состояние так, чтобы инвариант сохранился. Если метод не может гарантировать инвариант при всех входах — он должен **отказать** (исключение, `false`, `optional`), а не молча оставить мусор.

## private, public, protected

```cpp
class TicketCounter {
    int sold_{0};
    int limit_{100};
public:
    bool try_sell() {
        if (sold_ >= limit_) return false;
        ++sold_;
        return true;
    }
    int sold() const { return sold_; }
};
```

Снаружи нельзя написать `sold_ = -1`. Все переходы через `try_sell`, который знает про `limit_`.

**protected** — видимость для наследников (глава 3). Для инкапсуляции **наружному миру** protected не лучше public: клиент всё равно не должен зависеть от protected деталей базы. Используй protected осознанно для hook в иерархии, не как «public для друзей».

## const-методы и логическая неизменность

```cpp
int size() const { return static_cast<int>(q_.size()); }
```

`const` на методе обещает: **логическое** состояние объекта для наблюдателя не меняется. Физически можно менять `mutable` счётчики кэша — редкий приём.

**Критично для многопоточности:** `const` метод **не** делает объект thread-safe. Два потока могут звать `size() const` на очереди без mutex — гонка на внутреннем `deque`. Инкапсуция + **sync внутри** каждого мутирующего/читающего метода — отдельная обязанность (том 3).

## Антипаттерн: геттер/сеттер на всё

Стиль «Java bean»:

```cpp
void set_balance(int b) { balance_ = b; }
int get_balance() const { return balance_; }
```

Клиент может установить `-1000` и сломать инвариант. Лучше **операции домена**:

```cpp
bool withdraw(Money amount);
void deposit(Money amount);
```

Инкапсуляция — **поведение**, не секретность ради секретности. Иногда readonly доступ уместен (`name()`, `id()`), но пара `get/set` на каждое поле — запах.

## friend — узкий прорыв

`friend bool operator==(const Queue& a, const Queue& b);` — допустимо для симметричного сравнения без public accessors на каждое поле. `friend class Tests;` — иногда для white-box тестов (спорно; лучше тестировать через public API).

Friend **не** отменяет инвариант: друг обязан его уважать. Если friend лезет в поля и обходит mutex — дизайн сломан.

## PIMPL — инкапсуляция компиляции

Когда тяжёлый заголовок (`boost::...`, GUI) раздувает время сборки:

```cpp
// widget.hpp
class Widget {
    struct Impl;
    std::unique_ptr<Impl> impl_;
public:
    Widget();
    ~Widget();
    void draw();
};
```

Клиенты не видят полей `Impl`. Это **инкапсуляция зависимостей** от компилятора, не только логики. Цена: indirection, один heap block. Для учебных размеров редко нужно; в проде — часто.

## Исключения и инвариант

Метод `push` под mutex: если внутри выбросилось исключение после изменения `q_` но до отпускания инварианта — **RAII** `lock_guard` снимает mutex, но очередь может остаться в промежуточном состоянии, если исключение из `q_.emplace_back`. Практика: операции на `deque` не бросают (кроме bad_alloc); при bad_alloc объект может быть unusable — редкий edge; в курсе обычно не разбирают.

Главное: **не** оставлять mutex захваченным при unwind — для этого guard.

## Связь с bounded queue (идея)

Публичный контракт: `push` блокируется при полной, `pop` ждёт элемент, `close` — сигнал «больше не принимаем, но дренируем». Клиент **не** знает, один `condition_variable` или два — инвариант «не потерять элементы при close» снаружи проверяется поведением тестов, не полями.

## Упражнение для головы

Возьми `02_ticket_office`: счётчик внутри класса `Counter` с методом `buy()` под mutex vs глобальный `int` и `lock` в `main`. Второй вариант **может** быть корректным, но инкапсуляция переносит **знание** про инвариант в тип. Спроси себя: «где одна причина для изменения логики билетов?»

## Сценарий: «утёк» внутренний контейнер

```cpp
class Bag {
    std::vector<Item> items_;
public:
    std::vector<Item>& raw() { return items_; }  // антипаттерн
};
```

Клиент делает `bag.raw().clear()` **мимо** инварианта «сумма весов ≤ лимит». Правильнее: `bool add(Item)`, `span<const Item> view()` без мутации снаружи. Если нужен bulk export — `void for_each(F&&)` под контролем класса.

## Инвариант под concurrent вызовами

Два потока: один `push`, другой `pop`. Инвариант «нет lost wakeup» **не виден** в сигнатуре public API — он в **протоколе** cv + mutex. Инкапсуляция прячет `not_empty` / `not_full`; клиент видит только блокирующие `push`/`pop`. Это образец **хорошей** границы для тома 3 + тома 8 вместе.

## Антипаттерн: «DTO на всё»

Структуры с десятью public полями гоняют между слоями без поведения — иногда нужны (JSON DTO), но **доменная** модель «заказ» с `add_line` и проверкой суммы должна **инкапсулировать** правила. Иначе валидация размазана по «сервисам» — anemic model (глава 14).

## Закон Demeter (намёк)

Метод `order.customer().address().zip()` — цепочка через чужие внутренности. Лучше `order.shipping_zip()` на фасаде Order. Меньше coupling — проще менять Customer без правки всех call sites.

## К собесу

«Инкапсуляция vs private» — инвариант и доменные операции. «const method thread-safe?» — нет, если есть mutable shared state без sync. «Пример инкапсуляции в multithread» — mutex + cv внутри класса очереди.

## Типичные заблуждения

«private = инкапсуляция» — без инварианта и API это просто скрытые поля.

«const = потокобезопасно» — нет.

«struct с public полями всегда плохо» — для `Point` OK; для очереди — нет.

«Инкапсуляция замедляет» — вызов метода vs прямой доступ negligible; выигрыш в корректности.

## Сценарий: счётчик билетов и гонка

В `02_ticket_office` инвариант «`sold <= limit`» должен держаться при двух потоках. Если `sold_` public, один поток делает `++sold_` без замка — гонка. Инкапсуляция **сводит** все мутации к `try_sell()` под mutex — один дверной проём. Это мост к SRP: «логика продажи билетов» живёт в типе, а не в `main`.

## mutable и кэш (осторожно)

```cpp
class Expensive {
    mutable std::optional<int> cache_;
public:
    int value() const {
        if (!cache_) cache_ = compute();
        return *cache_;
    }
};
```

Логически const, физически меняет cache. В **многопоточном** коде такой cache без sync — гонка. Инкапсуляция не отменяет tom 3: внутри const метода всё равно нужен mutex или atomic для shared cache.

## Краткое резюме

Инкапсуляция = инвариант + публичные операции. Меньше слепых set/get, больше доменных методов. const — про логику, не про threads. friend и PIMPL — спецприёмы. Очередь и пул в курсе — эталоны границ. Дальше — наследование.
