# Глава 12. Модули: module, import, export

## Зачем эта тема

Долгое время граница между «моим кодом» и «чужим API» в C++ проходила через одну привычную строку: `#include "geometry.hpp"`. Препроцессор не «подключает библиотеку» в смысле линковщика — он **вставляет текст** файла прямо в твоей единице компиляции. Макросы из заголовка становятся твоими. Одно и то же объявление может пройти через десять `.cpp` и десять раз попасть в парсер. Компилятор кэширует что может, но на больших проектах минуты сборки часто упираются именно в повторный разбор заголовков.

**(C++20)** комитет добавил три keywords — **`module`**, **`import`**, **`export`** — и вокруг них новую модель: **модуль** как единица с **явным интерфейсом**. Потребитель пишет `import geom;` и получает только то, что производитель пометил `export`. Это не отменяет линковку и не заменяет CMake одним волшебным словом, но меняет **первый контакт** с API: меньше текстовой вставки, меньше случайного макро-загрязнения, чётче граница «видно снаружи / только внутри модуля».

В репозитории `training` трек многопоточности пока живёт на **C++17** и классических заголовках — так проще собирать на любой Fedora без возни с BMI (binary module interface). Эта глава нужна не для немедленной переписки `thread_pool.hpp`, а чтобы ты **читал** современные репозитории, понимал, зачем там `export module`, и не путал новый `export` со старым `export template` из учебников нулевых. Детали флагов GCC и Clang — в томе 5 серии.

## Две роли: производитель и потребитель

Представь библиотеку геометрии. В мире заголовков автор кладёт объявления в `geom.hpp`, реализацию — в `geom.cpp`, клиент делает `#include "geom.hpp"`. В мире модулей появляется **module interface unit** — файл, который компилятор трактует как «лицо» модуля:

```cpp
export module geom;

export struct Point {
    int x, y;
};

export int manhattan(Point p);
```

Строка **`export module geom;`** одновременно **объявляет имя модуля** и говорит: этот файл задаёт публичную часть. Реализацию `manhattan` можно держать в **module implementation unit** того же модуля (отдельный `.cpp` с `module geom;` без `export` на строке модуля — схема зависит от toolchain, но идея одна: интерфейс и тело могут делиться).

Потребитель больше не вставляет текст заголовка. Он пишет:

```cpp
import geom;

int main() {
    return manhattan({1, 2});
}
```

Keyword **`import`** говорит компилятору: подтяни **скомпилированное представление** модуля `geom` — BMI и связанные артефакты — и сделай доступными **экспортированные** имена. Это принципиально не то же самое, что `#include`: препроцессор не раздувает твой файл сотнями тысяч строк из `<vector>`; компилятор загружает уже подготовленный интерфейс.

Если ты привык думать «include = подключил зависимость», полезная замена: **`import` = я зависим от модуля с именем `geom`**, а что именно из него видно — решил автор через `export`.

## `export` — граница модуля, не «экспорт в DLL»

Слово **`export`** в **C++20** путают с Windows DLL export или с Java — это другое. Здесь export отвечает на вопрос: **какие имена клиент модуля имеет право использовать после `import`?**

```cpp
module secrets;

int internal_hash(int x);   // не export — клиент не увидит
export void api_login();
```

Функция `internal_hash` может быть определена в том же модуле и вызываться из `api_login`, но другой файл с `import secrets;` **не сможет** вызвать `internal_hash` — имя не часть публичного интерфейса. Это похоже на разницу между `public:` и `private:` внутри класса (глава 3), но **на другом уровне**: `export` режет видимость на границе **translation unit модуля**, а не внутри одного типа.

Экспортировать можно не всё подряд: типы, функции, переменные, typedef/using, шаблоны, namespace — по правилам стандарта и с ограничениями. Нельзя «экспортировать макрос» как first-class сущность модуля так же, как функцию: макросы живут в мире препроцессора, модули — после него. Отсюда главная боль миграции legacy-кода с `#define`.

Критично для чтения старых текстов: в **C++03** существовало **`export template`** — попытка вынести определения шаблонов в `.cpp`. Эту конструкцию **удалили**; она почти нигде не прижилась. В **C++20** keyword **`export` вернулся с новым смыслом** — только модули. Если статья 2005 года говорит «export шаблонов», не переноси это в голове на `export module` (глава 9 и 13).

## Имя модуля и module partition

Объявление **`export module my.lib.core;`** задаёт **глобальное имя** модуля. Точки в имени — не оператор доступа, а **соглашение** о иерархии (`my.lib.core` логически «внутри» семейства `my.lib`). Стандарт не навязывает файловую структуру папок один к одному, но команды часто зеркалят имена в путях для людей.

Большой модуль дробят через **module partition** — части одного логического модуля в разных файлах:

```cpp
export module foo:part;

export void part_api();
```

В другом файле интерфейса того же модуля:

```cpp
export module foo:impl_part;
import :part;
```

Запись **`import :part;`** — импорт **partition** текущего модуля, без повторения полного имени. Это для сопровождения: не один файл на три тысячи строк, а несколько единиц компиляции с общим именем `foo`. Для первого знакомства достаточно знать, что `:part` в `import` — не опечатка, а осознанный синтаксис.

## Global module fragment — мост с `#include`

Чистый модульный мир хотел бы жить без препроцессорных вставок. Реальность: годы кода включают `<cstddef>`, platform headers, C API с макросами. Для этого есть **global module fragment** — блок в **начале** файла:

```cpp
module;

#include <cstddef>
#include <cstring>

export module M;

export void use_c_api();
```

Строка **`module;`** **без имени** открывает fragment. Здесь разрешены обычные **`#include`** и препроцессор, как в до-модульной эпохе. После **`export module M;`** начинается собственно модуль M; код там уже в модульной семантике. Fragment — **не** «экспорт include наружу»: клиент `import M;` не получает автоматически все макросы из `<cstring>`, unless они как-то пробрались через объявления — детали миграции кропотливы, и это аргумент за постепенный переход.

Если видишь файл, который начинается с `module;` и длинного списка includes — автор честно признаёт: «этот модуль стоит на плечах C и старых заголовков».

## Варианты `import` и header units

Базовая форма — **`import имя_модуля;`**. Для partition внутри того же модуля — **`import :partition;`**.

**(C++20)** добавили **header units** — попытку импортировать стандартный заголовок как модульную единицу:

```cpp
import <vector>;
```

Вместо `#include <vector>` в некоторых конфигурациях toolchain. Поддержка и скорость сильно зависят от версии компилятора и от того, собран ли BMI для `<vector>`. На практике это отдельная кнопка в CI, не «заменил все include одним днём».

**(C++23)** в разговорах о модулях часто всплывает **`import std;`** — импорт стандартной библиотеки как **одного модуля** `std`, если реализация это поставляет. На момент типичной Fedora это проверяется через `g++ --version` и документацию: «есть ли prebuilt std module». Книга не обещает, что `import std;` уже работает в твоём `CMakeLists.txt` — только что keyword **`import`** — правильная грамматика для потребления.

## Что происходит при сборке (интуиция без BMI-магии)

Когда ты **`import geom;`**, компилятор ищет **уже скомпилированный** интерфейс модуля `geom` — BMI и сопутствующие файлы — или строит его, если компилируешь модуль впервые в этой конфигурации. Ошибки вроде «failed to read compiled module» или «unknown compiled module» обычно означают: модуль не собран, собран другим компилятором/флагами, или путь к BMI не передан в командную строку (том 5).

С `#include` ты привык, что достаточно `-I` с путём к заголовкам. С модулями добавляется **граф модульных зависимостей** и кэш артефактов. Это не недостаток keywords — это цена другой модели изоляции.

## Макросы, ODR и смешанные сборки

Макрос `#define DEBUG 1` в заголовке при `#include` виден **везде**, куда заголовок вставили. При **`import`** клиент **не** должен рассчитывать, что макросы из global fragment «протекут» так же, как при include. Legacy, завязанный на `#ifdef NDEBUG`, требует явного плана: вынести конфиг в отдельный модуль, заменить на `constexpr bool`, оставить headers для части проекта.

**ODR (one definition rule)** никуда не делся. Если один и тот же символ объявлен и в header, и в module без дисциплины, получишь duplicate symbol или тихую путаницу. Миграция часто **гибридная**: часть библиотеки на modules, часть на `#include`, пока не выстроен граф.

Типичная ошибка новичка: ожидать, что **`import`** «подтянет» `#define PLATFORM_LINUX` из старого `config.h` так же, как include. Проверяй реальный интерфейс модуля, а не привычки препроцессора.

## `export` и инкапсуляция класса

Keyword **`private`** в class задаёт доступ **членам и друзьям** типа. **`export`** на `class Widget` в module interface делает **сам тип** видимым клиенту модуля; члены внутри по-прежнему `public`/`private`. Можно экспортировать класс, не экспортируя вспомогательную функцию в том же файле — два слоя «что видно».

Не путай: **`export` не заменяет `private:`**. Можно случайно экспортировать слишком много — и тогда API модуля раздувается так же, как публичные заголовки в monorepo.

## Практика на Fedora: GCC и Clang

На рабочей машине первый шаг — версия:

```bash
g++ --version
clang++ --version
```

Флаги модулей эволюционировали: раньше часто фигурировал экспериментальный `-fmodules-ts`, в новых GCC/Clang — более стабильные режимы. Точная строка для твоей версии — в manual и в томе 5. Если `-std=c++20` включён, а **`import`** всё равно «unknown`, проблема не в стандарте на бумаге, а в **реализации** и в том, собран ли модуль-поставщик.

Мини-проверка из главы 1: создай два файла `geom.cppm` / `main.cpp` из примеров выше, собери по инструкции cppreference для твоего компилятора. Одна успешная сборка запоминается лучше, чем десять абзацев про BMI.

## Private module interface и implementation (картина целиком)

У крупной библиотеки часто **несколько** `.cpp` на один модуль: один файл с **`export module lib;`** и минимальным API, другие с **`module lib;`** (без export на строке модуля) — implementation units, которые **видят** внутренние partition и не обязаны экспортировать детали. Keyword **`module`** без **`export`** в начале implementation unit говорит: «я часть модуля `lib`, но не объявляю новый публичный интерфейс».

Клиент по-прежнему пишет только **`import lib;`**. Ему не нужно знать, сколько файлов собирали BMI — как ему не нужно знать, сколько `.cpp` реализуют класс из одного `.hpp`. Путаница начинается, когда в implementation unit забывают **`module lib;`** и получают обычный TU без модульной семантики.

## Сравнение с привычным `#include` одной таблицей

| Вопрос | `#include "api.hpp"` | `import api;` |
|--------|----------------------|---------------|
| Что делает препроцессор | Вставляет текст | Не вставляет тело модуля |
| Макросы из заголовка | Видны потребителю | Обычно **не** часть контракта `import` |
| Повторный разбор API | В каждом `.cpp` | Интерфейс через BMI |
| ODR | Классика заголовков + include guards | Модульная модель + те же правила символов |

Таблица — ориентир, не замена toolchain manual: header units и hybrid builds размывают границы, пока миграция не завершена.

## Когда разумно остаться на headers

Модули — не моральный долг. Оставайся на `#include`, если:

- библиотека **header-only** и так задумана (много open source);
- целевые компиляторы **старше C++20** (встроенные toolchain, кросс-компиляция);
- учебный проект вроде **`training`**, где цель — mutex и пул, а не BMI в CI;
- команда не готова поддерживать **двойную** сборку модулей и headers.

Keywords **`module` / `import` / `export`** всё равно стоит знать: они уже в чужом коде, в статьях и в `-std=c++20` по умолчанию в новых проектах.

## Типичные заблуждения

Иногда думают, что **`import`** — это просто «быстрый include». Быстрота может прийти, но суть — **другая граница видимости** и другой pipeline компиляции, не текстовая вставка.

Другой миф: «перепишем репозиторий на модули за выходные». На практике упираются в макросы, порядок сборки, mixed TU, тесты, которые тянут private headers — недели и план, не один keyword.

Третий миф: **`export`** на всё подряд «как в Java». Лишний export раздувает API и фиксирует детали реализации; хороший module interface маленький, как хороший `.hpp`.

## Краткое резюме

**(C++20)** keywords **`export module`**, **`import`**, **`module`** описывают модули с явным публичным интерфейсом через **`export`**. **`import`** потребляет модуль через скомпилированный интерфейс, а не через препроцессорную вставку. **Global module fragment** (`module;` … `#include` … `export module M;`) — мост для legacy. Старый **`export template`** удалён; новый **`export`** — только про модули. Репозиторий `training` на C++17 и headers — нормально; эта глава для чтения современного C++ и миграции с глазами открытыми.
