# Глава 2. Хранение и время жизни

## Зачем эта тема

Ты уже писал счётчик под `mutex` в упражнении про кассу и пул потоков в кузнице. Там важно не только «замок», но и **сколько копий** переменной существует в процессе: одна на все потоки или своя на каждый? Keywords `static`, `extern`, `thread_local` и связанные с ними правила **storage duration (времени хранения)** и **linkage (связывания)** отвечают именно на это. Ошибка «у меня локальный static, почему гонка» — почти всегда про эту главу, а не про «плохой mutex».

`auto` в современном C++ чаще про **вывод типа**, а не про кучу и стек; но начинающие всё ещё путают его со старым смыслом «автоматическая переменная» из учебников C. `register` — пережиток, который встречается в легаси и сбивает с толку. Разобравшись здесь, ты спокойнее читаешь заголовки с `extern` в C-библиотеках и поля `thread_local` в рантаймах.

## Три вопроса к каждому объекту

Когда видишь объявление, задай три вопроса — не обязательно вслух, но в голове:

**Сколько долго живёт объект?** До выхода из блока (automatic), до конца программы (static), или отдельная копия на поток (`thread_local`)?

**Сколько экземпляров в процессе?** Одна глобальная, одна на вызов функции, одна на поток?

**Видит ли имя другие `.cpp` при линковке?** External linkage — да, internal (часто через `static` в глобальной области) — нет.

Keywords из этой главы раскладываются по этим осям. Layout в памяти (стек vs сегмент данных) — деталь реализации; язык говорит о **семантике**, которую обязан соблюдать компилятор.

## `auto` — вывод типа (C++11)

До C++11 `auto` в объявлении переменной означало **automatic storage class** — почти бессмысленное «эта переменная локальная», потому что локальные и так automatic. С C++11 `auto` стало keyword **вывода типа**: компилятор подставляет тип из инициализатора.

```cpp
auto count = 0;           // int
auto name = std::string{"forge"};
auto& ref = count;        // int&
```

Это удобно с итераторами и длинными `typename` в шаблонах. Но `auto` **не снимает** с тебя обязанность думать: `auto x = expr` **копирует**, если `expr` — lvalue и ты не взял ссылку. В range-for `for (auto x : vec)` каждый раз может копироваться элемент; для тяжёлых типов пишут `const auto&` или **(C++20)** `auto&&` с осторожностью.

`auto` в возвращаемом типе функции — **(C++14)**; `decltype(auto)` сохраняет ссылочность возврата, когда обычный `auto` отбросил бы `&` и вернул копию. Это уже стык с лямбдами (том 2), но keyword один — `auto`.

Важно: `auto` **не** означает «положи в кучу» и не означает «это shared_ptr». Куча — это `new` или умные указатели; время жизни по-прежнему определяется тем, где объявлен объект.

## `register` — слово, которое не стоит писать

В учебниках восьмидесятых `register` намекал компилятору держать переменную в регистре процессора. Современные оптимизаторы сами раскладывают значения по регистрам и памяти; keyword ничего не гарантирует.

В C++17 сняли правило, что нельзя брать адрес `register`-переменной. Слово осталось в таблице keywords для совместимости со старым исходником. Если видишь `register int i;` в новом коде — это шум, не оптимизация. В главе 14 мы ещё раз отделим `register` от «ускорения цикла».

## `static` — одно слово, три разных истории

Путаница со `static` — классика собеседований, потому что грамматика использует одно keyword в трёх несвязанных на первый взгляд местах.

### Локальный `static` внутри функции

```cpp
void on_request() {
    static std::size_t id = 0;
    ++id;
}
```

Переменная `id` создаётся **один раз** при первом входе в функцию и живёт до конца программы. Следующие вызовы видят то же значение. Инициализация в C++11 **потокобезопасна** для такого static local: два потока не создадут две копии при первом входе.

Но **`++id` не потокобезопасен**, если функцию зовут из нескольких потоков без mutex. Ты проходил пул потоков: представь счётчик заказов в `static` внутри `submit` без замка — это data race (том 3). Keyword `static` дал **одну** переменную на весь процесс, а не защиту.

### `static` в глобальной области или namespace

```cpp
static int helper_state = 0;
```

Здесь `static` на file scope даёт **internal linkage**: символ `helper_state` виден только в этом `.cpp`. Линковщик не свяжет его с одноимённым static в другом файле. В современном стиле то же часто пишут через анонимный namespace:

```cpp
namespace {
    int helper_state = 0;
}
```

Смысл для сборки похож; `static` на глобальной переменной встречается в C и старом C++.

### `static` член класса

```cpp
struct JobId {
    static int next();
private:
    static int counter_;
};
```

Один счётчик на **весь класс**, не на каждый объект. Определение `int JobId::counter_ = 0;` обычно в одном `.cpp`, иначе ошибки линковки. **(C++17)** можно `inline static int counter_ = 0;` прямо в классе — keyword `inline` из главы 6, не путать со `static` здесь.

### `static` member function

Метод без `this`: вызывается как `JobId::next()`. Не имеет доступа к нестатическим полям без объекта. Keyword `static` перед функцией в классе — снова про «нет скрытого this», а не про storage duration локальных переменных внутри функции.

## `extern` — имя живёт в другом translation unit

Программа на C++ собирается из **translation units** — обычно один `.cpp` после препроцессора плюс включённые заголовки. Линковщик склеивает символы.

```cpp
// config.cpp
int g_timeout_ms = 5000;

// other.cpp
extern int g_timeout_ms;
void use() { g_timeout_ms = 1000; }
```

`extern` во втором файле — **объявление**: «где-то есть определение». Определение с инициализатором должно быть **одно** на всю программу (правило ODR). Если в двух `.cpp` написать `int g_timeout_ms = 1;` без `static`, получишь duplicate symbol при линковке.

В заголовках часто пишут `extern int g_timeout_ms;`, а инициализацию оставляют в одном `.cpp`. Ошибка новичка — `extern int x = 5;` в заголовке, который включают в десять `.cpp`: десять определений.

### `extern "C"` — не про время жизни

```cpp
extern "C" void legacy_init(void);
```

Меняется **имя на линковке** (name mangling) для вызова из C. Keyword `extern` здесь в связке с строкой `"C"`. К storage duration отношения почти нет, но в учебниках ставят рядом — не смешивай с `extern int x`.

### `extern template` (C++11)

Явное «инстанцируй шаблон здесь, в остальных только объявление». Это снова linkage инстанции шаблона; разберём в главе 9, когда дойдём до `template`.

## `thread_local` (C++11) — своя копия на поток ОС

```cpp
thread_local std::string tls_log_prefix;
```

Каждый поток, который впервые обратится к `tls_log_prefix`, получит **свою** строку. Длительность хранения как у static — до конца жизни потока (уничтожение при выходе из потока, порядок с другими `thread_local` в том же потоке может быть нетривиален).

Это удобно для кэша «без mutex», если данные не шарятся между потоками. Это **не** замена синхронизации: если два потока пишут в **общую** переменную без `thread_local`, `thread_local` на другой переменной не поможет.

В треке multithread ты используешь `std::thread` и общие структуры под mutex; `thread_local` — другой инструмент, когда каждому потоку нужен свой буфер или свой генератор случайных чисел без глобального замка.

## Как это стыкуется с `mutable` и `const`

`mutable` — не из этой главы по keyword, но часто рядом: const-метод может менять `mutable` поле. Если это счётчик или кэш без mutex в многопоточной программе — снова гонка. Storage duration не спасает от модели памяти.

## Типичные ошибки

Положить в заголовок `static int counter = 0;` внутри inline-функции — у каждого включения заголовка в `.cpp` может быть своя static local **внутри функции** (одна на TU), но глобальный `static` в заголовке без inline — отдельная боль. Путать «static local thread-safe init» с «любой inc thread-safe». Думать, что `extern` в `.h` **создаёт** переменную — нет, только объявляет.

## Краткое резюме

`auto` (C++11) выводит тип, не задаёт кучу. `register` не пишем. `static` — локальный singleton на программу, internal linkage на файле, или член/метод класса. `extern` связывает имена между `.cpp`; помни ODR. `thread_local` — копия на поток, не mutex.
