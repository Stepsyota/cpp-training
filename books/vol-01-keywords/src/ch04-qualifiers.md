# Глава 4. const, volatile, mutable

## Зачем эта тема

Ты уже видел в заголовках `void process(std::string const& s)` и метод `size() const` у контейнеров. Это не «украшение для читабельности», а **cv-qualifiers** — квалификаторы типа, которые говорят компилятору и человеку, можно ли менять объект через данное имя. Keyword **`const`** (constant — постоянный, неизменяемый через это имя) — основа **const-correctness**: контракт «я только читаю» vs «могу портить данные».

Keyword **`volatile`** (летучий, «нестабильный» с точки зрения оптимизатора) реже в прикладном коде на Fedora, но встречается в сигналах и embedded. Keyword **`mutable`** (изменяемый) — осознанная дырка в логической const-ности метода. Эти слова не про storage duration из главы 2: layout памяти тот же, меняются **правила доступа** и то, какие оптимизации компилятору разрешены.

Путаница «`volatile` для потоков» и «`const` значит объект никогда не меняется» ломает и API, и отладку. Здесь мы разложим три keyword по сценариям, не смешивая их с `mutex` и `atomic` из тома 3.

## `const` на объектах и ссылках

Объявление `const int limit = 100;` запрещает присваивание в `limit` через это имя. На практике GCC и Clang могут положить такой объект в read-only сегмент, если инициализация известна на этапе компиляции; для `const int limit = read_config();` «неизменяемость» всё равно действует через имя `limit`, хотя байты в RAM.

Ссылка **`const int&`** (const lvalue reference — const-ссылка) — способ принять большой объект «посмотреть, не копируя». Через `cref` нельзя менять объект, на который ссылаешься, если только внутри struct не окажется поле **`mutable`** (ниже). Для API это сигнал: функция обещает не менять аргумент через эту ссылку; нарушение — ошибка компиляции, а не «тихий side effect».

Маленькие типы вроде `int` часто передают по значению: копия дешевле, чем лишний уровень indirection. Для `std::string` и `vector<T>` const-ссылка — норма.

## Указатели: читай тип справа налево

С `const` у указателей путаются чаще всего, потому что keyword может относиться к **данным** или к **самому указателю**:

```cpp
int n = 0;
const int* p1 = &n;       // указатель на const int
int* const p2 = &n;       // const-указатель на int
const int* const p3 = &n;
```

`p1` можно переназначить на другой `int`, но выражение `*p1 = 1` — ошибка: данные через `p1` считаются const. `p2` всегда указывает на `n`, зато `*p2` менять можно. Стиль `int const*` эквивалентен `const int*` — дело привычки команды.

Сценарий: функция возвращает `const int*` на внутренний буфер — клиент не должен писать через указатель; если вернуть `int* const`, запрет только на смену адреса, а содержимое — нет. При ревью сигнатур это различие стоит проговаривать вслух.

## `const` в параметрах и возвращаемых типах

Сигнатура `void log(std::string const& message)` говорит: внутри `log` не ожидается изменение `message`. Это не магическая защита от гонок в многопоточности — другой поток может менять **другую** копию или тот же объект без const — но локально компилятор не даст вызвать не-const методы на `message`.

Возврат `const std::string` по значению в новом коде обычно не нужен: он мешал move в C++11 и реже оправдан сейчас. Const имеет смысл на ссылках и указателях в контракте, не как «запрет оптимизации» на return by value.

## Const member functions и перегрузки

Keyword **`const` после списка параметров** делает метод **const member function** — его можно вызывать на `const Blob&`:

```cpp
struct Blob {
    std::size_t size() const { return data_.size(); }
    void clear() { data_.clear(); }
private:
    std::vector<int> data_;
};
```

Внутри `size() const` компилятор трактует `this` как указатель на **const Blob**: нельзя вызывать `clear()` и другие не-const методы без `const_cast`. Клиент с const-ссылкой на объект получает только const-интерфейс.

Две версии одного имени — не дубликат:

```cpp
struct V {
    int& get()       { return v; }
    const int& get() const { return v; }
    int v = 0;
};
```

Выбор перегрузки зависит от const-ности объекта слева от точки. Это часть дизайна: mutable view vs read-only view.

### Логическая и физическая const-ность

**Логическая** const-ность: для пользователя `size()` «не меняет смысл» объекта, хотя внутри `vector` могли сдвинуть указатели. **Физическая**: байты в памяти реально меняются — кэш, счётчик вызовов. Для логической const с физическими изменениями и нужен **`mutable`**.

## `constexpr` рядом с `const` (C++11)

Keyword **`constexpr`** (constant expression — константное выражение) из главы 6 часто стоят рядом с `const`, и их путают. Переменная `constexpr int k = square(10);` обязана быть инициализирована константным выражением; она автоматически **const**. Обратное неверно: `const int x = read_fd();` — просто «не меняй через `x`», не обязательно compile-time.

Функция `constexpr int square(int x) { return x * x; }` *может* выполниться при компиляции, если аргументы подходят. **`if constexpr`** **(C++20)** — отдельная история: ветвление на этапе компиляции, keyword `if`, не «const if».

На Fedora проверка: `g++ -std=c++17 -Wall -c file.cpp` — `constexpr` функции C++14+ с телом из нескольких statement; для C++20 расширений нужен `-std=c++20`.

## `volatile` — особые обращения к памяти

**`volatile`** говорит компилятору: каждое чтение и запись по этому имени должны попасть в программу как обращение к памяти, без «удержания в регистре» и без удаления «лишних» повторных чтений. Типичный пример — флаг для обработчика сигнала в стиле C:

```cpp
volatile std::sig_atomic_t flag = 0;
```

Здесь `std::sig_atomic_t` — тип из `<csignal>`, для которого чтение/запись в handler считаются атомарными на уровне платформы; `volatile` дополнительно ограничивает оптимизатор **этого** объекта.

### Где уместно

MMIO (memory-mapped I/O), регистры устройств, некоторые протоколы с общей памятью с hardware — часто `const volatile T*` «только читаю регистр, значение меняется снаружи». На desktop Linux в обычном серверном C++ `volatile` встречается реже, чем в прошивках.

### Где не уместно — многопоточность

Между потоками **`volatile` не создаёт happens-before** и не даёт атомарности. Два воркера с `volatile int counter` без синхронизации — та же data race, что и с обычным `int`. Для флага «готово» между потоками в современном C++ — **`std::atomic`**, не `volatile`. В треке multithread ты уже проходил mutex и CAS; подменять их `volatile` — антипаттерн.

Комбинация **`const volatile`** на указателе означает: я не пишу сам, но значение может меняться извне (регистр, DMA). Это не «const между потоками».

## `mutable` — изменение внутри const-метода

Поле **`mutable unsigned calls_`** можно менять в методе, помеченном const:

```cpp
struct Statistics {
    int value() const {
        ++calls_;
        return data_;
    }
private:
    mutable unsigned calls_ = 0;
    int data_ = 0;
};
```

С точки зрения клиента `value() const` не меняет «данные статистики»; счётчик вызовов — служебный. Без `mutable` строка `++calls_` не скомпилировалась бы: const-метод не может менять обычные поля.

### Кэш и lazy initialization

Классический сценарий — mutable кэш, который заполняется при первом const-доступе. Если объект **шарится между потоками** без mutex, mutable кэш снова гонка. Паттерн с **`mutable std::mutex`** и `lock_guard` в const-методе легален синтаксически, но обязан соблюдать правила блокировки из тома 3:

```cpp
struct Lazy {
    int get() const {
        std::lock_guard lock(m_);
        if (!ptr_) ptr_ = std::make_unique<int>(42);
        return *ptr_;
    }
    mutable std::mutex m_;
    mutable std::unique_ptr<int> ptr_;
};
```

`mutable` не «включает потокобезопасность» — только разрешает синхронизацию внутри const API.

## Указатели на const member functions

Синтаксис вроде `void (C::*pmf)() const;` — указатель на **const member function**. Keyword `const` снова в хвосте типа функции, как у объявления метода. Это редкий уголок, но при чтении метaprogramming и `std::mem_fn` полезно помнить: const-ность метода — часть типа указателя.

## `const_cast` — связь с главой 8

Снять верхний уровень const/ref можно только **`const_cast`**. Изменить через указатель объект, который **изначально был const**, — **undefined behavior (UB)**. Keyword `const` описывает контракт; обход для «удобства» ломает оптимизации и гарантии. Легальный случай — вызов legacy-API без const, когда объект реально не const, но API принимает `T*`.

## Сценарий на Fedora: const API и сборка

Создай `qual_test.cpp` с const-методом, который случайно вызывает не-const метод — Clang и GCC дадут понятную ошибку про discarding qualifiers. С `-Wcast-qual` (GCC) лишние C-style cast к «менее const» типу подсветятся. Это дешевле, чем ловить UB в проде.

## Top-level const и const вложенных типов

**Top-level const** на объекте (`const int x`) запрещает менять `x`. **Low-level const** на pointee (`const int*` или `T const&`) — другой уровень. В шаблонах `template<typename T> void f(T const&)` const-ность аргумента не «протекает» в `T`: для `vector<int>` параметр const, но `T` — `vector<int>`, не `const vector<int>`.

Если нужен «const view» контейнера, используют `vector<T> const&` или итераторы `cbegin`/`cend` — keywords `const` на методах iterator типа `const_iterator` задают read-only проход. Путаница: «передал const ref на vector, значит элементы const» — нет, пока тип элемента не const и метод не const.

## const и multithread (связь с томом 3)

**`const`** на shared объекте **не** означает «безопасно читать из многих потоков без синхронизации». Data race — про одновременный доступ, где хотя бы один — write. Const-метод, который только читает поля без mutex, может гоняться с не-const методом, если оба трогают одни данные. **`mutable`** кэш усугубляет: const-метод пишет в mutable поле — для других потоков это write.

Правило из упражнений с mutex: const — про **контракт API**, atomic/mutex — про **модель памяти**. Keyword `const` не заменяет `std::lock_guard`.

## volatile vs atomic — таблица только как якорь

| Вопрос | `volatile` | `std::atomic` |
|--------|------------|---------------|
| Потоки | не синхронизирует | да, с правильным ordering |
| Оптимизатор | не убирает обращения | обычные правила + atomics |
| Embedded MMIO | иногда да | не про регистры |

Остальное — в prose выше: не выбирай `volatile` для счётчика в thread pool.

## Типичные ошибки

Поставить **`volatile int counter`** в воркерах пула и ждать синхронизации — гонки останутся; нужен mutex или atomic. Считать, что **`const T&`** на вложенный объект делает весь граф const — const-ность **не глубокая** для `vector<T>`: элементы через неконst ссылки внутри класса всё ещё можно менять, если метод не const.

**`mutable`** счётчик в const-методе без замка в многопоточной программе — data race. Путать **`constexpr`** с «любой const в заголовке» — в заголовке const globals без `inline` **(C++17)** — отдельная боль линковки (глава 2), не квалifier.

## Краткое резюме

**`const`** задаёт неизменяемость через имя: объекты, указатели, методы, перегрузки по const. **`volatile`** запрещает агressive оптимизации доступа к памяти; для потоков не заменяет **`std::atomic`**. **`mutable`** позволяет менять поля в const-методах — кэш, статистика, mutex — с ответственностью за потоки. **`constexpr`** — про compile-time; не каждый `const` — `constexpr`. Глубокая const-ность контейнеров не следует автоматически.
