# Глава 1. Цепочка сборки

## Зачем эта тема

Сообщение «ошибка на строке 42» может относиться к **исходнику**, к **развёрнутому макросу** после `#include`, к **несовпадению сигнатур при линковке** или к **старому объектном файле**, который CMake не пересобрал. Пока этапы **preprocess → compile → assemble → link** смешаны в одну «магическую команду `g++`», флаги из следующих глав кажутся произвольными, а CMake — чёрным ящиком, который «сам знает».

На треке `multithread/` ты уже собирал цели вроде `06_thread_pool`: несколько `.cpp`, один executable, иногда header-only шаблоны в `08_parallel_map`. Каждый такой `.cpp` проходит **свою** цепочку до `.o`, а линковщик склеивает `.o` в бинарник. Если понимать, где обрывается pipeline, ты быстрее отличишь «забыл `-pthread`» от «опечатка в типе» и не будешь чинить линковку правкой синтаксиса.

## Четыре фазы одной команды g++

Когда ты пишешь `g++ main.cpp -o app`, на самом деле работает **драйвер** `g++`: он запускает препроцессор, компилятор C++ (`cc1plus`), ассемблер и линковщик (`collect2` → `ld`). Ты почти никогда не вызываешь их по отдельности — и это нормально. Важно знать, **какой этап** сгенерировал строку в терминале.

**Препроцессор** обрабатывает `#include`, `#define`, `#if`, `#ifdef`. На выходе — один длинный текст (условно файл `.i`), где директивы исчезли, а содержимое заголовков вставлено **inline**. Ошибка «в `vector` на строке 2000» часто означает: проблема в **твоём** файле на строке 3, где был `#include <vector>`. Номера строк в сообщении после препроцессора могут не совпадать с тем, что ты видишь в редакторе — редко, но бывает на тяжёлых макросах.

**Компиляция** (C++ front-end) разбирает текст на токены, строит AST, проверяет типы, выбирает overload, инстанцирует шаблоны. Здесь рождаются сообщения про `noexcept`, «candidate template ignored», несуществующий метод. Эта фаза **не** знает, есть ли у тебя `main` в другом `.cpp` — она видит только **одну** единицу трансляции (TU).

**Ассемблер** превращает сгенерированные инструкции в **объектный файл** `.o`: машинный код плюс **таблицы символов** — имена функций и переменных, а также **неразрешённые ссылки** на символы из других TU или библиотек.

**Линковщик** собирает `.o` и библиотеки (`libc`, `libstdc++`, `libpthread`) в **исполняемый файл** или разделяемую библиотеку `.so`. Классика многопоточного курса: **`undefined reference to pthread_create`** или к методу `ThreadPool::submit` — это **линковка**, не «синтаксис C++». Компиляция прошла, символ не нашли при склейке.

## Только компиляция: -c

Раздельная компиляция — основа CMake и любого крупного проекта:

```bash
g++ -std=c++17 -Wall -c task.cpp -o task.o
g++ -std=c++17 -Wall -c test.cpp -o test.o
g++ task.o test.o -o exercise -pthread
```

Флаг **`-c`** останавливает pipeline после объектника. Вторая команда **не** передаёт `-Wall` на `.o` — предупреждения уже были на этапе compile. Третья — **link**: здесь обязателен **`-pthread`** для упражнений с `std::thread`, как в `AGENTS.md`.

Так работает `cmake --build`: изменил только `task.cpp` — пересобирается один `.o`, link быстрый. Если линковщик жалуется, а compile чистый — смотри список `.o` в target и флаги link (глава 7).

## Препроцессор отдельно

Иногда нужно увидеть «что реально компилируется»:

```bash
g++ -std=c++17 -E file.cpp | less
```

Полезно при подозрении на макрос или странный `#if`. Для обычного учебного кода не злоупотребляй — вывод на тысячи строк. Флаг **`-save-temps`** оставляет `.i` и `.s` на диске для глубокой отладки toolchain — за пределами базового курса, но термин полезен на собеседовании.

## Драйвер vs компилятор vs линковщик

`g++` — **драйвер**: подбирает дочерние программы и передаёт им аргументы. `clang++` устроен похоже. Флаги **compile-only** (`-Wall`, `-std=c++17`, `-I`) идут в front-end. **Link-only** (`-pthread`, `-lfoo`, `-Wl,...`) — линковщику. Некоторые (`-g`, `-O2`, `-fsanitize=thread`) затрагивают **оба** этапа — отсюда правило «sanitizer и на compile, и на link» в томе 7.

Если вызвать `ld` вручную без libstdc++ и crt — получишь «пустой» мир без `_start`. Драйвер добавляет системные объекты и библиотеки по умолчанию. Поэтому «одна строка g++» из главы 13 проще, чем воспроизвести link руками.

## Сценарий: три файла thread pool

Advanced `06_thread_pool` в CMake перечисляет `thread_pool.cpp`, `smithy.cpp`, `test.cpp`. Это **три TU**, **три `.o`**, один link в `06_thread_pool`. Заголовок `thread_pool.hpp` **не** компилируется сам — его текст попадает в каждый `.cpp`, который делает `#include`.

Если забыл добавить `thread_pool.cpp` в `add_executable`, линковщик увидит объявление методов из заголовка, но **не найдёт** определений — снова `undefined reference`. Ошибка выглядит как «C++ сломан», а лечится списком исходников в target (глава 10).

## Ошибки по фазам — шпаргалка

На этапе **compile** ты видишь `error:` с указанием файла `.cpp` и строки из редактора (обычно). Слова `template`, `noexcept`, `expected ')'` — front-end.

На **link** — `undefined reference`, `multiple definition`, иногда `cannot find -l...`. Файл в сообщении может быть `.cpp`, но суть — символы между TU.

«Stale build»: compile не запускался, потому что CMake решил, что `.cpp` не менялся, а ты правил заголовок, который включён в десять TU — нужен rebuild или touch. Это уже граница CMake, но корень — понимание TU.

## Связь с репозиторием

`multithread/check.sh` гоняет все восемь целей через один `build/`. Каждая цель — свой набор `.cpp` и свои include paths (`target_include_directories` в `CMakeLists.txt`). Beginner собирает `task.cpp` + `test.cpp`; advanced добавляет фабрику, smithy, несколько translation unit.

Header-only `parallel_map.hpp` в `08` инстанцируется из `test.cpp` — **один** `.o`, но шаблоны генерируют код в этом TU. Это не «отдельная компиляция hpp», а особый случай include (глава 8).

## Типичные заблуждения

«Одна ошибка — одна фаза» — linker errors после **чистой** компиляции обычны. «`#include` компилирует библиотеку один раз на весь проект» — нет: **каждый** `.cpp` заново разворачивает заголовки; выигрыш — кэш `.o`, не общий AST.

«`clang++` и `g++` дают один бинарник побитово» — нет, но **стандартный C++** один; для курса достаточно одного компилятора. «Если `g++` одной строкой собралось, CMake лишний» — CMake фиксирует те же флаги для всех и для clangd (глава 11).


## Практика: verbose pipeline

Чтобы **увидеть** вызовы дочерних программ, GCC умеет **`-v`** (verbose). Одна команда:

```bash
g++ -v -std=c++17 -c multithread/beginner/01_rocket_launch/task.cpp -o /tmp/task.o 2>&1 | less
```

В хвосте лога — реальный **`cc1plus`**, пути к **`crtbegin.o`**, **`libstdc++.a`**. Тебе не нужно заучивать каждый путь; достаточно увидеть, что **link** — отдельный шаг с **`collect2`**. Clang: **`clang++ -v`** — та же идея.

Сохранить препроцессированный TU для маленького файла:

```bash
g++ -std=c++17 -E multithread/beginner/05_highscore/task.cpp | wc -l
```

Сравни с числом строк в редакторе — разница показывает «сколько текста добавили заголовки». Это объясняет, почему первая компиляция после `#include <iostream>` **дольше**, чем правка одной строки в **`task.cpp`**.

## Разбор типичных сообщений по фазам

**Compile-time:** `error: 'mutex' in namespace 'std' does not name a type` — часто забыли **`#include <mutex>`** или собирают как C без **`g++`**. `error: no matching function for call to 'lock'` — overload / const, фаза front-end.

**Link-time:** `undefined reference to std::thread::thread(...)` — почти всегда **нет `-pthread`** на link (глава 7). `multiple definition of main` — два файла с **`main`** в одном target (не случай beginner, если случайно добавил **`main`** в **`task.cpp`**).

**Stale object:** симптом — «я исправил заголовок, а поведение старое». Решение: **`cmake --build build --target ... --clean-first`** или удалить конкретный **`.o`**. Корень — TU уже скомпилирован с другим текстом заголовка.

## Связь с check.sh

**`multithread/check.sh`** (не правь без запроса) предполагает, что все targets из **`CMakeLists.txt`** собираются в **`build/`**. Каждый target — свой набор **`.o`** и один link. Если понимаешь pipeline, лог **`check.sh`** читается как «N раз compile + N раз run test», а не магия.


## Историческая заметка: K&R compile model

Модель «каждый `.c` → `.o` → link» старше C++. C++ добавил templates, exceptions, mangling — но **pipeline** тот же. Modules **(C++20)** пытаются изменить **единицу** компиляции; **`multithread`** их не использует — classic TU model из этой главы остаётся актуальной для всего репо.

## collect2 и линковка libstdc++

Драйвер **`g++`** передаёт **`‑lstdc++`** по умолчанию. Явный **`‑nodefaultlibs`** — только для embedded/experts; сломаешь **`training`**, если по эксперimentу уберёшь defaults.

## Углубление: связь с пройденным курсом multithread

Ты уже реализовал **`01_rocket_launch`** — там важно было **`join`**, не pipeline. С точки зрения toolchain это один **`task.cpp`**, один **`test.cpp`**, один link с **`-pthread`**. **`02_ticket_office`** — тот же каркас; mutex не меняет флаги, но если забудешь **`-std=c++17`**, **`std::mutex`** всё равно есть (C++11), зато другие привычки (bindings, optional в других файлах) поплывут.

**`03_oracle`** — **`async`**; link как у thread. **`04_elevator`** — первый раз, когда Debug с **`-g`** реально нужен для lost wakeup: без символов **`wait`** в gdb — адрес. **`05_highscore`** — atomics; Release **`-O2`** не заменяет CAS, но UB без atomics проявится иначе на Release.

**`06_thread_pool`** — первый target с **тремя** `.cpp` в **`CMakeLists.txt`**. Ошибка «не тот список файлов» — глава 8 и 10. **`07_pipeline`** — два `.cpp` и header-only queue. **`08_parallel_map`** — один test TU, шаблон в hpp; **`Threads`** всё равно на link, потому что **`parallel_map`** создаёт **`std::thread`**.

Когда перечитываешь том 5 после сдачи advanced, отметь галочкой: «эта глава объясняет мой симptom N». Так книга становится справочником, не только линейным чтением.

## Углубление: чтение вывода cmake --build

Первые строки compile — **`Building CXX object`**, имя **`.o`**, путь к **`.cpp`**. Link — **`Linking CXX executable`**, имя **`06_thread_pool`**. Если compile прошёл, а link упал — scroll к **link** stanza, не к первому warning compile.

Warning в **`test.cpp`**, который «не трогаешь» — всё равно **твой** build; CI не разделит «виноват test». Репетитор может сказать «игнорируй test», но toolchain всё равно показывает warning — решай, нужен ли **`‑Wno`** или fix в **`task`**.

## Углубление: дисциплина build directory

Один **`build/`** на ветку git — норма. Два clone репо — два **`build/`**. Не копируй **`build/`** между машинами. **`compile_commands.json`** привязан к absolute paths на машине — на другом ноутбуке regenerate.

## Мини-кейс для самостоятельной проверки toolchain

Возьми **`multithread/beginner/02_ticket_office/`** (или любую сданную задачу). Собери через CMake target **`02_ticket_office`**. Затем собери одной строкой **`g++`** из главы 13 с **`-Wextra -Wpedantic`**. Оба run должны быть зелёными. Если расходятся — выпиши diff флагов из **`compile_commands.json`** и ручной команды. Повтори для **`06_thread_pool`** только через CMake (ручная строка длиннее). Запиши один вывод **`ldd`** на любой binary. Это занимает 15 минут и закрепляет том лучше, чем перечитывание без terminal.

## Краткое резюме

Сборка — цепочка фаз; **`-c`** останавливает после `.o`; **link** разрешает символы и подключает `libstdc++`, `pthread`. Читай ошибку с пониманием этапа. Репозиторий `multithread/` — несколько TU на target, pthread на link. Дальше — что установить на Fedora и как проверить версию компилятора.
