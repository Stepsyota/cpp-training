# Глава 2. Toolchain на Fedora

## Зачем эта тема

Книга и репозиторий `training` предполагают **Fedora + GCC/Clang**, как на машине, где ты уже проходил `multithread/`. Это не снobизм: разные минорные версии GCC меняют, доступны ли coroutines **(C++20)**, `std::jthread`, modules или `import std`. Команды `dnf`, проверка `g++ --version` и понимание «кто есть кто в `/usr/bin`» — часть ответа на вопрос «в томе написано C++23, а компилятор молчит» или «на ноутбуке собралось, в CI — нет».

Toolchain — не только бинарник компилятора. Это **libstdc++** (реализация STL от GCC), **заголовки** в `/usr/include/c++`, **linker** из binutils, **cmake**, **gdb** (том 6), опционально **clang** как второй front-end. Без этой карты легко перепутать «обновил Fedora» с «автоматически получил все фичи C++23».

## Базовые пакеты

Для C++ на Fedora обычно ставят группу разработки и отдельные инструменты:

```bash
sudo dnf install gcc-c++ cmake ninja-build gdb
```

**`gcc-c++`** даёт драйвер **`g++`**, компилятор C++, стандартную библиотеку **libstdc++** и заголовки STL. Без этого пакета `g++` просто отсутствует, а `gcc` может собирать только C.

**`cmake`** — генератор build-системы; в репо `multithread/` configure выглядит как `cmake -S . -B build`. **`ninja-build`** — быстрый backend (`cmake -G Ninja -S . -B build`); на больших проектах пересборка приятнее, чем Makefiles по умолчанию.

**`gdb`** — отладчик; том 5 лишь готовит символы `-g`, том 6 научит `break`, `next`, потоки. Установи заранее, чтобы не откладывать отладку «на потом».

Дополнительно для документации и разработки:

```bash
sudo dnf install cpp man-pages-devel
```

`cpp` — препроцессор GCC отдельно; редко нужен вручную, но иногда полезен для `-E` без полного `g++`.

## Clang параллельно с GCC

```bash
sudo dnf install clang clang-devel lld
```

**`clang++`** — другой front-end (parser, diagnostics), часто более читаемые сообщения об ошибках в шаблонах. На типичной Fedora Linux **по умолчанию** Clang всё ещё линкует с **libstdc++** от GCC, а не с **libc++** (как на macOS). Для учебника это плюс: STL одна, поведение ближе к `g++`.

Проверка:

```bash
clang++ --version
g++ --version
```

Сборка того же target через Clang:

```bash
cd multithread
cmake -S . -B build-clang -DCMAKE_CXX_COMPILER=clang++
cmake --build build-clang --target 02_ticket_office
```

Если что-то падает только на одном компиляторе — зафиксируй версии в багрепорте или в чате с репетитором.

## Версии компилятора и стандарты

Fedora двигает **GCC** с релизом дистрибутива: Fedora 40, 41, 42 — разные GCC 13/14/… Таблицу «GCC X = полный C++20» **не заучивай** — смотри [статус C++ в GCC](https://gcc.gnu.org/projects/cxx-status.html) и пометки **(C++20)** в томах 1–4.

Правило для практики:

- флаг **`-std=c++17`** (или CMake `CMAKE_CXX_STANDARD 17`) **запрашивает** режим языка;
- **версия GCC/Clang** решает, **реализована** ли конкретная фича в этом режиме.

Пример: `-std=c++20` не гарантирует рабочие modules **(C++20)** — у GCC они долго были experimental и требовали отдельных флагов. Книга помечает такие вещи явно, чтобы ты не смешивал «стандарт на бумаге» и «фича в твоём `g++ --version`».

## gcc vs g++

**`gcc`** — драйвер, который умеет и C, и C++, но для `.cpp` принято вызывать **`g++`**. Драйвер `g++` автоматически подключает **libstdc++** и выставляет согласованные defaults для C++. Если собрать `.cpp` через `gcc` без явного **`-lstdc++`**, можно получить странные ошибки линковки на `std::` символах.

На практике: в репо, в AGENTS.md и в однострочниках главы 13 — **`g++`**, не `gcc`.

## libstdc++ и ABI

Объектные файлы и библиотеки C++ завязаны на **ABI** libstdc++ (layout `std::string`, `std::list`, exception handling). Смешивать `.o`, собранные **разными мажорными** версиями GCC, или линковать старый `.o` с новой `libstdc++.so` — рецепт subtle crash, не обязательно immediate link error.

В учебном репо всё собирается **одним** компилятором в одном `build/` — проблем нет. Если скачал чужой бинарник или `.a` — это уже чужой ABI; для курса не актуально, но на собеседовании «почему нельзя смешивать компиляторы» звучит часто.

## alternatives и несколько версий GCC

На одной машине иногда стоят **toolset** side-by-side (`gcc-14`, `g++-14`). `update-alternatives` переключает симлинк `/usr/bin/g++`. Если ты не настраивал — **не трогай**; для экспериментов безопаснее полный путь:

```bash
/usr/bin/g++-14 --version
```

CMake выбирает компилятор при первом configure (`CMAKE_CXX_COMPILER`). Сменил системный `g++` — иногда нужен **чистый** каталог `build/`, иначе cache помнит старый путь.

## Связь с CI и томом 0

В репозитории может быть каталог `cicd/` (том 0 упоминает pipeline). Флаги там должны совпадать с локальными: **C++17**, предупреждения, **pthread**. Если job крутится на другом дистрибутиве или в контейнере — первым делом смотри **`g++ --version`** в логе, не только «зелёная галочка».

Локально «у меня Fedora 42» не гарантирует идентичность CI, если там Ubuntu LTS с GCC постарше.

## Сценарий первого дня на новой машине

Ты клонировал `training`, открыл `multithread/` в Cursor. Минимальный чеклист:

1. `g++ --version` — компилятор на месте?
2. `cmake --version` — не ниже 3.16, как в `CMakeLists.txt`?
3. `cmake -S . -B build && cmake --build build --target 01_rocket_launch`
4. `./build/01_rocket_launch` — зелёный старт.

Если шаг 3 падает на «compiler not found» — вернись к `dnf install gcc-c++ cmake`. Если падает на C++14 defaults — в следующей главе `-std=` и CMake standard.

## К собесу

Уметь назвать разницу **front-end** (gcc/clang) и **runtime STL** (libstdc++/msvc runtime). Объяснить, почему для `.cpp` вызывают **`g++`**. Сказать, что **версия дистрибутива** ≠ **полная поддержка C++20/23** без status page.

## Типичные заблуждения

«Поставил clang — автоматически libc++» — на Fedora Linux чаще всё ещё **libstdc++**. «Новая Fedora = все фичи C++23 в `-std=c++23`» — проверяй implementation status. «cmake скачивает компилятор» — нет, только генерирует Ninja/Make и вызывает уже установленный `g++`. «gdb ставить не обязательно до отладки» — ставь вместе с toolchain, иначе отложишь навсегда.


## Версии на типичной рабочей станции

Когда читаешь книгу на Kindle, а собираешь на ноутбуке, сверяй **три числа**: версия **Fedora**, **`g++ --version`**, **`cmake --version`**. Запиши их в заметку репетитору один раз — потом не спорить «у меня должно работать», не зная toolchain.

Пример диагностики «какой компилятор выбрал CMake»:

```bash
grep CMAKE_CXX_COMPILER multithread/build/CMakeCache.txt
```

Если там **`/usr/bin/g++`**, а ты думал про **`clang++`** — IDE и build могут расходиться, пока не сделаешь **`-DCMAKE_CXX_COMPILER=clang++`** в **новом** каталоге build.

## devcontainer, toolbox, WSL

Некоторые читатели собирают **`training`** в **Fedora toolbox** или **WSL** с Fedora/Ubuntu. Книга не требует именно bare metal, но **требует согласованности**: если в контейнере Ubuntu, версия GCC может отличаться от «Fedora в тексте» — сверяй **`cxx-status`**, не номер главы.

**WSL2** + Windows IDE: **`compile_commands.json`** часто генерируют в Linux-дереве, а Cursor открывает **`\\wsl$\...`** — пути в json должны быть **теми же**, что видит clangd (иногда нужен **`clangd.pathMappings`** — за пределами базового курса).

## Пакеты, которые пригодятся позже

**`valgrind`** — не sanitizer, но memory; том 7 фокус на ASan/TSan. **`strace`** — syscalls при «зависании» (осторожно с шумом). **`perf`** — profiling Release **`08_parallel_map`**. Устанавливай по мере перехода к томам 6–7, не обязательно в первый день.

## Обновление системы и пересборка

После **`dnf upgrade`** с новым **libstdc++** старые **`build/`** object files **обычно** совместимы в пределах одного мажорного GCC, но при смене **мажора** compiler — **удали `build/`** и configure заново. Симптом: странные crash в **`std::string`** после обновления системы без clean rebuild.


## rpm -ql gcc-c++

**`rpm -ql gcc-c++ | head`** — какие файлы поставил пакет: **`/usr/bin/g++`**, headers under **`/usr/include/c++/`**. Понимание «откуда **`#include <vector>`**» — не заучивание путей, а уверенность, что **toolchain package** установлен полностью, не только **`gcc`**.

## clang libstdc++ vs libc++

**`-stdlib=libc++`** у **`clang++`** — другая STL; на Fedora может потребовать **`libcxx-devel`**. **Не** смешивай с **`multithread`** без причины; книга assumes **libstdc++**.

## Углубление: связь с пройденным курсом multithread

Ты уже реализовал **`01_rocket_launch`** — там важно было **`join`**, не pipeline. С точки зрения toolchain это один **`task.cpp`**, один **`test.cpp`**, один link с **`-pthread`**. **`02_ticket_office`** — тот же каркас; mutex не меняет флаги, но если забудешь **`-std=c++17`**, **`std::mutex`** всё равно есть (C++11), зато другие привычки (bindings, optional в других файлах) поплывут.

**`03_oracle`** — **`async`**; link как у thread. **`04_elevator`** — первый раз, когда Debug с **`-g`** реально нужен для lost wakeup: без символов **`wait`** в gdb — адрес. **`05_highscore`** — atomics; Release **`-O2`** не заменяет CAS, но UB без atomics проявится иначе на Release.

**`06_thread_pool`** — первый target с **тремя** `.cpp` в **`CMakeLists.txt`**. Ошибка «не тот список файлов» — глава 8 и 10. **`07_pipeline`** — два `.cpp` и header-only queue. **`08_parallel_map`** — один test TU, шаблон в hpp; **`Threads`** всё равно на link, потому что **`parallel_map`** создаёт **`std::thread`**.

Когда перечитываешь том 5 после сдачи advanced, отметь галочкой: «эта глава объясняет мой симptom N». Так книга становится справочником, не только линейным чтением.

## Углубление: чтение вывода cmake --build

Первые строки compile — **`Building CXX object`**, имя **`.o`**, путь к **`.cpp`**. Link — **`Linking CXX executable`**, имя **`06_thread_pool`**. Если compile прошёл, а link упал — scroll к **link** stanza, не к первому warning compile.

Warning в **`test.cpp`**, который «не трогаешь» — всё равно **твой** build; CI не разделит «виноват test». Репетитор может сказать «игнорируй test», но toolchain всё равно показывает warning — решай, нужен ли **`‑Wno`** или fix в **`task`**.

## Углубление: дисциплина build directory

Один **`build/`** на ветку git — норма. Два clone репо — два **`build/`**. Не копируй **`build/`** между машинами. **`compile_commands.json`** привязан к absolute paths на машине — на другом ноутбуке regenerate.

## Мини-кейс для самостоятельной проверки toolchain

Возьми **`multithread/beginner/02_ticket_office/`** (или любую сданную задачу). Собери через CMake target **`02_ticket_office`**. Затем собери одной строкой **`g++`** из главы 13 с **`-Wextra -Wpedantic`**. Оба run должны быть зелёными. Если расходятся — выпиши diff флагов из **`compile_commands.json`** и ручной команды. Повтори для **`06_thread_pool`** только через CMake (ручная строка длиннее). Запиши один вывод **`ldd`** на любой binary. Это занимает 15 минут и закрепляет том лучше, чем перечитывание без terminal.

## К собесу (дополнение)

Назови пакет `gcc-c++`. Объясни разницу front-end Clang и libstdc++. Почему не смешивать `.o` разных мажорных GCC.

## Краткое резюме

**`dnf install gcc-c++ cmake gdb`**; по желанию **clang++** и **ninja**. Сверяй **`--version`** с фичами стандарта из книги. Используй **`g++`** для C++. Один `build/` — один ABI. Дальше — как зафиксировать **C++17**, как в `multithread/CMakeLists.txt`.
