# 01. Контрольный скрипт

Сейчас на работе ты вручную собираешь и проверяешь. В CI первым делом
автоматизируют **то же самое одной командой** — у нас это `./check.sh`.

В `multithread/check.sh` лежит **эталон идеи** (cmake, build, прогон
тестов, exit code). **Не копируй** его слепо: здесь другой продукт и
другая структура. Напиши **`cicd/check.sh` сам** по спецификации ниже.

Файл уже создан: в нём только заглушка `exit 1`.

## Что должно получиться

Запуск из каталога `cicd/`:

```bash
./check.sh
```

Скрипт:

1. падает с понятной ошибкой при сбое любой команды (`set -euo pipefail`);
2. конфигурирует CMake для `workshop/` в `cicd/build/`;
3. собирает таргеты `forge_cli` и `forge_cli_test`;
4. запускает `./build/forge_cli_test` — он печатает `OK` и exit 0;
5. при успехе exit 0, при провале теста или сборки — exit ≠ 0.

Путь к корню `cicd/` не должен зависеть от того, откуда вызвали скрипт
(подсказка: `dirname "$0"`).

## Подсказки (не решение)

- Shebang: `#!/usr/bin/env bash`
- `ROOT="$(cd "$(dirname "$0")" && pwd)"` — аналог multithread, но свой каталог
- `cmake -S "$ROOT/workshop" -B "$ROOT/build"`
- `cmake --build "$ROOT/build" -j$(nproc)` или без `-j`
- Проверка: `"$ROOT/build/forge_cli_test"` — если exit 0, в конце `exit 0`
- Не забудь `chmod +x check.sh` после первого сохранения

## Зачем это в CI/CD

Job в GitLab — это по сути:

```yaml
script:
  - cd cicd && ./check.sh
```

Пока скрипт красный локально — CI будет красным. Сначала зелёный локально,
потом упражнение 02.

## Проверка

```bash
cd cicd
chmod +x check.sh
./check.sh
echo $?    # должно быть 0
```

Когда будешь готов — напиши «проверь check.sh», разберём без подмены файла.
